# 迪卡侬中国 · Digital 部门门户 产品方案

**版本** v1.0 ｜ **日期** 2026-09-17 ｜ **状态** 可评审
**配套交付**：可交互高保真原型（`portal/`，双击 `dist/index.html` 即可打开，含 375 / 768 / 1440 / 1920 四档）

## 一、结论前置

这个门户要成立，靠的不是功能数量，是两件事：

1. **每个内容块都必须有 Owner 和更新节律**，并且让使用者看得见。
2. **三次点击内必须能找到东西**——找不到就说明信息架构错了，不是用户不熟。

其余都是执行细节。反过来，任何一版方案如果这两条没落实，功能做得再多也会在 3–6 个月内变成一个没人维护的静态页。

还有一条定位必须先说清楚，否则后面全错：

> **门户的竞争对手不是 IM，是"遗忘"。**
> IM 永远更快——讨论一件事，IM 是更优解，我们不该和它抢。门户要赢的是另一个场景：**三个月后新人问"这个决定当初为什么这么定"，而群里已经翻不到了。**
> 所以门户的定位是**权威沉淀与检索**，不是实时沟通。凡是"要快"的信息仍然走 IM；凡是"要准、要能追溯、要能被下一代人找到"的，才进门户。

## 二、三个痛点 → 用户任务

| # | 谁 | 什么时候 | 想干什么 | 现状 |
|---|---|---|---|---|
| A1 | 工程师 | 早上到岗 / 会后 | 30 秒内掌握"昨天到今天"有哪些重要决议 | 翻聊天记录 + 邮件堆，怕漏、无权威单一来源 |
| A2 | 产品/项目经理 | 决议发生时 | 第一时间知道并判断是否影响我的排期 | 靠别人口头转告，滞后且失真 |
| A3 | Team Leader | 发布重要决议时 | 让目标人都看到，且可追溯 | 群里被刷屏、邮件被淹没，触达不可控 |
| B1 | 新入职工程师 | 接入某个内部系统时 | 知道它叫什么、入口在哪、怎么申请权限 | 完全不知道从何找起，只能反复问人 |
| B2 | 工程师 | 记得有工具能查日志/发版但想不起入口 | 几秒内到达正确入口 | 在收藏夹和聊天记录里翻，平均数分钟 |
| B3 | 任何人 | 遇到某类问题想找对应系统 | 按"我要做的事"而不是"系统名字"找到工具 | 导航靠记名字，心智与工具名不匹配 |
| C1 | 新人 | 入职首月 | 系统性了解技术栈、流程、规范、最佳实践 | 全靠口口相传，上手周期长 |
| C2 | 资深工程师 | 踩坑并总结出最佳实践后 | 把它沉淀成可复用文章，让团队看到并复用 | 没有载体，写完没人看，下次还被重复踩 |
| C3 | on-call / 负责人 | 全天特别是故障期 | 随时掌握核心系统流量、资源、稳定性 | 要登录多个平台来回切换，发现时间变长 |
| C4 | 任何成员 | 遇到具体操作问题 | 自助找到答案，找不到再问人 | 没有 FAQ 或答案过时，只能等人工回复 |

## 三、信息架构：不做 10 个模块平铺

**核心主张：1 首页 + 4 分区 + 1 全局能力层。按用户任务分区，不按内容来源分区。**

```
Digital 门户
├─ ① 首页 · 今日 Hub         主编排层，不是模块
│     置顶决议 · 健康度快照 · 近期 Release · 里程碑精选 · 快捷入口 · Agent 引导
├─ ② 信息中心                时效性信息流
│     公告与决议 · 产品 Release · 项目动态
├─ ③ 监控运营                实时数据
│     L1 健康度看板（流量 / 资源 / 稳定性）
├─ ④ 知识中心                沉淀与检索，不强调时效
│     最佳实践 · 设计规范 · FAQ
├─ ⑤ 工作台                  找资源、提需求
│     工具导航（服务目录）· 组织速查 · 需求提交
└─ ⚡ 全局层                  跨分区常驻，不占导航位
      全局搜索 · Agent for Digital · 通知
```

### 模块归位与取舍

| 原模块 | 归位 | 判断 |
|---|---|---|
| 1 最新公告及决议 | ② 信息中心（默认频道） | 门户的心脏，直接命中痛点 A |
| 2 监控看板 | ③ **独立分区** | 不并入信息流——数据源、刷新机制、受众（on-call/负责人）都不同，混流会污染信息中心 |
| 3 设计规范 | ④ 知识中心 | 与最佳实践同属"长期检索型"，共享分类与搜索。**若已有独立规范站点，做聚合入口而非重建** |
| 4 产品 Release | ② 信息中心（子频道） | 本质是"随时间产生的重要信息"，与公告同心智，共用订阅与置顶机制，避免再造孤岛 |
| 5 项目进度更新 | ② 信息中心（子频道） | 与动态信息同源。**结构化看板依赖项目管理工具打通，MVP 只做动态列表** |
| 6 最佳实践文章 | ④ 知识中心 | 解决痛点 C 的主阵地，需分类/标签/搜索，不强调时效 |
| 7 组织架构员工速查 | ⑤ 工作台（**已降级**） | 企微/通讯录已能查人，自建一份是重复建设。**降级为"关键联系人 + 全局搜索命中"，不做完整模块** |
| 8 常用入口工具导航 | ⑤ 工作台 | 解决痛点 B 的最高性价比模块。**做成服务目录，不是链接墙**（见下） |
| 9 FAQ + Agent | ④ + ⚡ **拆开** | FAQ 是内容，Agent 是**贯穿全站的能力**——它应该能回答公告、工具、规范，锁在一个 Tab 里等于废掉一半价值 |
| 10 需求提交入口 | ⑤ 工作台 | 属"提交/服务"动作。**MVP 只做表单 + 提交记录，打通需求管理工具放二期** |

### 两条容易被忽略的设计要求

**工具导航必须是"服务目录"。** 每张工具卡都要有：用途、**Owner**、**运行状态**、**权限申请入口**。少了 Owner 和状态，它就退化成浏览器收藏夹——那用户为什么不用自己的收藏夹？这一条是从内部开发者门户（Backstage）学到的核心：门户的价值密度等于**上下文基础设施**（谁拥有什么、依赖是什么、标准在哪）的完整度。

**公告必须分层。** 重点公告用大卡承载（置顶、必读、制度变更），日常公告走紧凑列表。时间倒序一长串平铺，等于把"重要"和"不重要的"拉平——那正是 IM 群消息的问题，把它复制到门户里毫无意义。

## 四、三个关键架构决策

### 决策 1：监控只做 L1 概览，一键下钻，不做嵌入

**决定**：门户承载 L1 层（核心系统可用性、SLO 达成、错误预算余量、当前责任人），深挖一律跳转到 Grafana 等专业平台。**不把监控大屏 iframe 嵌进门户。**

**理由**：
- 数据已在监控系统里，重建采集/存储管道成本高、维护重，且容易与真实源不一致。
- 嵌入界面技术脆弱、视觉割裂、维护双份。
- 门户里的监控受众是**部门全员**（"现在系统健康吗"），不是值班工程师（"哪个 Pod 在抖"）。用运维看板的密度服务全员，是把 20% 的需求强加给 80% 的人。

**关键**：这个决策必须**画进界面**，而不只是写在文档里。原型在监控页显式说明"本页只承载 L1 概览，具体时序明细与告警认领需在专业平台完成"，并给出三个下钻卡。否则用户会持续抱怨"门户的监控不好用"。

### 决策 2：Agent 二期再上 LLM，MVP 先做"结构化 FAQ + 反馈闭环"

**决定**：MVP 交付可检索的 FAQ 库 + 「这个回答有用吗」反馈 + 兜底提问入口；LLM 对话式 Agent 放二期。但 **Agent 的入口在 MVP 就要占位**（顶栏常驻 + 首页引导条），因为它是整个门户的交互范式方向。

**理由**：LLM 依赖知识库结构化、权限隔离、幻觉控制和成本评估。先用结构化 FAQ 验证核心价值——**"自助解决率"**——再上智能体，风险更低、见效更快。

**但真正要紧的是这条顺序**：

> **知识底座必须先于 Agent 存在。**
> Agent 能回答什么，完全取决于它脚下有什么。模块 1/3/4/5/6（公告、规范、Release、项目动态、最佳实践）的沉淀物就是它的知识底座。如果这些内容是空的，接再好的模型也只能编。
> 换句话说：**Agent 的门槛不是模型能力，是内容资产。**

**MVP 里最容易被漏掉、但最决定 Agent 二期成败的机制**：

```
用户提问 → Agent 答不出/答不好 → 用户点"没帮到我"
    → 问题自动进入「待补知识」队列（带来源组、等待天数、关注人数）
    → 指派给该领域内容 Owner → 补齐内容 → 回流进知识库
```

这个闭环让 Agent 同时是 FAQ 的**消费端和生产端**。跑不起来，知识库三个月就过时；跑起来，门户就从"静态知识库"变成"活知识系统"。**所以它必须出现在 MVP 的界面上，而不是文档里。**

### 决策 3：需求提交 MVP 只做表单 + 提交记录

打通 Jira / Meego / TAPD 涉及字段映射、权限、双向状态同步，是典型二期工程，不该阻塞 MVP。

一个补充：提交页不能只有表单，**必须能看到"别人提了什么、处理到哪一步"**。只有提交入口没有公开列表，用户会认为它是个黑洞，从而继续走 IM 提需求——那等于白做。

## 五、分期

### P0 · MVP 首发

| 内容 | 说明 |
|---|---|
| 首页 · 今日 Hub | 置顶决议 / 健康度快照 / 近期 Release / 里程碑精选 / 快捷入口 / Agent 引导 |
| 信息中心 | 公告与决议、产品 Release（含表格视图）、项目动态（列表版） |
| 监控运营 | L1 概览 + 三个下钻入口 |
| 知识中心 | 最佳实践、设计规范、FAQ + **待补知识队列** |
| 工作台 | 工具服务目录、关键联系人、需求提交（表单 + 公开记录） |
| 全局 | 全局搜索（基础版）、Agent 入口占位、通知 |

### P1 · 二期

最佳实践原生编辑发布 · 设计规范自建或聚合完善 · 组织速查打通通讯录 API · 项目进度结构化看板 · **Agent for Digital 接入 LLM** · 需求提交打通需求管理工具 · 订阅与通知机制

### P2 · 远期

个性化推荐 · 智能摘要 · 监控自建数据管道（收益低，非必要不做）· 与企微/飞书 IM 双向打通

### 关于"订阅 / 已读"的一个硬约束

**用户已决策门户采用无登录鉴权。** 这意味着 MVP 与二期的以下能力**全部不可做**：

- 「我的已读」「我的订阅」「我关注的」
- 个性化推荐、按角色变化的导航
- **公告触达率**（"发布后 24h 内目标读者查看率 ≥80%"）——**无身份即无法测量**

代价明确，但我认为对 50–200 人的部门内网，这个取舍是对的：换来的是零登录摩擦、上线最快、没有权限维护成本。

代价的补偿方式：**用"重要信息向上提升"替代"向特定人推送"**——重要决议一律同步置顶到首页，而不是想办法追踪谁没看。组织规模显著变大后（>300 人、出现子团队）需要重新评估这条决策。

## 六、内容治理机制（决定门户生死的部分）

门户失败的首要原因不是功能少，而是**内容没归属、没生命周期**。成熟门户改造的公开经验是平均可裁掉 60–80% 的页面——因为大量内容无人维护、相互重复。

因此以下机制不是"锦上添花"，是**上线门槛**：

| 机制 | 具体做法 | 为什么必须有 |
|---|---|---|
| **Owner 制** | 每个分区/栏目指定内容负责人，界面上可见「内容负责人 / 最后更新」 | 没有归属就没有维护，半年后必然荒废 |
| **待补知识队列** | 负反馈 → 缺口 → 指派 Owner → 补齐回流 | Agent 与 FAQ 的活水来源 |
| **知识复核** | 条目超过 90 天未更新自动进入待复核队列 | 内部文档最大的问题是"过时"而非"没有" |
| **公告生命周期** | 临时公告设有效期（7–30 天）自动归档；长期政策永久留存 | 防止列表被历史噪音淹没 |
| **工具卡状态** | 每个工具标注 Owner + 运行状态 + 权限要求 | 让"找工具"变成"找到能负责的人" |
| **命名与模板** | 页面/频道统一命名规范；公告、文章、FAQ 各有标准模板 | 降低创建门槛，提升一致度 |

**建议在 MVP 上线前先做一轮"内容治理"而不是先写代码**（见第八节）。

## 七、成功指标

**北极星指标建议**：*"周活跃用户中至少完成一次有效动作（检索命中 / 工具跳转 / 文章阅读）的比例"*。
理由：门户的价值不在"被访问"，在"被使用"。只看 PV 会奖励"把首页做得热闹"，只看留存会奖励"发通知骚扰"。

| 指标 | 目标 | 备注 |
|---|---|---|
| 工具查找耗时 | 从"想用某工具"到"进入正确入口" **< 30 秒** | 可通过门户跳转的点击路径长度代理 |
| FAQ 自助解决率 | **≥ 60%**，且"有用"好评率持续上升 | 核心价值验证指标 |
| **待补知识队列平均清空天数** | **< 7 天** | **最能反映门户是否"活着"的指标** |
| 需求提交闭环率 | 有效需求数 + 平均受理响应 **< 2 个工作日** | 黑洞与否的判据 |
| 知识沉淀量 | 每月新增最佳实践/规范 ≥ N 篇，且阅读/引用持续增长 | 结合复核队列淘汰率一起看 |
| 门户周活跃度 | 部门 WAU 占比 + 人均周访问频次 | 匿名口径 |
| ~~公告触达率~~ | **不可测**（无登录） | 已用"匿名详情页 PV / 部门人数"作为弱代理 |

**特别说明"待补知识队列清空天数"**：它同时衡量了"用户在提问"（有活跃度）和"内容在维护"（有治理）。如果队列只进不出，说明门户已经在死——而这时候 DAU 可能还很漂亮。所以我建议把它作为**首要运营指标**，比 DAU 更有诊断价值。

## 八、落地路径

| 阶段 | 周期 | 内容 | 关键交付 |
|---|---|---|---|
| **阶段 0：内容治理** | 1–2 周 | 确定各栏目 Owner 与更新节律；盘点并迁移存量内容；撰写首批种子内容（10–15 篇最佳实践、30 条 FAQ、完整工具目录） | **这一步不是技术工作，是组织工作。跳过它，门户上线即空。** |
| **阶段 1：MVP 上线** | 3–6 周 | 首页 / 信息中心 / 工作台 / 知识中心（FAQ + 待补队列）；监控走嵌入或跳转 | 可用门户 + 治理机制运转 |
| **阶段 2：能力补齐** | 4–8 周 | Agent 接入 LLM；监控原生 L1 看板；项目进度结构化；需求提交打通工具 | 智能问答 + 数据打通 |
| **阶段 3：演化** | 持续 | 订阅通知、个性化、IM 打通 | 视使用数据决定，不预先承诺 |

**建议的验证方式**：阶段 1 上线后第 4 周做一次评审，只看三个数——**工具查找耗时、FAQ 自助解决率、待补队列清空天数**。这三个数决定后面投不投资源，比任何主观评价都可靠。

## 九、风险

| 风险 | 影响 | 应对 |
|---|---|---|
| **治理失效（Owner 不维护）** | 门户 3–6 个月后退化为静态页 | **最大风险**。从第一天就把"待补队列清空天数/复核队列"作为运营指标考核，而非上线后补 |
| 内容与 IM 重复 | 用户认为"群里也有，为什么要来门户" | 定位必须是"权威沉淀与可追溯"，不做"更快"。凡是能即时解决的一律回 IM |
| 无登录带来的能力天花板 | 无法个性化、无法追踪触达 | 已知取舍。用"重要信息置顶"替代"定向推送"。组织 >300 人时重估 |
| 集成边界未定 | 监控/项目/人员/需求各模块落地方式不明 | **本期最大成本变量**。落地前必须确认各系统是否有可用 API（见第十节） |
| 自建成本被低估 | 门户本身不难，难在长期维护 | 优先"入口聚合"而非"原生重建"，把维护成本压到最低 |

## 十、待决策事项

1. **身份与权限**（已决策：无登录。但需确认这是否会影响后续接入权限敏感的工具入口）
2. **数据源与集成边界**：监控（Grafana?）、Release（发布系统?）、项目进度（Jira/Meego?）、人员（企微/HR?）、需求提交——**分别来自哪些系统、是否有可用 API**。这是本期最大的成本变量，直接决定各模块是"原生自建"还是"入口聚合"。
3. **内容 Owner 名单与更新节律**：谁负责哪个栏目、多久更新一次。
4. **是否已有可复用的资产**：现有设计规范站点、知识库（语雀/Confluence）、工具清单——有的话优先聚合，不重建。
