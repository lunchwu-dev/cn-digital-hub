## 一、本次交付了什么

在已交付门户（Decathlon Digital 部门门户 v0.1）基础上做**两块增量**，解决「业务团队找不到在哪提需求」和「提需求说不清」两个问题。

### 面 1 · 首页强入口（对应需求 1）

首页新增「提交需求」独立区块，**置于「快捷入口」之前**，页面从上到下为：
置顶决议 → 健康度快照 → 双栏 → **提交需求** → 快捷入口 → Agent 条。

区块含三件东西：
- **入口大卡**：白底 + **4px 品牌蓝左侧强调条**（全页唯一，其余强调条均为 3px）+ 主按钮「提交需求」+ 状态摘要（待处理 1 / 进行中 2 / 已完成 3，等宽数字）+ 一句服务承诺「提交后 2 个工作日内由受理人回应并指派，进度在提交页实时可见」
- **公开列表**：最近 3 条，带说明「别人提了什么、处理到哪一步」
- 路由仍在 `#/workspace/demand`（按裁决：留工作台，但首页强入口）

**为什么强调条是 4px 而不是整块品牌蓝填充**：填充会抢走置顶决议的首屏优先级，也会把品牌蓝从「点缀色」降格成「大面积色」。4px 竖条既能在首屏被眼睛抓到，又不喧宾夺主。

### 面 2 · 提交页模板引导 + BRD 助手（对应需求 2）

提交页做**双档分流**（这是本轮最关键的设计判断）：

| | 轻量档（权限 / 其他） | BRD 完整档（功能 / 系统集成） |
|---|---|---|
| 字段 | 5 个，其中 4 项必填 | 8 个字段 |
| 评分 | **不评分** | 启用「资料完整度」 |
| 适用 | 申请权限、登记类需求 | 功能开发、系统对接 |

**为什么必须分档**：一刀切上 8 字段 BRD，内部工程师要个权限就被逼写「现状/期望结果/验收标准」，人会直接跑掉回到 IM 提需求；而只给一张裸表单，业务团队又说不清要什么。分档让两边都留得住。

版式为**左表单 + 右引导栏**（复用既有 `.dp-g-spec`，1.5fr:1fr，≤900px 自动单列）。

**BRD 协作助手**要点：
- 是右栏**内联卡，不是 Drawer**——Drawer 会遮住正在填的表单
- 铁律：**任何时刻气泡里最多 1 条待改建议**；点快捷问题**保留**当前建议，只追加 Q&A（不因"想问一句"丢掉刚拿到的建议）
- 「资料完整度」：进度条 6px **只用品牌蓝，永不随分数变色**；三档命中/部分/缺失**只用中性视觉**（品牌蓝实心 / 品牌蓝描边 / textDisabled 空心）；**不出现红黄绿**
- 不逐项给分值，只给一条行动提示
- 「涉及系统」里的 **「说不清，帮我定位」**——把用户的说不清转成一句服务承诺；选中后其他选项清空/禁用，该维度计 0.5
- 纠偏会真的咬：填「加个导出」这种把方案塞进现象的描述，D1 会掉、完整度从 67% 回落到 47%，并提示「把这句移到期望结果」

**语义色硬边界**：红/黄/绿**只允许**出现在「稳定性状态」区。评分/完整度区域绝不占用语义色——扫过 12 个 success/warning/error 取值，命中 0。

## 四、本轮修掉的三类真问题（含一次真实事故）

### 1. 内联 style 压过媒体查询，窄屏布局静默失效
`.dp-demand-side` 上挂了内联 `display:'flex'`，优先级高于 `@media(max-width:900px){display:contents}`，导致该媒体查询**完全不生效**，窄屏下表单被挤到公开列表之后。
**修法**：删内联，桌面态 flex 改由 CSS 类承载，`display:contents` 才能生效。

### 2. 断言作用域污染 → 空转断言
`AgentDrawer` 用 `getContainer={false}`，关闭后 DOM 仍常驻且含「说不清」等词，整页文本断言会**假通过**。变异删掉真实 chip 文案后 smoke 仍全绿才暴露。
更隐蔽的第二层：该短语在源码有 **5 处**（chip label + 4 处字段 hint），所以只收窄到面板作用域**仍不够**，必须精确定位到 `button[aria-pressed]`。
**修法**：断言前剔除常驻 `.ant-drawer` 子树；关键文案改元素级定位。

### 3.（事故）变异工具崩溃污染工作树 —— 已修复并加固
`tests/mutation.cjs` 存在字段名 bug：备份写 `buf`、还原读 `rec.original`（undefined）→ 写入抛错被吞 → **正常路径下还原也失败**。表现是 smoke 失败数 1→2→…→6 累加，且崩溃后变异**持久残留**在源码里（本轮真实发生，需手工改两行才恢复）。

> **澄清一处错误表述**：审查报告曾写污染「自动复原 / 自愈」，**不属实**。事实是 lead 手工还原（两个文件 mtime 15:00，其余源文件停在 13:41–13:44）。

**加固后**：三层还原（`finally` → `process.on(exit/SIGINT/SIGTERM/SIGHUP/uncaughtException/unhandledRejection)` 同步还原 → 启动自愈）+ `Buffer.compare` 字节级校验 + **前置洁净校验**（sha 不符则 exit 1 且不写任何文件）+ 并发锁。`exit` 模式（跳过 finally、只剩进程钩子）自证通过。
**残留在加固前是「持久污染」，加固后才降级为「运行期窗口」**——这两态必须分开说。

另修正一条危险提示：拒绝文案原写「用 `git checkout --` 恢复」。本仓库这些文件相对 HEAD 带着未提交的特性改动（两个新组件还是 untracked），照做会**连特性一起抹掉**。已改为从 `.mutation-backup` 的 `.bak` 或基线 sha 手工还原，并显式标注禁止 `git checkout`。

## 六、本轮沉淀的可复用经验

1. **`display:contents` 重排方案的容器绝不能挂内联 `display`** —— 内联会压过媒体查询使其静默失效。注释里写「这里生效」不可信，必须实测 computed style。
2. **断言「某文案存在」前必须剔除常驻 DOM**（Drawer/Modal 关闭后仍驻留）。一个文案可能有 3–6 个来源，**修一处 ≠ 修模式**。
3. **验证工具本身也要被验证**。一个「可能改坏被测代码且不还原」的工具比没有它更危险。收工前必须做**对抗性实测**：故意把源码弄脏，确认闸门真的会红。
4. **恢复污染不能想当然用 `git checkout`** —— 先确认工作树相对 HEAD 的状态（有无未提交特性、有无 untracked）。
