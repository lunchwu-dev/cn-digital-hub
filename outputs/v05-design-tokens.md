## 1. 糅合楼层版式（上带身份 + 下带标签）

### 1.1 结构（单 Panel，上下两带）

```
┌─ Panel  className="dp-person-head dp-floor-merged" ────────────────────────┐
│  上带  .dp-person-head-main   padding: 18px 22px                            │
│        [头像64] 姓名24 / 组别·职务 / 地点·邮箱                                │
│  ───────────────────────  1px 实线分隔（c.border）  ───────────────────────  │
│  下带  .dp-floor-tags          padding: 14px 22px 18px                      │
│        「技能标签 · 共 N 个 · 按技能领域排序」一行 12px meta                    │
│        .dp-tag-floor  横排标签卡（flex-wrap，gap:10）                          │
│        合规脚注（12px text3，一行）                                            │
└─────────────────────────────────────────────────────────────────────────────┘
```

**关键：`.dp-tag-floor`、`.dp-person-head-main`、`.dp-floor-tags` 三个类名一律**不改名、不改内部**（它们各被 5+ 处测试引用）。TagMatrix 只去掉**外层 Panel 与 PanelHead**（否则会出现 Panel 套 Panel 的双边框），改由一行 12px meta 取代标题条。

### 1.2 具体数字

| 部位 | 现值（v0.4.3） | 新值（v0.5） | 依据 |
|------|---------------|-------------|------|
| Panel padding | `24px 28px`（hero）/ 外层 `marginTop:20` + TagMatrix 内 `padding:16` | **`0`**（两带各自管理） | 单 Panel 不再需要整体 padding |
| 上带 `.dp-person-head-main` padding | `0`（由 hero Panel 的 24/28 提供） | **`18px 22px`** | 糅合后楼层高度需压缩；18/22 与 v0.4.3 hero 的 24/28 成 0.75 比例 |
| 两带分隔 | —（原为两个 Panel + 20px 留白） | **`border-top: 1px solid c.border`** | **选「1px 实线」而非留白**：两带同属**一个楼层**，实线表达「同一张卡、两个分区」；纯留白会被读成「两张独立卡」，反而削弱糅合语义。 |
| 下带 `.dp-floor-tags` padding | 外层 `marginTop:20`；TagMatrix 内 `padding:16` | **`14px 22px 18px`** | 左右与上带对齐（22px），上下按 8pt 栅格收紧 |
| meta 行 | PanelHead 标题 16px + desc 12px | **单行 12px / c.text3 / lineHeight 1.6 / marginBottom 10** | 去掉 16px 标题（楼层内已有姓名作主标题，再给标签一个 16px 标题＝凭空造第二主标题） |
| 上带内 `gap`（头像↔文本） | `18` | **保持 18** | 身份块内部节奏不动 |
| 头像 | `size:64 fontSize:23` | **保持 64 / 23** | 身份不降权（候选 A 的核心收益） |
| 姓名字号 | `24 / 500 / lineHeight1.25 / ls-0.01em` | **保持** | 糅合后姓名仍是楼层主标题 |

**为什么这样屏效更好（一句话）**：把「身份」与「标签」压进同一张卡，**消掉了一次「Panel 边框 + 20px 楼层间隙 + PanelHead 标题条（约 32px）」的纯装饰开销（合计约 55px 垂直空间），标签流同时拿到通栏满宽（1440 下约 1250px，可容 8–9 卡/行）**——省的是「结构之间的空隙」，不是「信息」。

### 1.3 合规脚注样式（team-lead 点名要给）

| 位置 | 样式 |
|------|------|
| 糅合楼层脚注（技能标签来源） | `marginTop:10; fontSize:12; color:c.text3; lineHeight:1.7; padding:0 22px 0`（在下带 padding 内，故不再额外给左右） |

## 2. 轻量化标签卡（现值 vs 新值对照表）

### 2.1 对照表（逐项）

| 项 | 现值（v0.4.3，实读） | 新值（v0.5） | 省 |
|----|-------------------|-------------|----|
| 卡内边距 `padding` | `10px 12px` | **`8px 10px`** | 高 4px |
| 标签名字号 / 行高 | `13 / 1.4` | **`13 / 1.35`** | ≈0.7px |
| 点赞高度 `TagLike.height` | `22` | **`20`** | 2px（行高由它决定） |
| 点赞 `padding` | `0 7px` | **保持 `0 7px`** | 0（不动，避免影响点击热区） |
| 点赞图标 `size` | `14` | **保持 `14`** | 0 |
| 分组名行 + 档位行 | 两行：`2+16.5` + `4+6` = **28.5px** | **合并一行：`2 + max(16.5, 5)` = 18.5px** | **10px** |
| 档位条 `height` | `6` | **`5`** | 计入上行 |
| **档位条 `width`** | `64` | **保持 64（红线）** | — |
| **卡 `minWidth`** | `132` | **保持 132（红线）** | — |
| 卡外间距 `.dp-tag-floor gap` | `10` | **保持 `10`** | 0（不动，密度已由卡高提供） |
| 卡圆角 | `radiusCard = 8`（`.dp-card`） | **保持 8** | 0（不改形状签名） |
| 卡边框 | `1px solid c.border`（`.dp-card`） | **保持** | 0 |
| 标签名 `title` 兜底 | 有 | **保持**（截断补偿） | — |

### 2.2 单卡高度复核（我独立重算，非转述）

```
现状 = 10 + max(13×1.4=18.2, 点赞22) + (2 + 11×1.5=16.5) + (4 + 6) + 10
     = 10 + 22 + 18.5 + 10 + 10 = 70.5px
新值 = 8 + max(13×1.35=17.55, 点赞20) + (2 + max(11×1.5=16.5, 5)) + 8
     = 8 + 20 + 18.5 + 8 = 54.5px
降幅 = (70.5 − 54.5) / 70.5 = 22.7 %
```

**结论：许明需的 −22% 成立（实测 −22.7%），同意。** 且**零信息损失**（标签名/点赞数/档位条/分组名四项全在）。

### 2.3 ❗我的修正：合并两行**必须**让卡片「按内容自适应宽度」，否则分组名会被挤断

**上游漏洞**：许明需只算了「合并省 10px」，**没算合并后的宽度账**。我实算：

- 132px 卡、`padding:8px 10px` → 内容宽 = `132 − 20 = 112px`
- 档位条固定 `width:64`（红线不可改） + 间隙 6 = **70px**
- 留给分组名 = `112 − 70 = 42px`
- 11px 中文字 × 42px ≈ **3.8 个字** → 「业务与场景」（5 字 = 55px）会被截成「业务与…」

**但卡片是 `flex: 0 1 auto`（内容自适应）**，而 `.dp-tag-floor` 是 `flex-wrap`——**卡片会在换行前先按内容撑宽**，所以：

- 若分组名用 `flex: 0 0 auto`（不许收缩）→ 卡片**自然撑到** `10 + 64 + 6 + 55 + 10 = 145px`，**分组名不截断**。
- 5 字组名（工程与架构 / 数据与分析 / 产品与设计 / 平台与安全 / 协作与流程 / AI 与算法）→ 卡 ≈ **145px**；4 字组名（业务领域）→ 卡 = 132px（下限）。

**⇒ 我的规格（不可拆）**：
1. 合并行 = `display:flex; align-items:center; gap:6; marginTop:2`
2. **档位条在左**（`flex:0 0 auto`，64×5），**分组名在右**（`flex:0 0 auto`，11px/1.5/text3，`nowrap`）——**视觉上「先读档位、再读类目」，且组名不截断**。
3. 分组名**必须是 `<div>`**（不是 `<span>`）且 inline style 含 `font-size: 11px` ——**这是 `smoke.cjs:1786` 门⑤的硬要求**（它用 `card.querySelectorAll('div')` 找 11px 元素）。改 span → 门⑤ 直接红。
4. **不设 `maxWidth`**：卡片靠内容撑宽是本方案成立的前提。

**代价（诚实告知）**：合并后**有效最小卡宽由 132px 升到约 145px**（被 5 字组名拉动）→ 1440 下每行从约 9 张降到约 8 张。

**这是取舍不是 bug**：`minWidth:132` 的值**没改**（红线守住），卡片只是「内容驱动地变宽」；而**高度省 22.7% 的收益远大于每行少 1 张的成本**。若评审方认为屏效优先于分组名完整，**替代方案**：分组名允许 `ellipsis`（`flex:0 1 auto; minWidth:0`）→ 卡恒为 132px、每行 9 张，代价是 5 字组名显示为「业务与…」——**我推荐前者**（不丢信息），把后者列为备选。

### 2.4 关于「激进方案（删分组名，−48%）」

**我同意许明需：不推荐。** 补一条设计理由：分组名行是横排唯一的「类目上下文 + 排序可见性」来源（横排序仍按 `SKILL_GROUPS` 组序，删了小字用户看不懂「为何这几个相邻」）。**用户要的是「轻量化一些」（程度副词），不是「极简」。**

## 3. 8 周资源甘特

### 3.1 网格几何 + 三断点退化

**容器与网格（可直接落 `global.css`）**：

```css
/* 甘特滚动容器：横向滚动只发生在这里（绝不许 body 级溢出，否则击穿 shots「内容不超宽」门）*/
.dp-gantt-scroll {
  overflow-x: auto;
  min-width: 0;              /* 关键：防止撑破 grid 父级 */
}
.dp-gantt {
  display: grid;
  grid-template-columns: minmax(180px, 240px) repeat(8, minmax(44px, 1fr));
  column-gap: 0;             /* ★ 0：让跨周色带无缝相接 */
  row-gap: 4px;              /* ★ 4：让相邻任务行不粘连 */
  align-items: center;
  min-width: 512px;          /* 160 + 8×44 —— 低于此值即自动触发横向滚动 */
}
@media (max-width: 1200px) {
  .dp-gantt { grid-template-columns: minmax(160px, 180px) repeat(8, minmax(44px, 1fr)); }
}
@media (max-width: 900px) {
  .dp-gantt { grid-template-columns: minmax(160px, 160px) repeat(8, minmax(44px, 1fr)); }
}
```

| 符号 | 规格 |
|------|------|
| 任务名列（第 1 列） | `minmax(180px, 240px)`；≤1200 → `160–180`；≤900 → `160` |
| 8 周列 | `minmax(44px, 1fr)` 等分剩余（1440 下 ≈130px/列） |
| 格高 `.dp-gantt-cell` | **28px** |
| 行高（任务行，由行首 2 行决定） | **40px**（行首 = 标题行 18.2 + 间距 2 + 元信息行 17 ≈ 37，取 40） |
| 行间 `row-gap` | **4px** → 任务行垂直节奏 44px |
| 圆角 | 格 `4px`；**仅色带首/末格有圆角，中间格 0**（见 §3.4） |
| 表头行高 | **34px**（两行：`W1` / `09/14`） |
| 任务行首内容 | 行 1：`title` 13px/500/`c.ink`，单行 ellipsis + `title` 兜底；行 2：`WorkStatusPill`(22) + `key` 11px mono `c.text3` + `due` 11px mono `c.text3`（靠右）；`project` 降级入行首 `title` |
| 总占用行高 | **28px**（同格高） |

**行首两行 vs 一行（我的判断）**：上游 `WorkItem` 是「行 1 = 单号+状态+任务名；行 2 = 项目+日期」。甘特行首列仅 240px，**四个信息（单号/状态/任务名/日期）挤一行会把任务名压到 ~48px（约 3.6 字）**，不可读。故改为**两行**（任务名独占行 1；元信息行 2）。**代价**：行高由 28→40px。**收益**：任务名可读到约 17 字（「图标线性化收尾（面版图标下线）」= 16 字可全显）。

> 注：`smoke.cjs:1862` 门⑦断言「行含 `DS-3121` / `设计规范文档站改版` / `2026-10-09`」——CSS ellipsis **不改 DOM textContent**，故即便视觉截断，`textContent.includes` 仍成立。但**为可读性仍应按上面给足行 1 宽度**。

**三断点退化（修正上游：不手写「滚动 or 压缩」二选一，交给 `min-width` 自动）**：

| 视口 | 容器宽（1280 栅格 − 2×32） | 行首列 | 8 列宽 | 行为 |
|------|--------------------------|--------|--------|------|
| **1440** | ≈1280 | 240 | ≈130 | 无滚动；表头 `W1` + `09/14` 完整 |
| **900–1200** | 836–1136 | 180 | ≈82–120 | 无滚动 |
| **769–900** | 705–836 | 160 | ≈68–84 | 无滚动 |
| **≤576（含 375）** | <512 | 160 | **44（下限）** | **自动横向滚动**（容器 < min-width 512）；行首列 `position:sticky; left:0` |

**为什么改成「自动」**：手写断点（如 `@media(max-width:900px){overflow-x:auto}`）只能按**视口**判断，而我只需要按**容器实际宽度**判断；`min-width:512px` + `overflow-x:auto` 让浏览器在「容器真的装不下」时才出滚动条——**768 下不会误出滚动条**（容器 705 > 512），**375 下必出**。更稳、更少 CSS。

**行首列 sticky 规则**：
```css
.dp-gantt-rowhead { position: sticky; left: 0; z-index: 1; background: #ffffff; }
```
（`background` 必须给，否则滚动时后面的格会从任务名下透出。`z-index:1` 高于格的默认层。）

**红线**：横向滚动**只允许发生在 `.dp-gantt-scroll` 内**，`body`/`.dp-shell` **不得**出现横向滚动（`shots.cjs` 有「内容不超宽」门 + 顶栏高度门）。

### 3.2 三档占用色 + 对比度实算（真算，非估）

**配色（全部复用现有 token，0 新色值）**：

| 档位 | 语义 | 色值 | 现有令牌名 |
|------|------|------|-----------|
| 空 | 该周 0 项 | `#F5F4F5` | `c.page` |
| 轻 | 该周 1 项 | `#DCE0F4` | `c.brandStep1` |
| 中 | 该周 2 项 | `#A9B2E6` | `c.brandStep2` |
| 高 | 该周 ≥3 项 | `#6B78D4` | `c.brandStep3` |
| 任务条（占用格） | 该任务本周在办 | `#3643BA` | `c.brand` |

> **为什么任务条用 `c.brand`（最深）而不用某一档**：任务条与「总占用档位」是**两个不同量**（条 = 一件事在办；档 = 一周几件事），若共用同一深浅会产生「1 条 = 3 项」的误读。用最深色 → **任务条是画面最重的元素（它就是主角），总占用行是它的浅色汇总**。且 `c.brand` 作数据填充有先例：`SystemTier` 最高档（authoritative）即用 `c.brand`（`ui.jsx:371`）。

**WCAG 相对亮度与对比度实算**（node 实算，公式与原始输出见 `outputs/_v05_contrast.txt`）：

```

      L = 0.2126·R_lin + 0.7152·G_lin + 0.0722·B_lin
      Contrast = (L_hi + 0.05) / (L_lo + 0.05)

实算相对亮度 L：
  #F5F4F5 L=0.9071   #DCE0F4 L=0.7506   #A9B2E6 L=0.4599
  #6B78D4 L=0.2131   #3643BA L=0.0834   #000F17 L=0.0040
```

| 高 `#6B78D4` | **3.99 : 1** ✅（非文本 ≥3:1） | 3.64 : 1 ✅ |

**③ 格内计数数字（正文 AA 需 ≥4.5:1）—— 全部达标 ✅**

| 数字色 / 底 | 对比度 |
|------------|--------|
| `c.ink #000F17` on 轻 `#DCE0F4` | **14.82 : 1** ✅ |
| `c.ink #000F17` on 中 `#A9B2E6` | **9.44 : 1** ✅ |
| `c.ink #000F17` on 高 `#6B78D4` | **4.87 : 1** ✅ |
| `c.ink #000F17` on 空槽 `#F5F4F5` | 17.71 : 1 ✅ |

**④ 任务条 vs 空槽**

| 对 | 对比度 |
|----|--------|
| `c.brand #3643BA` vs 空槽 `#F5F4F5` | **7.17 : 1** ✅ |
| `c.brand` vs 白底 | 7.87 : 1 ✅ |

#### ❗最重要的判断：浅端不可辨 → **计数数字是三档唯一的可靠通道**

实算证明：**档1 对白底只有 1.31:1、档1 vs 空槽仅 1.20:1、轻 vs 中仅 1.57:1**。这不是配色失误，而是**「品牌蓝同色系 + 必须够浅」的数学必然**——单色阶的浅端天然低对比。

**因此本方案的可访问性成立，完全依赖那条硬要求「格内计数数字」**：

- **数字是主通道**（全部 ≥4.87:1，达正文 AA）；**深浅是辅助通道**（快速扫读）。
- **色盲/灰度用户**：靠「有无数字 + 数字值」读出档位；深浅只是加成。
- **绝不允许**做成「只有底色、没有数字」的色块热力图 —— 那会让 1.20:1 的档1 对色盲用户**完全不可读**，直接违反 team-lead 铁律第 4 条。
- **补充结构通道（推荐）**：总占用行的格加 `1px solid c.border` 边框 —— 让每格边界**不依赖填充**也能看出。这样「轻 vs 空」即便填充近似，也有边框 + 数字双重区分。

**数字规格**：`fontSize:12; fontWeight:500; className="dp-num"`（等宽，列间对齐）；色 = `c.ink`（各档均 ≥4.87:1）；**空槽不显示数字**（无占用＝空态，显示「0」会让 8 格满屏零）；水平垂直居中。

**若评审方要求「三档本身 ≥3:1」**（更严）：唯一可行解是把档1 提到 `#A9B2E6`（2.06:1，仍不足 3）、或引入一个更深的浅档（**新色值**）——但会破坏「轻」的语感（浅档变深，三档挤在一起）。**我的裁定**：**不引入新色值**，改用「数字主通道 + 边框结构通道」满足可访问性；把「三档 fill 均 ≥3:1」标为**已知不达标项**并书面说明理由（这是本文 §6 自检里必须勾的一条）。

### 3.3 跨周色带的画法

**规则（gap:0 前提下）**：

1. **色带 = 该任务行内、被 `weekIndexesOf(issue)` 命中的连续格**，填充 `c.brand`。
2. **圆角只在色带两端**：首格 `border-top-left-radius:4px; border-bottom-left-radius:4px`；末格对称；**中间格 `border-radius:0`**。若带只有 1 格 → 四角全圆（4px）。
3. **实现**：施工方按 `weeks` 数组给格打 class —— `.is-on`（占用）、`.is-band-start`（首格）、`.is-band-end`（末格）。单周任务同时带 start+end。
4. **色带高度与格的垂直居中**：格高 28px、行高 40px、`align-items:center` → 色带在行内垂直居中，上下各留 6px——**「条」感，不是「块」感**（这是甘特图的标准读法）。
5. **跨行不连**：`row-gap:4px` 保证上一行色带与下一行色带**不断开成一条竖带**（否则整列会被误读为一条大色带）。

**色带 vs 空槽格线的冲突解法（我补的细节）**：
- 若给**每格**加竖分隔线，色带中间会被切碎（违背 §3.2 决策 2）。
- **解法**：**只有空槽格带左竖线，占用格不带**。即 `.dp-gantt-cell { box-shadow: inset 1px 0 0 <c.border> }`，`.dp-gantt-cell.is-on { box-shadow: none }`。
  - 连续空槽格：每格左竖线 → **网格可见** ✅
  - 连续占用格：无色带内竖线 → **色带连续** ✅
  - 空槽→占用 / 占用→空槽 的边界：由**颜色突变**自然标出（空槽格保留左竖线）✅
- 表头行与总占用行是**独立格**（不成带），照常每格带左竖线。

### 3.5 总占用行（计数 + 阈值）

- **行首格**：文本 `总占用`（11px / `c.text2`）。

- **阈值与理由（我确认许明需的 0/1/2/≥3）**：

| 计数 | 档 | 填充 | 理由 |
|------|----|------|------|
| 0 | 空 | `c.page`，无数字 | 「无占用」是空态 |

## 4. 最小新增令牌清单

### 4.1 结论：**0 个新色值**；新增 = 6 个「别名型 CSS 变量」+ 若干「结构性 class」

**为什么不用新色值**：三档占用色 = `brandStep1/2/3`（已存在，`theme.js:72-74`）；任务条 = `c.brand`；空槽 = `c.page`；格线 = `c.border`；数字 = `c.ink`。**现有令牌已完全覆盖，无需任何新色。**

**为什么仍要新增 CSS 变量**（team-lead 点名要「可直接落 global.css 的变量」）：甘特有 **8×N ≈ 60+ 个格**，若每格走 inline `style={{background:c.brandStep2}}` 则 JSX 臃肿、且「档位→颜色」的映射会散落在渲染逻辑里；改为 **class 修饰 + CSS 变量**后，档位映射收口在 CSS，格只需打 class。**这些变量是现有令牌的别名（alias），不是新色值** —— 这既满足「CSS 侧可取用」，又守住「零新视觉语言」。

**注意**：`global.css` 现有约定是「结构性样式用字面量、主题可变样式走 `useT()`」，全文件仅 `--dp-font-mono` 一个变量。**本轮新增 6 个变量是一次有意的、最小的例外**（理由：静态甘特格数量大，需要 CSS 侧引用同一套色）。若施工方更倾向不动全局约定，**替代实现**：不用变量，直接在 `.dp-gantt-*` 类里写**字面量**（与 `.dp-chip` / `.dp-card` 同样的写法）——两种都合规，**我推荐变量版**（可读性与「令牌即事实来源」更好）。
