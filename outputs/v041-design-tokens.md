## 0. 用户指令与本期设计主张

**用户原文（v0.4 迭代直接指令）**：

1. 员工标签体系不用横纵两个轴，太复杂了，就建立统一的技能标签树以及成熟度就好，可以覆盖兼顾产品经理、研发工程师、QA 工程师等各类 digital 岗位，即**标签树不区分适配岗位**。
2. 个人主页：基础信息板块，**员工技能标签以及成熟度呈现为主，近期知识贡献为辅**，不用其他内容了。
3. 页面布局更有个人主页的特征。

**本期核心设计主张（一句话）**：

> **把「两条轴」降级为「一棵树的一级分组」——不是删功能，是删掉「轴」这个需要用户做二次心智建模的概念**。所有标签进入单一 `skill tree`，树的一级节点就是分组（组名保证岗位中立），`axis` 字段从**语义轴**降级为**遗留兼容字段**，UI 层不再暴露。

**我要明确顶住的一件事**：用户说「就建立统一的技能标签树**就好**」，语气是「简化」。但**成熟度双证据模型（自评 + 实证）不能顺手砍掉**——它是 v0.4 最有价值的诚实机制（吹牛态、收敛态都是它的产物），且用户第 2 条明确要求「技能标签**以及成熟度**呈现为主」，说明成熟度是要保留且要突出的。**本期只砍「轴」，不砍「成熟度模型」**。

## 1. 统一技能标签树：信息架构规范

### 1.1 分组方案（岗位中立，7 个一级分组）

**结论前置**：把现有 9 个组（领域 5 + 能力 4）**重组为 7 个一级分组**，分组维度统一为**「技能主题域」（skill theme domain）**——即「这项技能是做什么的、作用在哪类问题上」，而不是「哪类岗位需要它」。

| 序 | 分组名 | 语义定义 | 覆盖的岗位举例（**仅用于论证覆盖度，不进 UI**） | 标签数 |
|----|--------|---------|--------------------------------|--------|
| 1 | **AI 与算法** | 让机器具备智能能力的技术主题：模型、检索、智能体、评测、算法建模 | 研发、算法、产品（AI 方向）、QA（模型评测） | 7 |
| 2 | **工程与架构** | 让系统能跑起来、跑得稳、跑得快的建造类主题 | 研发、QA（测试工程）、运维、安全 | 15 |
| 3 | **数据与分析** | 让决策有依据的主题：采集、建模、指标、实验、看板 | 数据分析、研发、产品、QA（数据质量） | 17 |
| 4 | **产品与设计** | 定义「做什么、给谁用、怎么用」的主题 | 产品经理、设计师、内容、用户研究 | 8 |
| 5 | **业务领域** | 组织所服务的具体业务对象（门店、会员、订单、供应链……） | 产品、研发、运营、业务方 | 16 |
| 6 | **平台与安全** | 支撑性的公共基础设施与合规主题 | 研发、运维、安全、SRE | 6 |
| 7 | **协作与流程** | 让一群人高效一起干活的主题 | **全部岗位**（这是唯一的「全员组」） | 12 |

> **标签数合计 = 7+15+17+8+16+6+12 = 81**，含每组的历史标签。下面 §1.3 给出 active 的精确分布（72 条）。

**为什么是「主题域」而不是「岗位」**：用户明确要求「标签树不区分适配岗位」。若按岗位分组（PM 组 / 研发组 / QA 组），则跨岗位共用的标签（如「需求管理」「跨部门协同」）无处安放，且会被读成「这是 PM 的标签，不是我的」——正好违背用户意图。**主题域天然是共用的**：QA 工程师可以对自己挂「AI 与算法 / 模型评测」，产品经理可以对自己挂「工程与架构 / 系统架构」，互不排斥。

### 1.2 组间关系与排序规则

**排序 = 由「专精」到「通用」的认知漏斗**（这也是排序的唯一依据，不按字母、不按标签数）：

```
AI 与算法  →  工程与架构  →  数据与分析  →  产品与设计
                                              ↓
            平台与安全  ←  业务领域  ←  （并列层）
                                              ↓
                          协作与流程（压底，全员组）
```

**设计理由**：
- **1–4 组（AI / 工程 / 数据 / 产品）是「专精技能层」**：一个人通常只强在其中 1–2 个，是区分度的来源，所以排在上面（用户第一眼看到自己的「硬本事」）。
- **5–6 组（业务领域 / 平台与安全）是「场景技能层」**：依附于具体业务或基础设施，横向铺开。
- **7 组（协作与流程）压底**：这是**全员共性组**，人人都有、区分度最低，排在最后符合「漏斗收敛」的阅读直觉——把通用的东西放在最后，不占据宝贵的首屏注意力。
- **组内排序**：按「具体 → 抽象」，即子技术排在母技术之后（如 `AI 与算法` 内：AI 与智能 → RAG → Agent → 向量检索 → 提示词工程 → 模型评测）。

## 2. 单轴之后的视觉规范（**明确取舍**）

### 2.1 字形：保留 `◈`，反对「彻底去掉字形」

**我的专业结论：保留 `◈` 作为唯一统一字形，但重新定义其语义为「主标签标记」；`◇` 彻底废弃。**

**理由（三条，非选项罗列）**：

1. **删除字形是「减法做过头」**。原双轴字形的存在意义是「色盲冗余」——用户提到「太复杂」，矛头指向的是**两条轴的心智负担**，不是这个 2px 的符号。符号本身零认知成本，删掉它反而丢失了一个「免颜色可辨识」的通道（`◈` 与 `◇` 在灰度下形状不同，是 v0.4 无障碍设计的实际资产）。
2. **但 `◇` 必须死**。单树之后若两个字形都留，用户会问「为什么有的标签带实心有的带空心」——**这正是双轴制的幽灵**，必须彻底清除。
3. **`◈` 的语义重定向到「主标签」是正确落点**。原 primary 分支已经用 `◆`/`◈` 表示主标签（`ui.jsx:757`），`selected` 分支也复用（`:787`）。也就是说，**代码里已经存在「用字形标记主标签」的先例**——把它从「轴字形」升格为「主标签专属字形」，是**顺着既有代码演进**，不是发明新约定。

**具体规则**：

| 场景 | v0.4（双轴） | v0.4.1（单树） |
|------|-------------|---------------|
| active 默认态 | `{◈ 或 ◇} 标签名` | **`标签名`（无前缀）** |
| primary 主标签 | `{◆ 或 ◈} 标签名 主` | **`◈ 标签名 主`（统一 ◈）** |
| selected 已选 | `{◆ 或 ◈} 标签名 ×` | **`◈ 标签名 ×`** |
| deprecated 已停用 | 无前缀 + 左 3px 轴色条 | 无前缀 + 左 3px **中性条** |
| disabled | `{◈ 或 ◇} 标签名` | **`标签名`（无前缀）** |
| merged | 内层 chip + 「原『旧名』」 | 内层 chip + 「原『旧名』」 |

> **关键决策：active 默认态去掉字形前缀**。原 `active` 分支渲染 `{glyph} {label}`，双轴下这是「宣布自己是哪个轴」的必要信息。单树下它变成纯噪音——每个标签都带同一个符号，等于没有符号。**默认态回归纯文字，字形只在 primary / selected 出现，用来强调「这是我主动标记的主标签」**。这恰好让 `◈` 从「到处都是」变成「稀有标记」，语义重量反而上升。

### 2.2 配色：取消轴色差，改用「单一中性底 + 状态驱动的重音」

**结论：取消 `brandSubtle/brand`（领域）vs `page/text2`（能力）的轴色差，Tags 的默认态统一为中性；品牌蓝从「领域专属色」提级为「交互与强调色」——只在 hover / selected / primary 时出现。**

**理由**：原设计的轴色差（领域=品牌蓝系、能力=中性灰系）隐含一个价值判断——**「领域比能力重要」**（蓝是主色、灰是退后一档）。在双轴框架下这是有意的（领域是检索主轴）。但单树之后，**7 个分组没有高下之分**（AI 与「协作与流程」是平等的技能主题）。若保留「领域蓝 / 能力灰」，用户会继续追问「哪些算领域哪些算能力」——**轴色差就是轴的最后一个视觉抓手，必须一并拆除**。

**新的层级表达（取代轴色差）**：用**「状态」而非「类别」**承载差异：

| 状态 | 底色 | 边框 | 文字色 | 字重 |
|------|------|------|--------|------|

## 3. 「统一技能标签树 + 成熟度」的呈现规范

### 3.1 TagMatrix 新结构：从「两区」到「按分组的多段树」

**结论：`TagMatrix` 的两区拆分（领域轴区 / 能力类型轴区）改为「按 7 个一级分组的多段树」，每段一个 `groupBar`，段内三列标签卡。**

**结构规范**：

```
┌─ Panel ─────────────────────────────────────────────┐
│ PanelHead: 技能标签        desc: 7 组 · 24 个标签     │
│                            extra: 近 12 月实证 4 条   │
├─────────────────────────────────────────────────────┤
│  ▸ AI 与算法                              3          │  ← groupBar（32px）
│  ┌────────┐ ┌────────┐ ┌────────┐                   │
│  │ 模型评测◈│ │ RAG    │ │ Agent  │                   │  ← 标签卡（3 列栅格）
│  │ ●●●○ 在项目中用过                 │                   │
│  │ ▬▬▬▭ 有初步产出                   │                   │
│  └────────┘ └────────┘ └────────┘                   │
│                                                      │
│  ▸ 工程与架构                            5          │  ← 下一个 groupBar
│  ┌────────┐ ┌────────┐ ┌────────┐                   │
│  │ ...    │ │ ...    │ │ ...    │                   │
│                                                     │
│  ▸ 协作与流程                            2          │
│  ...                                                 │
└─────────────────────────────────────────────────────┘
```

**关键规则**：

1. **只渲染「该人有标签的分组」**——不渲染空分组。`PersonProfile` 是新场景（展示一个人的能力画像），空分组会制造大量噪音（一个人不可能 7 组都有标签）。**这与 v0.4 的「某轴无标签时分区不消失」规则相反，是本期明确的规则变更**——理由：v0.4 的两区是「固定两区」，藏着会显得信息缺失；v0.4.1 是「7 组动态树」，空组藏着才符合「个人画像」的叙事。
2. **组间排序**严格按 §1.2 的漏斗顺序（AI → 工程 → 数据 → 产品 → 业务 → 平台 → 协作）。
3. **组内排序**按该人对自己该组标签的 `evidenceTier` 降序（`authoritative` 在前），同档按 `selfRating` 降序——**这是唯一允许的排序依据，且只作用于「同一个人内部」**，绝不造出跨人比较（`TagBrowse` 的铁律不变）。
4. **`PanelHead` 的 `desc`**：从「领域标签 N · 能力标签 M」改为 **「N 组 · 共 M 个标签」**（M = 该人该页标签总数）。
5. **`groupBar` 函数保持原样**（`ui.jsx:850-872`，32px / `cardHeadBg` / 6px 圆角 / 13px 500 `text2`），**零改动复用**——它是中性的，没有轴色。

### 3.2 标签卡新规范（`tagCard`）

**卡内四要素，垂直排列**：

| 行 | 内容 | 规范 |
|----|------|------|
| L1 | 标签名 | 13px / 500 / `c.ink`，单行裁剪；**若为主标签，名前加 `◈`** |
| L2 | 分组名（**新增**） | 11px / `c.text3`，**替代原「领域 / 能力」角标**——「领域」「能力」两个词是轴制的遗物，必须换成所属分组名（如「AI 与算法」），它携带更多信息 |
| L3–L4 | `MaturityAxis` compact | **零改动复用**（含吹牛态、收敛态） |

**L1 右侧角标改动**（原 `ui.jsx:923-925`）：
```
{t.tag.axis === 'domain' ? '领域' : '能力'}   →   {分组名，如「工程与架构」}
```
> 若原型构建师发现卡内 L1 行右侧放不下分组名（如「协作与流程」5 字），**降级方案**：分组名移到 L1 行下方（新 L2 行），L1 行只保留标签名。**但绝不允许回退到「领域 / 能力」**——那是双轴词汇，出现在单树 UI 里会让整个改造功亏一篑。

## 4. 个人主页布局规范（对应指令 2、3）

### 4.1 版式结论：**新建专用 class，不复用 `.dp-g-article`**

**明确回答**：**新建 `.dp-g-profile`，不复用 `.dp-g-article`。**

**理由（三条）**：
1. **语义不同**。`.dp-g-article` 是「正文 + 目录侧栏」（主列宽绰、侧栏 232px 固定）；Profile 页是「能力画像 hero + 佐证列表」。套用同一个 class 会让两者在未来的响应式微调中互相绑架。
2. **硬约束**。`.dp-g-article` 被 `ArticleDetail.jsx:90` 共用，**改它会波及文章详情页**——这是主理人明确的既有约束。
3. **本期 Profile 页的栅格是非对称的**（主列要比 1fr 更宽），与 `1fr + 232px` 不同。

> **实施方式**：在 `global.css` 新增 `.dp-g-profile`，**不改 `.dp-g-article` 一个字**。两者在 `@media (max-width: 900px)` 块里各自塌缩为单列。

### 4.2 视觉层次（信息密度分配）

**核心主张：把 v0.4 的「四个等权区块」重构为「一个 hero + 一个主栏 + 一个辅栏」的三层结构，呼应指令 2「技能标签为主、贡献为辅」。**

| 层级 | 区块 | 视觉权重 | 面积占比 | 对应指令 |
|------|------|---------|---------|---------|
| **L0 hero** | 基础信息条（头像 + 姓名 + 部门/角色 + 联系） | **最高**（页头通栏） | 100% × 高度 ~96px | 指令 2「基础信息板块」 |
| **L1 主** | 技能标签树 + 成熟度（`TagMatrix`） | **高**（主栏，宽 2/3） | ~64% | 指令 2「技能标签以及成熟度**为主**」 |
| **L2 辅** | 近期知识贡献 | **低**（辅栏，窄 1/3） | ~36% | 指令 2「近期知识贡献**为辅**」 |

**用户说「不用其他内容了」——须删除的区块**：
- ❌ **能力分布概览**（`PersonProfile.jsx:218-251`，那行「领域 N 个 · 能力 M 个 · Sparkline」）——**删除**。它是双轴统计（「领域 / 能力」），且 Sparkline 是「第 4 个信息源」，与「简化」意图冲突。
- ❌ **协作触点**（`PersonProfile.jsx:289-328`，「负责的工具」）——**删除**。它与「标签 + 成熟度」主题无关，是 v0.4 的 P2 附属品。
- ❌ **底部注释**（`:332-334`）——**可以保留但降级**：合并进 `TagMatrix` 的 PanelHead 下方作为一行 12px `text3` 脚注（因为它承载「实证度不作为绩效评价」的合规声明，**建议保留**，但不再是独立区块）。
- ✅ **页头主标签卡**（`:176-215`，主标签的 expanded 成熟度卡）——**保留并升级为 hero 的一部分**。它正是「技能标签 + 成熟度为主」的集中体现。

### 4.3 栅格方案与版式

**Hero 区（通栏）**：
```
┌─────────────────────────────────────────────────────────┐
│  ┌────┐   张三                                    [主标签]│
│  │ 张 │   技术产品部 · 高级产品经理                ┌──────┐│
│  └────┘   上海 · zhang.san@decathlon.com          │模型评测◈││
│                                                   │●●●● 主动投入│
│                                                   │▬▬▬▬ 有沉淀与影响力│
```

- 左侧：`InitialAvatar(56)` + 姓名（22px/500）+ 部门·角色（14px/`text2`）+ 地点·邮箱（13px/`text3`）
- 右侧：主标签卡（≤2 个，`expanded` 成熟度；从 v0.4 的 ≤3 降为 **≤2**，因为宽度增加后 3 个会挤）

**主体区（两栏非对称）**：
```

```
- 左栏（宽）：`TagMatrix`（技能标签树）
- 右栏（窄）：`近期知识贡献` Panel

**区块垂直顺序（自上而下）**：

3. 两栏主体（左：技能标签树｜右：近期知识贡献）
4. （无独立底注，脚注并入标签树面板）

### 4.4 响应式断点行为

**沿用现有 `@media (max-width: 900px)`**（`global.css:458-483`），新增以下规则：

```css
    grid-template-columns: minmax(0, 1fr);   /* 两栏塌缩单列 */

  .dp-profile-hero {

  }
  .dp-profile-hero-tags {
```

**断点行为小结**：

| 宽度 | Hero | 主体 |
|------|------|------|

> **复用考量**：现有 `.dp-person-head` 系列 class 的三条 900px 规则**与新布局兼容**（都是 flex-wrap + column 塌缩），建议**保留并复用 `dp-person-head` 命名**（改名会增加原型构建师改动面）。若新 hero 结构与 `dp-person-head` 的 DOM 差异过大，则新命名 `dp-profile-hero`，二者择一，**不要两套并存**。
