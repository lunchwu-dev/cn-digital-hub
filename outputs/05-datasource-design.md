## 一、结论前置

先回答你问的那句「哪些人工、哪些半人工、哪些自动」——**一页表说清**：

| 运营模式 | 域 | 判断依据（一句话） |
|---|---|---|
| **全自动**（系统直连，人工零介入） | 监控三域（KPI/图表/稳定性）、工具运行状态链、关键联系人（若企微有 API） | 纯数值/状态，**怕的是延迟不是写错** → 唯一正解是直连 |
| **半自动 · 填链接自动抓取** | 设计资产聚合入口（Figma/组件库/图标） | 内容已在外部站点，门户只填链接；**但需登录的源站抓不到，前提待验证** |
| **半自动 · 人工写正文 + 系统补字段** | 项目动态、里程碑、Release 兜底、需求提交（MVP） | **门户是第一撰写地**（源系统没有这段文字）→ 人写，系统补 Owner/日期/分类 |
| **全人工** | 公告与决议、最佳实践、设计规范、FAQ 正文、工具目录字段、引导与页脚文案 | 是"人的判断与承诺"，无结构化源可依 |
| **派生 / 聚合** | 待补知识队列、需求记录（二期）、Agent 回复（二期）、通知列表 | 不生产内容，由其他域或外部系统累积得出 |

**三条最要紧的判断：**

1. **最大的成本变量不是「有没有 API」，而是「权威源是否唯一」。**
   所有集成风险本质是同一件事：门户显示"已发布"、源系统里还是"灰度中"，用户发现两边不一致后，就再也不信门户了。所以第一条裁定原则是——**凡是已有权威源的，门户一律不生产内容，只做投影（projection），不做状态机。**

2. **「出错代价高」要拆成「怕延迟」还是「怕写错」。**
   这是本次最容易搞反的地方。监控数值错 = **怕延迟**（晚一秒就是错的），必须高频自动、人工复核反而加重延迟；公告文字错 = **怕写错**（写错即成害），必须人工、宁慢勿错。**同为"高代价"，结论完全相反。**

3. **"到达高频"不等于"人工不可持续"——要看触发方式。**
   公告到达频率是日级，但它是**事件驱动**（有事才发），不是"每天必须发 N 条"，所以全人工跑得动。监控是**节律驱动**（每 15 秒产一条），人工绝无可能跟上。**频率决定自动化的下限，触发方式决定人工的上限。**

## 三、运营模式判定框架（可复用方法论）

### 3.1 模式谱系（5 类 + 1 复合）

| 代号 | 模式 | 定义 | 人工介入点 |
|---|---|---|---|
| **M1** | 全自动 | 定时/实时从权威源拉取，人工零介入（除阈值配置） | 无 |
| **M2** | 半自动 · 链接抓取 | 人工只填**来源链接/ID**，系统定时抓取解析 | 填一次链接 |
| **M3** | 半自动 · 人工录入 + 系统补字段 | 人工写正文，系统补 Owner/日期/分类/状态 | 写正文 |
| **M4** | 全人工 | 必须人工撰写维护，无结构化源可依 | 全流程 |
| **M5** | 派生 / 聚合 | 不直接生产，由其他域计算得出 | 无 |
| **M-combo** | 复合（目录 + 状态分链） | 同模块内目录走 M3/M4、状态走 M1 | 分链路裁定 |

### 3.2 准入决策树

按顺序问，第一个为「是」的分支即结论：

```
Q1 该数据是否已有权威源系统？
   ├─ 有 → Q2
   └─ 无 → Q4

Q2 权威源是否提供稳定 API？
   ├─ 有 API → Q3
   └─ 无 API，仅有可访问网页 → M2（链接抓取）
                              └─ 连网页都无可解析结构 → M3

Q3 该数据是否需要人的判断、语气、业务解读？
   ├─ 不需要（纯数值/状态/版本号）→ M1（全自动）
   └─ 需要 → Q3b

Q3b 判断所需的「正文」是否已在某个系统里写好了？
   ├─ 是（源系统已有这段文字，只是搬过来）→ M2（抓链接/ID）
   └─ 否（门户是第一撰写地）→ M3（人写正文，系统补字段）

Q4 该数据是否是"门户独有、无外部源"的叙述型内容？
   ├─ 是 → 需要人写？
   │        ├─ 是 → M4（全人工）
   │        └─ 否，可由其他域推导 → M5（派生）
   └─ 否（其实是配置/枚举）→ 静态配置
```

**Q3b 是关键补充。** 没有它，决策树在最常见的边界案例上会给出"M2 **或** M3"——而"或"不是结论：M2（填链接抓取）与 M3（人写正文）的实现路径、工作量、Owner 责任完全不同。

> **实测**：`projectUpdates` 走 Q1（有 Jira/Meego）→ Q2（有 API）→ Q3（需要判断）→ **Q3b：进展正文通常首先写在门户/手工表，Jira 里只有状态字段 → "否" → M3**。唯一解、可推导。

### 3.3 两个必备前提（此前被高估）

**① M2 只适用于「匿名可访问」的源页面。**
Figma、语雀、Confluence、Jira 几乎全部需要登录鉴权，**无登录的门户抓不到**。对需登录的源只有两条出路：(a) 服务端持凭据代抓；(b) 降级为纯跳转外链。

**② 所有 M1 探活类必须带 `unknown` 态。**
状态枚举必须是 `success / warning / error / unknown(探活失联)`。理由是"**探活失败 ≠ 服务挂了**"——探活脚本自己挂掉时，若没有 `unknown` 档，门户会显示**上一个已知状态**，等于对用户说谎。
**当前 `stabilityItems.status`（mock.js:452-457）只有三档、缺 `unknown`，落地必须扩展。**

### 3.4 六维判定表（边界仲裁用）

| 维度 | 倾向自动 | 倾向人工 |
|---|---|---|
| 结构化程度 | 天然字段化 | 自由文本、需版本化管理 |
| 是否有稳定 API | 有、有 SLA | 无 API 或不稳定 |
| 权威源是否唯一 | 唯一（单点真相） | 多源、需人工裁定口径 |
| 是否需人的判断/语气 | 不需要（事实即结论） | 需要解读、定调、担责 |
| 出错代价 | 极高（怕延迟）→ 必须自动保新鲜度 | 高（怕写错）→ 必须人工复核 |
| 触发方式 | 节律驱动 → 人工不可持续 | 事件驱动 → 人工可承受 |

## 五、关键实现契约（给接手的工程师）

### 5.1 三个复合域必须拆链（最易做一半的地方）

| 域 | 链路 A（人工） | 链路 B（自动） | 只做 A 的后果 |
|---|---|---|---|
| **D12 工具目录** | 用途 / Owner / 权限（月级人工） | `status` 运行状态（探活） | 状态永远是手填的"假绿"，探活挂掉还显示正常 |
| **D11 FAQ** | 答案正文（人工） | `helpful/notHelpful` 计数（事件采集） | 反馈闭环失效，待补队列只进不出 |
| **D02 Release** | 小系统兜底手填 | 主路径系统直连 | 无系统的小系统版本号永远缺 |

### 5.2 P01 反馈采集契约（当前实现根本不存在）

代码实证（`portal/src/pages/Knowledge.jsx:196-211`）：`markHelpful` 只写组件内 `useState` + 弹 toast；`faqs.helpful/notHelpful`（如 mock.js:600 `helpful:46`）是**静态值、点多少次都不变**；无落库、无 localStorage、**刷新即失**。也就是说 P01 的"负反馈事件"在当前原型里是**纯 UI 幻觉**。

落地必须新建采集链路：

| 项 | 约定 |
|---|---|
| 事件名 | `faq_feedback` |
| 字段 | `faqId`(string) / `helpful`(bool) / `ts`(ISO8601) / `dept`(可选，来自表单、不作身份追踪) |
| 存储 | `feedback_events` 表（或复用埋点平台） |
| 保留期 | ≥ 12 个月 |
| 写回 | `faqs.helpful/notHelpful` **由事件聚合回写，不得人工维护** |

**闭环五步各自要有 Owner**：反馈写入 → 计数聚合 → 待补队列 → Owner 认领 → 关闭。缺任何一步就是"只进不出"。

### 5.3 监控只拉"聚合序列"，不是"单标量"

产品方案已定"只做 L1 + 下钻"。精确边界是：**只拉按天/小时粒度的聚合序列，不拉秒级/请求级原始点位**。

注意 `opsCharts.series`（三条 7 点序列）与 `opsKpis.spark`（7 日序列）**本身就是序列数据**——若按"读 1 个标量接口"估算工作量，实现时会翻倍。

### 5.4 无登录架构的两条合规红线

- 所有身份类数据源（企微消息、HR 员工主体）**只能用于展示，不能用于追踪个人行为**。
- **`orgPeople.email` 仅用于展示与复制，禁止用于埋点关联。**

## 六、工作量与集成预算

**粗估口径**：S ≤3 人天 ｜ M 1–2 周 ｜ L 3–5 周 ｜ XL >5 周。估的是**从"确认有 API"到"门户稳定展示"**的集成量（含联调、权限、指标口径对齐、异常兜底）。

| 集成项 | 覆盖域 | 最乐观 | 最悲观 | 判定依据 |
|---|---|---|---|---|
| 监控数据接入 | D05/D06/D07 | 3 周 | 8 周 | 乐观=Grafana 只读 API 现成；悲观=需自建聚合层 + 口径逐项对齐 |
| Release / 发布系统 | D02 | 1.5 周 | 6 周 | 乐观=有按系统聚合 API；悲观=多系统各自为政，需人工兜底 |
| 项目进度接入 | D03/D04 | 2 周 | 8 周 | 乐观=单源单 API；悲观=Jira+Meego 双源 + 里程碑独立源 |
| 人员 / 通讯录 | D13 | 1 周 | 0.5 周 | 乐观=企微 API 直连；悲观=无 API 仅手工维护（**活反而更少**） |
| 反馈事件链路 | P01/D11 | 1.5 周 | 3 周 | 需新建 `feedback_events` + 聚合回写 + 待补队列打通 |
| M2 抓取链路 | D10b | 1 周 | 0.3 周 | 乐观=可服务端代抓；悲观=撞登录墙降级纯跳转（**活反而更少**） |
| **合计（硬集成）** | — | **约 6–8 周** | **约 12–18 周** | — |

> **列义说明**：「最悲观」指**收益最差时的方案形态**，不一定工作量最大。有两行"悲观值反而更小"，因为抓不到内容时方案降级为纯跳转/纯手工，**要做的活反而更少**——代价是门户价值下降，不是工期变长。

**一期 MVP 集成预算上限建议：≤ 8 周（1 名后端工程师全职）。** 超出时按此顺序砍域（先砍对"有效性验证"影响最小的）：

1. **先砍 D03/D04 项目进度接入** → 退化为纯人工列表（产品方案本就定 MVP 只做动态列表）
2. **再砍 D10b 的 M2 聚合** → 退化为纯外链跳转
3. **再砍 D13 人员自动化** → 退回手工维护 10 人关键名单
4. **最后才砍 D02/D05–D07** → 这两组是"门户不为空"的地基，砍了门户就没有存在理由

> **不砍项**：P01 反馈链路（1.5–3 周）**不可砍**。成本不高，但它是产品方案定的**首要运营指标**来源，也是二期 Agent 的活水；砍掉它等于砍掉门户的"生命体征传感器"。

## 七、风险与边界

### 7.1 最容易被低估的三项成本

1. **"权威源不唯一"导致的双写灾难（最高风险）**。门户若自行产生或缓存数据，就会与源系统漂移。用户第一次发现两边不一致，门户信誉就永久受损。**对策：对已有权威源的域只做投影，不做状态机。**
2. **工具状态的全自动探活**。11 个工具逐一探活，还要区分"服务挂了"还是"探活脚本挂了"。**对策：一期先做半自动（Owner 每月确认）；探活放二期。**
3. **知识域的人工成本是持续性的**。10–15 篇最佳实践、30 条 FAQ 只是"种子内容"，真正贵的是 90 天复核 + 待补队列清空这两条**永续运营**。**对策：用"待补队列清空天数 < 7 天"这个指标驱动，而非靠自觉。**

### 7.2 最容易失败的四个环节

| 环节 | 失败形态 | 根因 |
|---|---|---|
| **集成先行、治理缺位** | 花 6 周接通监控 API，但没人维护公告和 FAQ，门户上线即空 | 技术工作可见、治理工作不可见，团队天然偏向集成 |
| **半人工的"链接腐烂"** | M2 跑三个月后源站改版，抓取全断且无人知晓 | 抓取失败没告警；**必须给每条 M2 链路加"连续 N 次失败即告警 Owner"** |
| **M2 抓取撞登录墙** | 需登录的源永远返回登录页，解析出空内容 | 把 M2 前提想当然了（见 §3.3①） |
| **复合域只做了一半** | 工具目录做好了，状态还是手填的假绿 | 把 D12 当单一域处理，漏掉状态链路 |

### 7.3 明确的能力边界

- **无登录鉴权** → 已读/订阅/关注、个性化、"公告触达率"全部不可做。因此 D01 **不能**依赖"阅读追踪"证明价值，D11 **不能**做个性化推荐。
- **监控只做 L1 + 下钻** → 只拉聚合序列，明细一律跳转。这显著降低了集成工作量（只读聚合接口 vs 全量时序）。

**第 1 轮审查抓到的三个真问题**（值得记下来，因为它们是"看起来完整"的方案的典型漏洞）：

1. **盘点自称"没有遗漏"，但门户有 3 处内容域根本不来自被盘点的来源**。方案按 `mock.js` 清点，而通知/引导/页脚文案硬编码在组件里——**"我们盘点了全部"这句话在验证之前不成立**。
2. **实体数是 35 不是 34，且"28 + 6"两个数都对不上**。清点靠印象而非机械方法（grep），遗漏几乎是必然的。
3. **一个被标为"确定"的派生域，其依赖的源头在代码里根本不存在**。P01 反馈队列被设计得很好，但反馈本身只存在内存里、刷新即失——**设计的完整性掩盖了实现的空壳**。

> 这三条与 `04-delivery-notes.md` 第六节那条教训同源：**没人认领的格子一定是空的**。本文因此把"非 mock 内容域"单列成节、把 35 行对照表做成可机械复核、把 P01 的采集契约写成字段级约定——都是为了不让下一个格子在二期变空。
