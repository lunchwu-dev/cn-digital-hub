## 1.【核心判断】Jira 状态可视化：语义复用 vs 新建色组

### 1.1 先问对的问题：`status` 到底属于哪个语义域？

项目现有两套语义系统，**必须先分清楚，否则一定串味**：

| 语义系统 | 载体 | 语义域 | 现有实例 |
|---------|------|--------|---------|
| **A. 「运行/合规状态」语义** | `Pill` + `SEMANTIC`（success/warning/error/info/neutral） | 这东西**健康吗、合规吗、能不能用** | `StatusDot`（服务在线/降级）、需求提交的「说不清」提示、TagBrowse 的「已停用」 |
| **B. 「能力档位」语义** | `SystemTier` + `brandStep1-3`+`brand` 单色阶 | 这个人**在这个标签上有多少系统记录** | 技能标签卡的 4 段胶囊条 |

**关键判断**：Jira 的 `status`（待办/进行中/待评审）表达的是**「一件工作的流程阶段」**——
它既不是「这东西健康吗」（不是 A），也不是「这人多强」（不是 B）。

**但它和 A 同构**：都是「一类枚举状态 → 需要一个可扫读的标记」。区别只在**配色语汇**。

### 1.2 【取舍一】状态术语砍到 3 态，`blocked` 不上主视觉

**上游的 4 态我不同意全部等价上屏。** 我的裁定：

| 数据层 status | 上屏中文 | 视觉（Pill semantic） | 我的理由 |
|--------------|---------|---------------------|---------|
| `todo` | 待办 | `neutral`（page 底 / border 边 / text2 字） | 中性、最多数、不喧哗 |
| `inprogress` | 进行中 | `info`（infoBg / infoBorder / infoText） | 唯一「活着」的态，给唯一的蓝 |
| `review` | 待评审 | `warning`（warningBg / warningBorder / warningText） | 「等你评审」= 有行动请求 → 弱警示合理 |
| `blocked` | **（不上屏）** | **不渲染状态 Pill** | **见下方论证** |

**为什么 `blocked` 不该上主视觉——这是我本次最强的取舍：**

1. **它是唯一的「负面」态，会被读成人格判断。** 「阻塞」这个词，在**个人主页**这个语境（一个具体的人的名字正上方）出现时，读屏者会把「这个任务阻塞」滑向「这个人卡住了/这个人有问题」。全站铁律是**「不作为绩效评价」「不造跨人横向比较」**——个人主页上出现一个专门标红的负面徽章，是铁律的软越界。
2. **它违反「同事视角」的真实需求。** 同事看「近期工作内容」要回答两个问题：**「他在做什么」「什么时候好」**。`blocked` 对这两个问题零贡献，只贡献了「这个人不顺」。**信息价值低，而误伤风险高。**
3. **它与其他 3 态不是同一个「轴」。** `todo/inprogress/review` 是**流程进度**（一条时间轴上的位置），`blocked` 是**异常中断**（轴的断裂）。把 4 个不等距、不同质的态塞进同一排等宽 Pill，本身就是视觉谎言。

**那 `blocked` 要不要落地数据层？——要，但降级为「非视觉事实」：**

- 数据层**保留** `status:'blocked'`（上游 §2.2 枚举不改，保持 Jira 真实性）。
- 渲染层：`blocked` **不渲染状态 Pill**（状态位留空，用 `—` 或直接空），**不加红、不加任何图标**。
- **可选的最弱处理**（我建议施工方**本期不做**，留 v0.4.4）：若担心「状态位空白显得像 bug」，可给 `blocked` 渲染一个**与 `todo` 完全相同的中性 Pill**，文案仍显示「待办」？——**不行，那是文案撒谎**。所以正解就是**留空**。留空 = 「这个任务的状态不适合在这个语境展示」，是诚实且无伤害的。

> **给评审方的一句话**：如果你认为「blocked 不留红会丢失重要信息」——请回答：**这条信息对「同事找谁协作」有什么可用性？** 答不出，就不该上屏。

### 1.3 颜色纪律：**不新建语义色组，也不复用「档位」色阶**

- **不用 `SystemTier` 的 `brandStep1-3` 单色阶**：那套色阶被 v0.4.2 明确定义为**「能力实证档位」专用**。把工作状态也涂成同一族蓝，会让「这个人记录多」和「这个任务在评审」**共用同一个视觉通道**——同事会误读「蓝色深 = 这人厉害」在任务卡上也成立。**语义串味，禁止。**
- **复用 `SEMANTIC`（A 套）**：`Pill` 已经完整实现了 `neutral/info/warning` 三分支，**零新令牌**。这是「语义复用」的正确姿势——同构语义（枚举状态 → 徽标）复用同一套色，异质语义（档位 vs 状态）严格隔离。

### 1.4 增量令牌清单（§1 小结）

**新增令牌：0 个。** 全部复用：
- `SEMANTIC.neutral / info / warning`（`theme.js:98-103`）
- `Pill`（`ui.jsx:13`）
- 逾期日期色：`c.warning`（已有，`#E8890C`，**仅用于数字着色**，见 §2.5）

**新增组件：1 个** —— `WorkStatusPill`（薄封装，见 §2.3），**不新开色，只是把「status 枚举 → Pill semantic + 中文」的映射收口到一个地方**，避免施工方在卡片里散写三元表达式。

## 2.「近期工作内容」卡片视觉规范

### 2.1 容器与头部

复用 `Panel` + `PanelHead`，与右栏「近期知识贡献」**严格同构**（同 padding、同标题字号、同 extra 位置）：

| 部位 | 规格 | token |
|------|------|-------|
| 外框 | 1px 实线 | `c.border` |
| 头部 | `PanelHead` 默认 padding `14px 16px`，底边框 1px | `c.border` |
| 标题 | 「近期工作内容」16px / 500 | `c.ink` |
| 副标题 desc | 「来自 Jira 的负责人字段 · 当前至未来 1 个月」12px | `c.text3` |
| extra（右侧） | 总数或「N 条 · 显示近 5」，等宽数字 | `c.text3` |

**desc 文案（定稿，逐字）**：`来自 Jira 的负责人字段 · 当前至未来 1 个月`
—— 与右栏「每条都标注它喂养了哪个标签」形成对称的两条数据来源说明。

**extra 文案**：
- ≤5 条：`{n} 条`
- \>5 条：`{total} 条 · 显示近 5`（`total` 是真实总数，不是 5；`total` 与 `5` 均用 `.dp-num`）

### 2.2 单条任务行（inline 布局，逐行给 px）

每条任务渲染为一个 `div`，**上下列、左右两栏内联**：

```
┌────────────────────────────────────────────────────────┐
│ MEM-2184  [待评审]       会员积分规则迁移到自然年         │  ← 行 1
│ 会员中心 · Q4 迭代 3                     2026-10-08      │  ← 行 2
└────────────────────────────────────────────────────────┘
```

**逐行规格（不写死高度，用 padding 撑开）：**

| 元素 | 规格 |
|------|------|
| 行容器 padding | `10px 12px`（与右栏 `ContributionItem` 的 `10px 12px` **完全一致**，两栏行高对齐） |
| 行分隔线 | 第 N 条→N+1 条：`borderBottom: 1px solid c.border`；最后一条 `none`（同 `ContributionItem`） |
| 行 1 布局 | `display:flex; align-items:center; gap:8px; marginBottom:4px`，`minWidth:0` |
| Jira 单号 | `.dp-num` 12px `c.text3`，`flex:0 0 auto`，`letterSpacing:0`（等宽数字天然对齐） |
| 状态 Pill | `WorkStatusPill`，高度 22px（同 `Pill`/`dp-chip`），`flex:0 0 auto` |
| 任务名 | 13px / 500 `c.ink`，`lineHeight:1.5`，`flex:1 1 auto`，`minWidth:0`，**单行裁剪**（`whiteSpace:nowrap; overflow:hidden; textOverflow:ellipsis`） |
| 行 2 布局 | `display:flex; align-items:baseline; justifyContent:space-between; gap:12px` |
| 项目/迭代（左） | 12px `c.text3`，`flex:1 1 auto`，`minWidth:0`，单行裁剪 |
| 预期交付（右） | `.dp-num` 12px `c.text3`（**逾期时改 `c.warning`**，见 §2.5），`flex:0 0 auto`，`whiteSpace:nowrap` |

**行 1 的行高账**（供施工方核验，勿写死 height）：`max(22px Pill, 13×1.5=19.5px 任务名)` = 22px。
**行 2 行高**：`12×1.4 ≈ 17px`。**单条总高** = `10 + 22 + 4 + 17 + 10 = 63px`。**5 条 ≈ 315px**（不含 PanelHead），与右栏贡献列表量级相当——**这就是我坚持 `1fr/1fr` 的实测依据**（若用 1.85fr/1fr，工作栏被强制撑宽，行会变空，反而不平衡）。

### 2.3 `WorkStatusPill` 组件规范

```jsx
// 收口「status 枚举 → 上屏中文 + Pill semantic」，禁止在卡片里散写三元。
// 4 态 → 3 态视觉（blocked 不上屏，返回 null）
const WORK_STATUS = {
  todo:       { copy: '待办',   semantic: 'neutral' },
  inprogress: { copy: '进行中', semantic: 'info' },
  review:     { copy: '待评审', semantic: 'warning' },
  blocked:    null, // ★ 不上屏（见 §1.2）——负面色不作人格暗示
};
```

- 渲染：`const m = WORK_STATUS[status]; if (!m) return null; return <Pill semantic={m.semantic}>{m.copy}</Pill>;`
- **未知 status 兜底**：`return null`（不猜、不显红）。数据层若出现枚举外的值，宁可不显示也不误标。
- **图标纪律**：状态**一律不加图标**。Pill 的 `dot` 参数也**不传**（点阵在 A 套里已被用于 `StatusDot` 服务状态，任务状态再上点阵会与「服务在线」视觉撞车）。**纯文字 Pill**，与站内其他枚举徽标一致。

### 2.4 空态（逐字定稿）

**必须区分两种「空」，不要混用：**

| 情形 | 文案 |
|------|------|
| 该人有标签、但这 1 个月**无在办任务** | 「暂无在办任务。任务数据来自 Jira 的负责人字段，仅展示当前至未来 1 个月的排期。」 |
| 整个 Jira 表为空/未接入（防御性） | 同上（**不新增第二套文案**——本项目零后端，第 2 种情形不会真实发生，留多套文案是伪需求） |

**空态容器**：`padding:'20px 16px'; fontSize:13; color:c.text3; lineHeight:1.7`（**逐字复用**右栏贡献空态的容器样式 `PersonProfile.jsx:183`，保证两栏空态视觉一致）。

**绝对禁止的措辞**（评审核对项）：
- ❌「该成员没有工作」 ❌「暂无产出」 ❌「工作量为空」 ❌「无任务安排」
- 空态只陈述「暂无排期数据」这一**事实**，**不评价人**（铁律：不作为绩效评价）。

### 2.5 逾期提示：**用时间说话，不用「逾期」二字**（我对上游的加严）

上游 §2.4 建议「加一个极弱的『已逾期』提示」。**我不同意加这两个字。** 我的替代方案：

- **视觉手段**：`due < WORK_WINDOW_AS_OF`（即 `due < '2026-09-17'`）且 status 未完结时，**仅把行 2 右端的日期数字染成 `c.warning`**（`#E8890C`，已有令牌）。**不新增文案、不新增图标、不加 Pill、不加「逾期」字样。**
- **理由**：
  1. 「已逾期」是**评判词**；一个橙色日期是**事实**。橙色日期读作「注意这个日子」，「已逾期」读作「这人没按时交」。**个人主页是只读第三人称视图，评审判定应留给读的人，不该由页面代劳。**
  2. 一个日期色就能让逾期日期在扫读时**自然跳出来**，信息传递效率不比加个徽章低，但伤害小得多。
  3. 与 §1.2 的 `blocked` 处理**同一条原则**：**负面事实可以用「中性但突出」的方式呈现，绝不用「加判词」的方式呈现。**
- **排序不变**：逾期任务**仍排在窗口内任务之后**（上游 §2.4 排序规则保留），不因染色而浮顶——否则逾期任务天天霸占第一行，反而变成另一种「示众」。
- **边界**：`c.warning` 的对比度——`#E8890C` 对白底对比度约 3.1:1，**不满足正文 AA（4.5:1）**。故**这是「辅助数字着色」而非正文**：日期同时以**位置（行 2 右端）**和**等宽体**双重编码，颜色只是第三重强化。**不依赖颜色单独传达信息**（不影响无障碍：不认色的人仍能从日期本身与排序读出）。**若评审方坚持要 AA，则降级为 `c.warningText`（`#8A5200`，约 6.3:1）**——我给两个选项，让施工方按评审结论二选一。

## 3. 楼层 2「横向标签楼层」视觉规范

### 3.1 布局参数（确认并修订上游 §3.2）

| 参数 | 上游建议 | 我的裁定 | 说明 |
|------|---------|---------|------|
| 布局方式 | `flex-wrap` 流式 | ✅ **同意** | 短标签不被 grid 拉宽，是「提高屏效」的正解 |
| 卡片宽度 | `auto` + `min-width:132px` | ⚠️ **改为 `min-width:128px`** | 见 §3.2 宽度账——132px 在「标签名 + 点赞」同行时会挤掉点赞 |
| 卡片高度 | 不写死 | ✅ **同意** | 写死会在中文换行时截断 |
| 卡片间距 | `gap:10px` | ✅ **同意** | |
| 每行卡数 | 6–8 张 | ✅ **同意**（128px 下实际 7–9 张，更优） | |
| 内 padding | `10px 12px` | ✅ **同意** | |

### 3.2 窄卡（128px）内部布局——**必须逐行算账**

上游只给了「标签名 13px 一行 + 分组名 11px 一行 + 档位条 ≈8px + padding」。**但 v0.4.2 的卡是「标签名 + 点赞同行」，132px 装不下**，必须精确校验：

**卡内宽度账**：`128px - 12px(左 padding) - 12px(右 padding) = 104px` 内容宽。

| 行 | 内容 | 宽度需求 | 是否会溢出 |
|----|------|---------|-----------|
| 行 1 | 标签名（13px，flex:1，可 ellipsis）+ `TagLike` | `TagLike` ≈ 22px 高、宽 `7+14(图标)+4+数字+7` ≈ **36–44px**；剩余给标签名 `104-44 = 60px` | ⚠️ 60px 仅容 **约 4 个中文字**（13px×4=52px）。**「需求拆解与排期」（7 字）会被截成「需求拆解…」** |
| 行 2 | 分组名 11px，`nowrap+ellipsis` | 「业务与场景」（5 字×11=55px）< 104px ✅ | 不溢出，但长组名「协作与流程」（5 字）恰好 55px，**安全** |
| 行 3 | `SystemTier` 档位条 `width:64` + 文案（12px） | 档位条固定 **64px**，文案「暂无系统记录」（6 字×12=72px）> 104px | ⚠️ **文案在 128px 卡内会 ellipsis 成「暂无系统…」** |

**我的结论（3 条修订）：**

1. **宽度改为 `min-width:128px`，但真正的解法是让「标签名」和「点赞」允许换行**——不，换行会破坏「同高」韵律。**正解：把 `SystemTier` 的 `showCopy` 在横排卡里设为 `false`**（只留 4 段档位条 64px，不显示「暂无系统记录」文案）。
   - **为什么**：横排卡的核心信息是「**标签名 + 档位条**」；档位条已经用 4 段填充**结构性地**表达了档位，「暂无系统记录」这段文字在窄卡里既挤又重复（83.5% 实例都是 none 档，满屏「暂无系统记录」是纯噪音）。
   - **代价可接受**：档位文案的完整语义仍在**标签反查页**（`TagBrowse`）保留（那里卡宽充足）。个人主页横排是**速览态**，速览态减文字是正当的。
   - `SystemTier` **组件本身不改**，只在 TagMatrix 调用处传 `showCopy={false}`。
2. **标签名允许 2 行**（`whiteSpace:normal` + `WebkitLineClamp:2`）——但**这会破坏卡高一致性**。**我选择不允许多行**：保持 `nowrap+ellipsis` 单行，**把 `min-width` 提到 `140px` 换取 4→5 字的容度**？——**不。** 我最终定：**`min-width:132px`（采纳上游原值） + `showCopy=false`**。因为砍掉档位文案后，行 1 的 104→112px 内容宽里，`TagLike` 占 44px、标签名仍有 `68px ≈ 5 字`，7 字标签仍会截断——**但截断是 `ellipsis` 可控的，且 `title` 属性兜底全文**（见第 3 条）。
