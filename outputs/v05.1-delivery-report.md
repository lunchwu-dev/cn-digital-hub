## 1. 诉求 → 实现

### ① 技能标签与个人信息糅合成一个楼层，卡片轻量化

单张 `Panel` 承担两个「带」，中间用 1px 实线分隔（`.dp-person-head.dp-floor-merged`）：

- 上带 = 头像 + 姓名/部门/职务/工位/邮箱，`padding` 由 24/28 收到 **18/22**；
- 1px `borderTop` 分隔（`:root` 现有 `--dp-border`，**零新色值**）；
- 下带 = 技能标签 + 合规脚注，`padding 14/22/18`。

`padding: 0` 由 `.dp-floor-merged` 管，两带各自给内边距，避免双重内边距。

轻量化落在 `.dp-card`（标签卡）与本楼层结构上，**实测卡高 70.5px → 54.5px（−22.7%）**：

| 项 | 改前 | 改后 |
|---|---|---|
| `TagLike` 高度 | 22px | **20px** |
| `SystemTier` 档位条高 | 6px | **5px**（宽度 64px 红线未动） |
| 卡片 padding | 10/12 | **8/10** |
| 分组名 + 档位行 | 两行 | **合并为一行**（`flex` + `flex:0 0 auto`，不做 `maxWidth`） |
| 外层 `Panel` / `PanelHead` | 有 | **移除**（约 55px 纯结构开销消失，标签流拿到通栏满宽） |

楼层顺序（`tests/smoke.cjs` 实测 DOM）：糅合层@1 → 工作@2 → 贡献@3；模块级 `.dp-card` **= 3**；`.dp-g-duo` / `.dp-g-profile` **0 命中**。

### ② 近期工作内容独占楼层：未来 8 周资源占用甘特

- 独占通栏 `Panel.dp-floor-work`，标题「近期工作内容」，说明「来自 Jira 的负责人字段 · 未来 8 周资源占用」。
- 栅格：`grid-template-columns: minmax(180px,240px) repeat(8, minmax(44px,1fr))`，`column-gap: 0`，`min-width: 512px`，容器 `.dp-gantt-scroll{overflow-x:auto}`。

## 2. 三条已确认设计决策的落法

| 决策 | 实现 | 关键约束 |
|---|---|---|
| 三档强度 + 深浅色 | `low/mid/high` → `.t-low/.t-mid/.t-high` → `--dp-gantt-l1/l2/l3` | 图例文案由 `OCCUPANCY_TIER_THRESHOLDS` **拼出**，不手写字面量（防「改了阈值图例继续撒谎」） |

### ★ 颜色不是唯一信息通道

三档品牌蓝的浅端对白底对比度**实测复算**（按 `global.css` 实际值）：

| 变量 | 色值 | 对白底对比度 |
|---|---|---|
| `--dp-gantt-slot`（空槽） | `#f5f4f5` | 1.097:1 |
| `--dp-gantt-l1`（轻，1 项） | `#dce0f4` | **1.312:1** |
| `--dp-gantt-l2`（中，2 项） | `#a9b2e6` | **2.059:1** |
| `--dp-gantt-l3`（高，≥3 项） | `#6b78d4` | **3.991:1** |
| `--dp-gantt-bar`（任务条） | `#3643ba` | 7.869:1 |

l1 仅 1.31:1 —— **单靠颜色根本分不出三档**（尤其色盲用户）。故「总占用行每格必须有计数数字」是硬要求，并在门⑪里两侧都锁死：**有占用的格必须有数字、无占用的格必须没有数字**。

## 3. 本轮修掉的真缺陷

### 3.1 【P0，我自己引入】几何门恒假 → 4 条变异空转

`.dp-gantt-cell` 基底写了 `border-radius: 4px`，而探针期望**中间格左上圆角 0px**；CSS 里没有任何把中间格圆角置 0 的规则。

- 位置注释明写「中间格必须 0（否则一条带会被切成若干『药丸』）」，且 `.dp-gantt-cell.is-on.is-band-start.is-band-end{border-radius:4px}`（单周格四角全圆）只有**在基底为 0 时才不冗余** —— 两处都反证基底写错了。
- **后果一（对用户可见）**：一条 4 周的色带被渲成 4 个首尾相接的「药丸」（每个接头上下各凹 4px），用户选定的「连续色带跨越」被无声破坏；此外 inset 左竖线沿圆角内收，空槽 28px 分隔线两端出现缺口。
- **后果二（对测试致命）**：`bandRadiusOk` 在基线上**恒假** → 几何门 `ok` 恒为 `false` → 4 条走 `geom-gantt` 的变异**全都「变红」，且红与注入的变异无关**。这正是「空转断言」，也是本项目反复栽的那类。
- **为什么长期没暴露**：本机 `node` 进程内 `spawn` 子进程返回 `EBUSY`，node 编排器与自起 Chrome 的探针**从未真正跑起来过**，这扇门一次都没被评估过。
- **修复**：基底 `border-radius: 0`，圆角交回 `is-band-start` / `is-band-end`。探针由 `ok=false` 转为 **`ok=true`**，实测 `bandStartR=4px / bandEndLeftR=0px`。
- **防复发**：新增 M19（把基底圆角改回 4px）—— 证明 `bandRadiusOk` 是**活门**，而不是从「恒假装饰」翻转成「恒真装饰」。

### 3.2 【P1】图例没有解释任务条主色

图例只列了 l1/l2/l3，漏掉 `--dp-gantt-bar`（`#3643ba`，**7.87:1**）。它是整屏**面积最大、颜色最深**的一块，且比最高档 l3（3.99:1）**深一倍** —— 读者极易把「任务在办」读成「占用 = 高」。

修复：图例分两组（**任务行** / **总占用行**），补第 4 个色块。同时改正一处**说谎的文案**：原「格内数字为该周在办任务数」把数字说成在任务行里，实际只有总占用行有数字。

### 3.3 【P1】零交出行被渲成空行，且计数虚高

实测全量在办任务里恰有 **2 条**整段落在窗口开始日（2026-09-14）之前：

- `siyuan.chen` 的 `MEM-2160`（2026-09-05 ~ 09-10，in progress）
- `jia.he` 的 `SRE-860`（2026-09-03 ~ 09-08，in progress）

它们的 `weekIdx = []`，在甘特里渲成「**有任务名、8 格全空**」的一行 —— 看起来像渲染 bug；同时让楼层头显示「9 项在办」而表里只有 8 行有占用。

修复口径（三选一里最保守的那个）：

- `rows` 保持**全量**（`totals` 的唯一来源 → 口径不变、可审计，也保住「不截断」纪律）；
- 新增 `inWindow`（真正与这 8 周有交集的行，供甘特渲染）+ `outside`（被排除的条数）；
- UI 只渲 `inWindow`，并由 `OutsideNote` **明示**「另有 N 项在办任务的区间结束于窗口开始日（2026-09-14）之前，未占用这 8 周中的任何一周，故未列入上表」——**不静默丢弃**；
- **不把 `due` 硬拉进窗口**：`start`/`due` 是 Jira 事实，虚构占用比漏显更糟；
- extra 文案由「N 项在办」改「**N 项占用**」（陈思远全量在办 9 条，但只有 8 条占用窗口，沿用旧文案会与表内行数自相矛盾）。

与文件头「逾期照常进甘特」的裁定**不冲突**：那条管的是**区间与窗口有交集**的逾期任务（如 `DS-3080`，due 09-15 落在 W1 内，照常占格）；此处排除的是**不占用任何一周**的任务，藏掉它不会让任何一周的占用被低估。

### 3.4 【P1，测试层】M7 是空转变异

`M7` 变异 `getPersonWork` 的过滤条件，期望打红「blocked 整行仍渲染」。但 v0.5 换甘特后，`getPersonWork` 只剩「被 `getPersonProfile` 返回给 `profile.work`」一个出口 —— **页面不再渲染它，`tests/smoke.cjs` 里对它的引用数为 0**。于是这条变异改的是没人观察的代码，**永远不可能变红**。

根因是我此前「把 `getPersonWork` 当备份口径保留」的决定造成的假象：它让测试套看起来覆盖了这条规则，实际没有。而真正喂甘特的是 `getPersonOccupancy`。

修复（两头都补，不留假象）：

- **补数据层门**：`getPersonWork` 在其**一个月窗口**（`due ∈ [AS_OF, WINDOW_END]` ∪ 逾期）内一条未完结任务都不许丢，并含 blocked 样本。用 `total` 而非 `items` 比较 —— `items` 被 `slice(0,5)` 截断，用它会放过「第 6 条被丢」。
  - 这条门第一次跑起来就**抓住了我自己的错误假设**（我写的期望是「未完结条数」，实测 `rawOpen=7` vs `total=5`）：v0.5 为甘特 W6–W8 新增的样本 `due ≥ 2026-10-19` 本就在窗口之外，被正确排除。期望值改为按同一口径从原始数据推出后转绿。
- **新增 M24**：把 `getPersonOccupancy` 的未完结过滤再加 `&& status !== 'blocked'` → 唯一 blocked 样本 `DS-3121` 从甘特消失 → 门⑦变红。这条规则现在真正有了守门人。

### 3.5 【构建层】safe-delete 限流让「构建」看起来像被变异改坏

变异首轮跑出极具误导性的现象：M1–M3 正常变红，**M4 起连续报「变异后构建失败」**（跨不同文件），收尾构建也失败。看起来像变异把代码改坏了。

真实原因（原先被吞掉的堆栈）：

```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":53,"threshold":50,"scope":"turn"}
   at checkBulkDeleteGuard (node-safe-delete-shim.cjs)
   at emptyDir → at prepareOutDir → at build
```

本机沙箱的 safe-delete shim **按「turn」累计删除条目数**，超过 50 即拒绝。而 `vite build` 默认 `emptyOutDir=true`，每次构建都删 `dist/assets` 下的产物；23 条变异累计删除量必然越线，之后**每条构建都被拒**。

修复：`tests/mutation.sh` 三处构建统一加 `--emptyOutDir=false`（本项目产物全是**固定文件名**、无内容 hash，不会残留陈旧文件），并把「构建失败」时的构建输出**打印出来**（原先把输出写进临时目录、退出时删掉，日志里只剩一句「构建失败」，等于把根因丢掉）。已清理 20 个失败构建泄漏的 `vite.config.js.timestamp-*.mjs`。
