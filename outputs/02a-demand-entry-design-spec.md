## 0. 令牌校对结论（先确认事实，再谈新增）

已核对 `theme.js`，主理人给的令牌摘要**全部准确**，补两条对本次新增有直接影响的细节：

| 项 | 事实（来自 theme.js） | 对新增面的影响 |
|---|---|---|
| `space` 是**数字**不是字符串 | `space: { xs:4, sm:8, md:12, base:16, lg:24, xl:32, xxl:48, huge:64 }` | 组件里必须写 `c.space.base` 或字面量 `16`；`gap: c.space.base + 'px'` 这种拼字符串的写法会产生 `16px` 之外的脏值，禁止 |
| `textDisabled #B3B7B9` | 站内**全站只出现在禁用态与装饰位** | 大卡**不得**用它做任何说明文字（2.04:1，AA 不达标）。占位符/说明文字一律 `text3 #667085` |
| `SEMANTIC` 只有 5 键 | `success/warning/error/info/neutral` | 评分面板的「命中/未命中」**全部走 `neutral`**，不新增语义键，不改 theme.js |
| `radiusOverlay: 12` | 浮层 12px，`Modal` 已映射 | 评分面板展开区若做浮层，用 12；做成内联区则用 `radiusCard 8`、`radiusControl 6` |
| 已存在 `.dp-g-spec` | `1.5fr : 1fr`，且 900px 以下**自动塌成单列** | 需求提交页「左表单右引导」**不需要新定义栅格类**，直接用 `.dp-g-spec` |
| 已存在 `.dp-form` 规则 | 表单内输入框强制 `border-radius: 6px`，覆盖全局胶囊 | 提交页表单**必须**挂 `className="dp-form"`，否则输入框会变胶囊，与控件圆角档混用 |

**唯一需要新增的 CSS 类，我裁定为 0 个。** 所有新增形态都可由既有类 + 内联令牌样式表达（详见第 2、3 节）。构建师不要新建 `.dp-*` 类。

## 1. 裁决：首页「需求提交」入口区块的视觉方案

### 1.1 位置裁决 —— 放在第 4 节「快捷入口」**之前**，作为新的第 4 节，快捷入口顺延为第 5 节

理由（信息层级的判断依据，不是手感）：

1. **入口区块承载的是「动作」，快捷入口承载的是「检索」**。用户在首页的动作意图优先级是：先知道「今天有什么必须周知的事」（置顶决议）→ 看「系统是否正常」（健康度）→ 看「我正在等什么」（Release/里程碑）→ 然后才是「我要办一件事」（提交需求）→ 最后是「我要找某个系统」（快捷入口）。
2. **快捷入口是 4×2 的链接墙**，把入口大卡插进它中间会切断「工具磁贴」的连续扫描节奏；插在它之前，则形成「动作卡 → 工具墙」的自然递进（办不了的事 → 去工具里办）。
3. **长度控制**：入口区块是 1 行高的大卡（约 168px），快捷入口是 2 行网格（约 176px）。若把入口放在快捷入口之后，它会被推到 Agent 引导条上方，视线落点在整页最底部，与「入口」的语义相反。
4. **与第 5 节 Agent 引导条的关系**：Agent 引导条是横向条状、灰底，入口大卡是白底带强调条的大卡，两者相邻但形态差异足够（见 1.3 节），不会连成一块。

**最终页序**：① 置顶决议 → ② 健康度快照 → ③ 双栏（Release / 里程碑）→ **④ 需求提交入口** → ⑤ 快捷入口 → ⑥ Agent 引导条。

### 1.2 形态裁决 —— 采纳需求分析师的建议，但**加强一档**：白底 + 品牌蓝 3px 左边框 + 品牌蓝实心主按钮，**否决整块品牌蓝实底**

裁决：**白底（surface）+ 3px 品牌蓝左边框强调条**（复用 `PinnedCard` 的手法），**不做整块品牌蓝实底**。

理由，三条，按重要性排序：

1. **实底会破坏「置顶决议是首页心脏」的信息契约。** 首页现在只有一个 `#3643BA` 实底元素——顶栏的 active 导航项。置顶决议靠**黄色小面积标记 + 3px 品牌蓝强调条**取得第一优先级。若入口大卡铺满 `#3643BA`，它会是全页**面积最大、饱和度最高**的色块，在 0.3 秒的首次扫视里直接夺走置顶决议的位置。首页第一功能是「周知」，不是「提交」。
2. **实底大卡会把品牌蓝从「强调色」贬值成「面积色」。** 本系统实测结论写得很清楚：`#000F17` 是面积色（顶栏），`#3643BA` 是强调色（CTA / 强调块，生产站点出现 36 次但均为小面积）；`#FFCD4E` 是小面积标记。整块品牌蓝底会让「品牌蓝 = 最强调」这条规则失效，之后**再没有任何东西能比它更强调**，置顶决议、健康度异常都失去表达手段。
3. **白底 + 强调条是既有的、已被验收过的「重点卡」语汇。** `PinnedCard` 已经用「白底 + 3px 品牌蓝左边框 + 轻微内边距」建立了「这是重点但可读」的语汇。入口大卡复用同一手法，读起来是「同一个系统里的另一张重点卡」，而不是「另一个系统的广告位」。**这正是不做纵向视觉分裂的关键。**

**但要加强一档**（这是我对分析师方案的增量修改，理由是不加强就压不住快捷入口）：

- 强调条从 3px 提到 **4px**。为什么可以提到 4px 而不算破规矩？置顶决议是**「多张同款卡」**，强调条必须克制；入口大卡是**全页唯一的单张卡**，4px 既是「唯一性」的视觉声明，也不至于变成色块。**同一页只允许一个大卡使用 4px，其余一律 3px。**
- 大卡内主按钮**必须**用 `type="primary"` 实心品牌蓝（这是页面上最饱和的一小块），hover 走 `brandHover`。**强调条给「区块」，实心按钮给「唯一的行动」**——把饱和度集中在一个 34px 高的胶囊里，而不是铺满 300×168px 的面积。

### 1.3 它凭什么比快捷入口更显眼，又不抢置顶决议的位

这是两个方向相反的诉求，靠**三个正交维度**同时满足，不靠「谁颜色更亮」：

| 维度 | 入口大卡 vs 快捷入口 | 入口大卡 vs 置顶决议 |
|---|---|---|
| **面积 / 形态** | 大卡是 1 张跨 2 格、约 168px 高的横向卡；快捷入口是 8 张 16px 内边距的等大小磁贴。**大 → 小**，大卡胜 | 置顶决议是纵向堆叠的多张卡，视觉重量由「张数 + 黄色标记」累积；大卡单张、无黄色标记。**标记 → 无标记**，置顶胜 |
| **饱和度** | 大卡有一枚实心品牌蓝按钮（约 110×34px 的饱和区）+ 4px 强调条；快捷入口全是中性灰 icon + 墨色文字，无彩色。**有彩色 → 无彩色**，大卡胜 | 置顶决议有 `YellowMark #FFCD4E`（全站最亮的黄）+ 3px 强调条 + `#EEF0FB` 可展开底。**黄 + 蓝条 → 只有蓝条**，置顶胜 |
| **垂直位置** | 大卡在 y≈第 4 屏位，快捷入口在其后。**先 → 后**，大卡胜 | 置顶决议在页面最顶部第一屏，且页头下方第一个 `SectionTitle` 就是它。**首屏 → 第 4 屏**，置顶胜 |

**一句话结论**：入口大卡靠**面积与彩色按钮**赢快捷入口，靠**没有黄色标记、不占首屏、不自带卡片堆叠**不赢置顶决议。它永远不会是全页最亮的东西，但永远是工具网格里最亮的那个。

### 1.4 备选方案（已评估，不采纳，记录理由）

**备选 A：大卡跨 2 格 + 右侧迷你状态卡。**
评估：在 `.dp-grid.dp-g4`（4 列）里让大卡 `grid-column: span 2`，右侧再 `span 1` 放一张迷你状态卡，第 4 格留空或放「查看全部」。
**不采纳理由**：① 留空格会在 1240px 以下（`.dp-g4` 塌成 2 列）产生一个 33% 宽的孤岛空位，六档宽度里必然出现一处视觉缺口，要额外补媒体查询才能消掉；② 迷你状态卡会把「待处理/进行中/已完成」三个计数从主卡里拆出去，主卡就只剩标题+按钮，**回答不了第 ③ 个问题（现在有多少人在提）**，等于把大卡做回了普通 CTA；③ 状态摘要需要的是「同屏可比较」，拆成两卡后视线要多跳一次。**否决。**

**备选 B：大卡跨 4 格整行。**
评估：`.dp-grid.dp-g4` 里 `grid-column: 1 / -1`。
**不采纳理由**：整行大卡会把入口区块抬升到「与健康度快照同等宽度」的层级感，且 1280px 容器下卡片宽度 1216px、内容只有标题+按钮+三计数，**大量空洞**，反而显得单薄。**否决。**

**最终方案**：大卡 `span 2`，右侧 `span 2` 放**公开列表的最近 2–3 条**（即「谁在提、处理到哪了」）。这样 `.dp-g4` 正好排满：`[大卡 2格][公开列表 2格]`，1240px 以下塌成 2 列时是 `[大卡][列表]` 上下两行，900px 以下单列。**没有任何空位，不需要额外媒体查询。**

### 2.1 区块外壳

| 项 | 规格 | 依据 |
|---|---|---|
| 区块外框 | `<section style={{ marginBottom: 32 }}>` | 与 Home 现有 5 个 section 完全一致（现有全部 32） |
| 区块标题 | 复用 `SectionTitle`，`title="提交需求"`、`desc="内部系统与数据需求的统一入口"`、`extra=` 一个 `<Button type="link">查看全部需求 →</Button>`（跳 `#/workspace/demand`） | 与「置顶决议 / 健康度快照 / 近期 Release」四处的标题+右侧 link 结构同构 |
| 栅格 | `<div className="dp-grid dp-g4" style={{ gap: 16 }}>` | 复用 `.dp-g4`；`.dp-grid` 自带 `gap:16` 已够，**不要**再传 24（Home 的 `dp-g2-asym` 用 24 是因为它是双栏主区，本区块与健康度快照同级，必须 16） |

### 2.2 入口大卡（左，`span 2`）

```
Panel (复用 ui.jsx，hover=false)
  className: "dp-demand-entry"   ← 不新增 CSS，仅作语义钩子；若要加，必须先改 global.css 并由我复审
  style: { gridColumn: 'span 2', position: 'relative', overflow: 'hidden' }
  bodyStyle: { padding: '20px 24px 20px 26px' }   ← 左 26 = 20 + 4px 强调条 + 2px 视觉补偿
```

| 子元素 | 规格 |
|---|---|
| **4px 强调条** | 绝对定位 `<span>`，`left:0; top:0; bottom:0; width:4; background: c.brand`。**只此一处允许 4px** |
| **① 这是什么** | `<h3>` 18px / 500 / `c.ink` / `lineHeight 1.5`、`letterSpacing '-0.01em'`、`margin: 0 0 6px`。文案见第 10 节。**不要用 24px**——24px 是页头 `h1` 档，用了会与「今日 Hub」抢页级标题位 |
| **② 我为什么该用** | 一行 14px / 400 / `c.text2` / `lineHeight 1.65`，`margin: 0 0 14px`。**一条服务承诺，只写一条**（如「提交后 2 个工作日内由需求受理人回应并指派」）。不要写成 3 条 bullet——bullet 会让它读起来像营销模块 |
| **③ 现在多少人提、到哪了** | 见 2.3 状态摘要 |
| **主按钮** | `<Button type="primary" size="large" icon={<PlusOutlined />}>提交需求</Button>`，胶囊 999px（`.ant-btn` 已强制）、高 40px、`fontWeight 500`、`primaryShadow: 'none'`（theme.js 已设）。右侧可再放一个 `<Button type="link" style={{padding:0}}>先看提交指引</Button>`，字号 14 |
| **按钮与摘要的间距** | 摘要与按钮之间 `marginTop: 18`；摘要与承诺之间 `16` |
| **内部竖排顺序** | ① 标题 → ② 承诺 → ③ 状态摘要 → ④ 按钮行。**摘要必须在按钮上方**：先给「别人也在提、有人已经在处理」的社会证明，再给行动按钮，点击率与信任度都更高 |

**大卡最小高度 168px**（内容撑开，不写死 `height`）。若内容不足，靠 `bodyStyle` 的上下 20px 内边距自然形成。

### 2.3 状态摘要（大卡内的 ③）

结构：**三个计数 + 两档分隔**，不要做成三张小卡（会与大卡形成「卡中卡」，层级混乱）。

```
<div style={{ display:'flex', alignItems:'stretch', gap:0, marginBottom:18, borderTop:`1px solid ${c.border}`, borderBottom:`1px solid ${c.border}`, padding:'12px 0' }}>
  三个统计段，每段之间用 1px borderLeft: c.border 分隔（第一段不加）
</div>
```

| 段 | 数字 | 标签 | 颜色规则 |
|---|---|---|---|
| 待处理 | `rows.filter(pending).length` | 待处理 | 数字 `c.ink`；**不加 Pill** |
| 进行中 | 同上 | 进行中 | 数字 `c.ink`；**不加 Pill** |
| 已完成 | 同上 | 已完成 | 数字 `c.ink`；**不加 Pill** |

**数字排版（硬约束 C11）**：
- 计数数字：`className="dp-num"`、`fontSize: 28`、`fontWeight: 500`、`lineHeight: 1.15`、`color: c.ink`、`letterSpacing: '-0.02em'`。
- 标签：`fontSize: 12`、`color: c.text3`、`marginTop: 2`。
- **为什么 28 而不是 KpiTile 的 32**：KpiTile 是「健康度快照」的主体，32px 是那一区块的视觉音高；入口大卡是次级区块，28px 形成一档差，六档宽度下都不会与健康度快照打架。

**语义色裁决（C2 / C10）**：这里**三个计数一律不挂任何 Pill、不用任何语义色**。理由：这是「需求量分布」，不是「健康状态」。语义色在本系统的契约是「红黄绿 = 稳定性状态」，需求计数属于业务量级。**若一定要给视觉锚点，只能在数字左侧加 `<StatusDot semantic="neutral" size={8} />`**——中性点。构建师不得改这一条。

### 2.4 公开列表（右，`span 2`）

| 项 | 规格 |
|---|---|
| 容器 | `Panel`，`style={{ gridColumn:'span 2', overflow:'hidden' }}`，**静止无阴影**（`.dp-card` 已保证） |
| 头部 | 复用 `PanelHead`，`title="最近提交"`、`desc="别人提了什么、处理到哪一步"`、`dense` 不传（保持 14px 内边距） |

| 行可点 | 整行 `role="button"` + `tabindex={0}` + `onClick` 跳 `#/workspace/demand`（`.dp-row:focus-visible` 已有焦点环，无需补 CSS） |

### 2.5 响应式（六档必须逐档确认）

| 宽度 | 布局 | 具体变化 |
|---|---|---|
| **375** | 单列堆叠，大卡在上 | `.dp-g4` 在 ≤900px 塌成 `1fr`。大卡与列表各占整行。**大卡 `bodyStyle` 的左内边距必须从 26 降到 20**（4px 强调条 + 16px 内容边距），否则 375 下右侧只剩 375-32-40=303px，标题换 3 行。**按钮行改为 `flexWrap:'wrap'`**（`size="large"` 的按钮在 375 下 + 次级 link 按钮会挤成一行不足 303px）。状态摘要三段：`flexWrap:'wrap'` + 每段 `minWidth: 88px`，**不改成竖排**（竖排会变成 3×44=132px 高，太占屏） |
| **768** | 单列堆叠（同 375） | 与 375 同构，只是大卡内边距回到 26px。状态摘要三段在一行内舒适排开（768-32-32=704px 内宽，三段各 234px）。**按钮行恢复单行** |
| **1024** | 两列（大卡 2 格 + 列表 2 格，各 50%） | ≤1240px 时 `.dp-g4` 塌成 2 列，恰好是我们要的 `[大卡][列表]` 并排。各 (1024-64-16)/2 = 472px。大卡内 472-26-24=422px，标题一行放得下。**这是最紧的一档，必须实测标题不超 2 行** |
| **1280** | 两列各 50% | 容器封顶 1280，内宽 1216，各 600px。大卡 600-50=550px 内容宽，标题一行、承诺一行、摘要三段一行、按钮行单行。**这是设计基准档** |
| **1440** | 同 1280（容器封顶，不再变宽） | 大卡两侧留白增加。**注意**：`.dp-container/.dp-shell` 是 `max-width:1280`，1440 下内容不拉伸——所以 1440 与 1280 的内部布局完全一致，`grid` 不需要第三档变化 |
| **1920** | 同 1280 | 同上。**不要**为了「利用宽屏」把大卡改成跨 3 格——那会打破 1280 基准的视觉比例，且 `dp-g4` 的列宽会变得过宽（(1216-48)/4×3 = 876px），按钮会离标题过远 |

**栅格类用法结论**：**直接用 `className="dp-grid dp-g4"`，大卡与列表各 `gridColumn:'span 2'`。**
不需要 `.dp-g2`（2 列在 1024 下不会塌到合适位置），也不需要新类。**唯一需要在 `Home.jsx` 里内联的是 `gridColumn:'span 2'`。**
**六档横向溢出检查**：`.dp-grid` 是 `display:grid` + `minmax(0,1fr)`，天然不溢出；列表行内 `flex:1; min-width:0` + 文本 `text-overflow:ellipsis` 保证长标题也不撑破。**无溢出风险。**

## 3. 需求提交页（`DemandView()` 就地升级）· 布局规格

### 3.1 裁决：**左表单 + 右引导栏（`.dp-g-spec`）**，不用上下分段

理由：

1. **公开列表必须与表单同屏**（C3 是产品判据）。上下分段会把公开列表推到表单下方，用户填完一屏后**看不到列表**，等于事实上的黑洞。左右分栏让「别人提了什么」始终在右侧可见，是对 C3 最强的结构性保障。
2. **`.dp-g-spec` 已经存在且语义正好**：`minmax(0,1.5fr) minmax(0,1fr)`，左宽右窄，且 **≤900px 自动塌成单列**——完全命中需求，**零新增 CSS**。
3. **右栏天然容纳三样东西**：① 受理流程/响应承诺 ② 公开列表（最近 N 条）③ BRD agent 入口。上下分段无法把这三样放在「表单旁边」而不遮挡。
4. **左栏 1.5fr / 右栏 1fr 在 1280 容器下是 720 / 480**（gap 16 时约 730 / 486），右栏 480px 足够放下编号+标题+状态的三段行。**如果右栏是 320px（如 `dp-g-article` 的 232px 档）就放不下**，所以 `dp-g-spec` 是唯一合适的既有类。

### 3.2 页面结构（自上而下）

```
<div className="dp-shell">
  ├─ 页头：h1「提交需求」24px/500 + 一行说明 14px c.text2
  │   （h1 与 Workspace 的「工作台」同级；本页是 Workspace 的 tab，不新增一级导航，C4/C6 满足）
  ├─ 需求类型分流 Segmented（见 3.3）
  └─ <div className="dp-grid dp-g-spec" style={{ gap: 16, alignItems: 'start' }}>
       ├─ 左：表单 Panel（1.5fr）
       └─ 右：引导栏（1fr）—— 承诺卡 + 公开列表卡 + BRD agent 入口卡，纵向 gap 16
```

**`alignItems: 'start'` 是必须的**：否则 `.dp-grid` 的 `stretch` 会把右栏拉到与左栏等高，右栏内容不足时出现大片空白（且卡片边框会拉得很长）。参考 `ToolsView` 的 `.dp-g-tools` 就是用了 `alignItems:'start'`。

### 3.3 需求类型分流（两档模板切换器）

- 控件：`<Segmented>`（全局已设 `borderRadius:999px`、`itemSelectedBg: surface`、`itemSelectedColor: brand`），选项为两档：
  - `轻量` → 对应类型 `数据权限 - 只读` / `数据权限 - 读写` / `其他`
  - `BRD` → 对应类型 `功能需求` / `系统接入 / 打通`
- 位置：页头下方、表单上方，独立一行，`marginBottom: 16`。
- **实际控件顺序建议**：不要用「轻量/BRD」这种**内部术语**做选项（业务方读不懂）。选项文案改为 **「权限 / 其他（4 项）」和「功能 / 系统（8 项）」**，点选后表单内部再显示具体类型。
- 切换时：表单字段**保留已填内容**（分区渲染，不 `resetFields`），仅隐藏当前档不需要的字段。**切换不丢数据是硬要求**——用户先按轻量填了标题再意识到该走 BRD，丢数据会直接导致放弃。

### 3.4 375 窄屏降级

- `.dp-g-spec` 在 **≤900px 自动塌成单列**，右栏整块落到表单下方，**顺序变为：表单 → 承诺卡 → 公开列表 → agent 入口**。
- 落地顺序调整：单列下应把 **承诺卡提到表单上方**（`order` 或 DOM 顺序微调），因为窄屏用户看不到「右栏同时可见」的优势，必须让承诺先出现。**做法**：在 ≤900px 下把承诺卡渲染到表单前（用一个 `isNarrow` 判断或直接在单列版本里 DOM 顺序为 承诺 → 表单 → 列表）。构建师可读 `window.innerWidth` 或用 CSS `order`，**推荐 CSS `order`**（不引入 resize 监听，保持纯静态）。
- 表单内所有 `Input`/`TextArea` 宽度 `100%`，无横向滚动。公开列表行在 375 下允许标题换行 2 行（`.dp-row` 的 `min-height:56` 可被内容撑高）。

## 4. BRD 完整档 8 个字段 · 控件选型

> 控件圆角规则：表单必须挂 `className="dp-form"`，此时所有输入控件为 **6px**（`.dp-form` 规则强制）；表单**外部**的 Select/Search 保持 999px 胶囊。**切勿在表单里用 `.dp-chip` 胶囊输入框**。

| # | 字段 | 控件 | 必填/计分 | 具体规格 | placeholder（真实示例文案） |
|---|---|---|---|---|---|
| 1 | 需求标题 | `Input` | **必填**（硬门槛） | 高 34，`maxLength` 60，右侧显示字符计数 `dp-num` | 「例如：门店盘点时库存对不上账，希望定位到具体环节」 |
| 2 | 需求类型 | `Select` | **必填**（硬门槛） | 单选取值 `demandTypes`，`placeholder="请选择"` | — |
| 3 | 现状 / 遇到的问题 | `Input.TextArea rows={4}` | **必填**（硬门槛） | ≥20 字；字数提示「已写 32 字 / 建议 ≥20 字」，`dp-num` | 「例如：门店盘点时对不上账。系统显示的库存和实际货架差 3–5 件，但不知道是入库、调拨还是收银环节漏记的。」 |
| 4 | 期望结果 | `Input.TextArea rows={3}` | **必填**（硬门槛） | ≥15 字 | 「例如：能在盘点差异报表里直接看到差异产生的具体环节和时间点。」 |
| 5 | 影响范围与量级 | **结构化胶囊组**（见第 5 节） | **必填**（硬门槛） | 三组单选胶囊 | — |
| 6 | 涉及系统 / 入口 | `Select mode="multiple"` + **「说不清」合法选项** | **必填**（硬门槛） | 多选；选「说不清」时**清空其他选项并锁定**（见 5.4） | 「可多选；不确定就选『说不清』，我们会帮你定位」 |
| 7 | 期望完成时间 | `DatePicker` + 「无硬性期限」`Checkbox` | **计分项（选填）** | 选中「无硬性期限」时禁用日期选择器 | 「选择日期，或勾选『无硬性期限』」 |
| 8 | 验收 / 成功标准 | `Input.TextArea rows={3}` | **计分项（选填）** | ≥15 字（填了才计分）；提示建议句式 | 「例如：当盘点差异报表能按环节列出差异时，视为完成。（写不出可以不填）」 |

**必填硬门槛 = ①标题 ②类型 ③现状 ④期望 ⑤量级 ⑥系统**（6 个）。⑦时限 ⑧验收 = 计分项。**与需求摘要完全一致。**

**硬门槛校验的呈现方式（关键）**：
- **不要**用 `Form` 的 `required` 红字报错作为主要手段——会触发 `error` 语义色满屏红（违反 C2 的精神：错误色留给稳定性）。
- **做法**：必填未填时，字段下方给**中性提示**（`color: c.text3`，如「这一项受理人必须知道」）+ 字段边框转 `c.brandBorder`（不是红）。**只有用户点击「提交」且校验失败时**，才允许对未填字段使用 `error` 语义（`Form.Item` 内置）——这是「用户主动触发的失败」，用红是合理的；**填写过程中的实时提示一律中性**。

## 5. 「影响范围与量级」结构化胶囊组 · 具体设计

三组，**每组单选**（不是多选——量级是标量，多选会让 D2 判定失去意义）。

### 5.1 三组选项文案

| 组 | 组标题（12px `c.text3`，组内上方） | 选项 |
|---|---|---|
| ① 人数区间 | 「影响多少人」 | `3 人以内` / `3–20 人` / `20–100 人` / `100 人以上` |
| ② 频率 | 「多频繁」 | `每天` / `每周几次` / `每月几次` / `偶发一次` |
| ③ 是否阻塞业务 | 「是否阻塞业务」 | `阻塞，业务做不了` / `不阻塞，但有干扰` / `暂时不影响` |

**为什么单选用短文案而非数字滑块**：单选胶囊是「零思考成本」的，业务方 3 秒内能点完三组；滑块和数字输入会让人思考「到底算 15 人还是 20 人」，进而放弃。

### 5.2 默认态 / 选中态 / 交互态

- **未选（默认）**：背景 `c.surface`、边框 `1px c.borderStrong`、文字 `c.text2`、`fontSize 13`、高 30、`padding 0 12`、圆角 999（胶囊——**这里是「表单里的选择题」，属于「标签/胶囊」语汇而非「文本输入」语汇，因此保持胶囊，不受 `.dp-form` 的 6px 影响**，因为 `.dp-form` 规则只覆盖 `.ant-input`/`.ant-select-selector`/`textarea`）。
- **hover**：边框 `c.brandBorder`、文字 `c.ink`（**不变背景**，避免 hover 就变成选中感）。
- **选中**：背景 `c.brandSubtle #EEF0FB`、边框 `1px c.brand`、文字 `c.brand`、`fontWeight 500`。**前缀一枚 `<CheckOutlined />` 或 `<CheckCircleFilled />` 12px，颜色 `c.brand`。**
- **键盘焦点**：`outline: 2px solid c.brand; outline-offset: 2px`（与 `.dp-nav-item`/`.dp-card[role=button]` 的焦点环同规格）。**这需要一条 CSS 规则**——但我裁定**不新增类**，改为在组件上直接 `onFocus/onBlur` 切内联 `outline`；或允许新增 `.dp-chip-radio:focus-visible` 一条规则到 `global.css`。**若构建师选择新增 CSS，只允许这一条**（这是无障碍必需项，不是装饰）。
- **组间间距**：组之间 `16px`；组标题与选项行之间 `8px`；选项行 `display:flex; flexWrap:wrap; gap:8`。
- **必须 `flexWrap: 'wrap'`**：375 下四个选项必须能折行，否则溢出（C5）。

### 5.3 组标题前的序号

`① 影响多少人` 这种序号**不要加**。理由：加了序号会读成「第 1 步/第 2 步」，而这三组是并列属性不是流程步骤，会误导用户以为要按序填。

### 5.4 「说不清」的交互（字段 ⑥）

- 「说不清」是 `Select mode="multiple"` 选项列表里的**第一个选项**，文案：**「说不清，帮我定位」**（不是「不确定」——「帮我定位」把不确定性变成服务承诺，用户更愿意点）。
- 选中「说不清」时：**自动清空其他已选系统项**，并禁用其余选项（视觉上 `opacity:.5`，**不是** `textDisabled` 做正文）。
- 取消「说不清」后：其余选项恢复可选，已清空的项**不回填**（避免用户以为还在）。
- D3 计分：选具体系统 = 1.0；选「说不清」= **0.5（不扣光）**；空白 = 0。

## 6. 评分面板「资料完整度」· 视觉规格

### 6.1 命名与定位

- 叫 **「资料完整度」**，数字形式 **`资料完整度 68%`**。**禁止**出现「得分 / 分数 / 评分 / 打分 / 满分」字样。
- 原因：叫「分数」会把 agent 变成评分官，用户会为了刷分而写废话（「这个需求很重要，希望尽快处理」）；叫「完整度」则语义指向「资料齐不齐」，与「补上这句会更快被受理」的行为引导同向。

### 6.2 位置与默认态

- 位置：**左栏表单的底部，提交按钮上方**，独立成一条横向条（不是浮层、不是右侧栏）。
- 默认：**折叠态**，一行高 44px；右侧一个 `<Button type="link" size="small">展开明细</Button>` + `<DownOutlined/>`。
- 折叠态内容：`资料完整度` 标签 + **横向进度条** + `68%` 数字 + 右侧展开按钮。

### 6.3 进度条规格

| 项 | 规格 |
|---|---|
| 轨道 | 高 **6px**、宽 `flex:1`、`background: c.grid #ECEEF0`、`borderRadius: 999`（**胶囊圆角**） |
| 填充 | `background: c.brand #3643BA`、`borderRadius: 999`、`width: ${pct}%`、`transition: width .24s ease` |
| 填充颜色 | **永远只有品牌蓝**。低位（<40%）也不变色——**禁止红黄绿**（C2）。低完整度用「文案」表达关切，不用颜色 |
| 最小可见宽度 | `minWidth: 6`（0% 时仍显示一个小圆点，避免「条消失」的视觉歧义） |
| 百分比数字 | `className="dp-num"`、`fontSize: 15`、`fontWeight: 500`、`color: c.ink`、`minWidth: 44`（`textAlign:'right'`，防止 9% → 100% 时数字宽度变化导致进度条抖动）。**`%` 符号也用等宽**（整体包在 `dp-num` 里） |

### 6.4 总评一句话（文案模板）

按完整度分四档，**越低的档位话术越要「先肯定、再给一条建议」**，不能出现任何扣分口吻：

| 完整度 | 模板 | 说明 |
|---|---|---|
| ≥ 80% | 「资料齐了，受理人拿到就能直接排期。」 | 纯肯定，不给建议 |
| 60–79% | 「主体信息够了。补上{最弱项}会更快被受理。」 | 肯定 + 一条建议 |
| 40–59% | 「已经说清了问题。把{最弱项}补一句，受理会顺很多。」 | 肯定「已说清问题」+ 一条建议 |
| < 40% | 「先写清现状和期望就能提交；{最弱项}之后再补也可以。」 | 降低门槛感，明确「能提交」 |

`{最弱项}` 是 D1–D5 里得分最低那一维的**人话名**（不是维度编号）：`问题与方案的分离` / `影响范围` / `涉及系统` / `验收标准` / `标题的指向性`。

### 6.5 展开后逐项（D1–D5）状态呈现

**核心约束（C2 + C10 的交叉点）**：评分是「评价」，**不得**用红黄绿。命中/未命中的区分只用**三种中性视觉**：

| 状态 | 视觉 | 具体规格 |
|---|---|---|
| **命中（满分）** | 品牌蓝实心圆 + 中性文字 | `<CheckCircleFilled style={{ fontSize:13, color: c.brand }} />` + 维度名 `c.ink` + 右侧「已具备」`fontSize 12, color c.text3` |
| **部分命中（0.5，仅 D3「说不清」）** | 品牌蓝描边圆 | `<ClockCircleOutlined style={{ fontSize:13, color: c.brand }} />` + 「说到一半」`color c.text2` |
| **未命中（0 分）** | 中性空心圆 | `<CircleOutlined style={{ fontSize:13, color: c.textDisabled }} />` + 「待补充」`color c.text3` |

- **右侧不给分值**（不给「3/4 分」这种表达）。改为**每项一行 `c.text3` 的小字行动提示**，例如 D1 未命中 → 「把『加个导出按钮』移到期望结果，现状里写清现在的现象」。这比给分值有用 10 倍。
- 逐项行高 40px，行间 `borderTop: 1px c.border`（首行无），`padding: '8px 0'`。
- 顶部一行汇总：`资料完整度 68% · 5 项里 3 项已具备`（数字全 `dp-num`）。
- 5 项的展示顺序按维度固定 D1→D5，**不按得分排序**（排序会让用户觉得在被排名）。

### 6.6 折叠/展开交互

- 折叠行整体可点 + 右侧 link 按钮；`aria-expanded` 切换。
- 展开用高度过渡 `transition: height .2s ease`（或直接条件渲染 + `marginTop 12`，**推荐直接渲染**，因为高度动画需要测量，spec 阶段不引入）。
- 展开状态**不持久化**（切档位/刷新回折叠）。

### 6.7 轻量档的评分屏显

**轻量档不跑评分**（需求摘要明确）。此时表单底部**不显示任何进度条**，替换为一条中性承诺条：
`Panel` / `padding: '12px 16px'` / `background: c.page` / 文案「这类需求不需要填完整 BRD，提交后 2 个工作日内回应。」+ `<Pill semantic="neutral">4 项必填</Pill>`。
**不要**显示一个「—%」的灰进度条——那会让用户以为评分坏了。

## 7. BRD agent 侧栏 · 视觉规格

### 7.1 形态裁决：**可收起的内联提示卡（常驻右栏），不是 Drawer**

- **右侧引导栏（`dp-g-spec` 的 1fr 栏）内，常驻一张 agent 卡**，位置在「承诺卡」与「公开列表」之间（或最上）。**不用 `Drawer`**。
- 理由：① `Drawer` 会**遮挡表单**（420px 宽从右滑入），而需求是「与表单共存、不遮挡」；② agent 的定位是**协作者，随填随看**，用户需要一边填一边看见它的建议——抽屉要在「打开→看→关」之间来回，反而增加成本；③ 右栏本来就空着（它需要承载公开列表），把 agent 放进去是**零新增面积**。
- **`AgentDrawer` 的脚本化范式要沿用**（C7），但**载体换掉**：沿用它的 **①「脚本化原型」披露胶囊 ②气泡样式 `.dp-bubble--agent` ③单条建议的话术结构 ④「可以这样问」的快捷 chips**。不沿用 Drawer 外壳。
- **同时保留一个「展开完整对话」的入口**：右栏 agent 卡右上角放 `<Button type="link" size="small">完整对话</Button>`，点击后**复用现有 `AgentDrawer` 组件**（`onOpenAgent`）——这样既满足「不遮挡」，又保留了既有组件的复用。**首选：只做内联卡，右侧不给 Drawer 入口**（避免同一能力两个入口造成困惑）。**我的裁决：不做 Drawer 入口，只做内联卡。**

### 7.2 内联 agent 卡规格

| 项 | 规格 | 沿用来源 |
|---|---|---|
| 容器 | `Panel`（白底 1px 边框、8px 圆角、无阴影）。**不给它品牌蓝强调条**——强调条已被首页大卡占用，且 agent 不该比表单更强调 | — |
| 头部 | 复用 `PanelHead`，`title="BRD 协作助手"`、`dense`；`extra` = **「脚本化原型」披露胶囊**：`<span className="dp-chip" style={{background:c.page, border:`1px solid ${c.border}`, color:c.text3}}>脚本化原型</span>` | `AgentDrawer` title 里那枚完全一致 |
| 头像方块 | 26×26、`borderRadius:6`、`background: c.page`、`border: 1px solid c.border`、`color: c.text2`、`fontSize:13`，内放 `<RobotOutlined />` | `AgentDrawer` 的 agent 头像规格，**逐值复用** |
| 气泡 | `className="dp-bubble dp-bubble--agent"`（`background:#F5F4F5`、`border:1px solid #E1E0DF`、`color:#000F17`、圆角 12 左上 4） | `global.css` 已定义 |
| 气泡宽度 | 卡内不受 `.dp-bubble` 的 `max-width:88%` 限制——右栏 480px 下 88% 约 420px，够用，**保持不覆盖** | — |
| 快捷 chips | 复用 `.dp-chip`，`background: c.brandSubtle`、`border:1px solid c.brandBorder`、`color: c.brand`、`cursor:pointer`。文案**从表单语境取**（不是 FAQ 问题），如「我该先写现状还是期望？」「量级怎么估？」「验收标准写不写？」 | `AgentDrawer` 的 prompt chips 规格逐值复用 |
| 输入区 | **不做真实输入框**。理由：右栏空间有限，且「脚本化」的输入框会诱导用户打字却没有有意义反馈。改为：**3 枚 chips + 点击后吐出脚本化气泡**（`AgentDrawer` 的 `send(p)` 逻辑可直接借用） | `AgentDrawer` 的 chips 交互 |
| 卡内边距 | 气泡区 `padding: '12px 16px'`，chips 区 `padding: '0 16px 16px'` | — |

### 7.3 与表单共存的交互规则（「协作者不是评分官」的落地）

这是本次设计的**行为契约**，构建师必须按此实现话术切换时机：

| 时机 | agent 说什么 | 不说 |
|---|---|---|
| **初次进入（表单空）** | 「先写现状就行。标题、类型、现状、期望、量级、系统这 6 项齐了就能提交。」（**降低门槛**） | 不报分数、不列 8 项清单 |
| **用户填完 ≥2 项** | 「{已填项} 这块清楚了。」+ **只给一条**建议（当前最弱维度的修正） | 不一次列 7 条扣分项 |
| **用户点过提交但被拦** | 「还差 {N} 项必填。{最弱项} 不填也能提交，但补上会更快被受理。」 | 不说「提交失败」 |
| **D1 命中方案词** | 「『加个导出』是解决办法，挪到期望结果里；现状写清现在是什么现象——受理人据此才能判断该不该做。」 | 不扣分、不指责 |
| **完整度 ≥80%** | 「资料齐了，我没什么要改的。」+ 停止给建议 | 不为了显得有用而硬提建议 |

**铁律：agent 的气泡里任何时刻不得同时出现 2 条以上「待改」建议。** 一次一条，用户改完再出下一条。

## 9. 破坏既有系统的红线清单（构建师绝对不要做）

以下每一条都对应一个**具体的、可能被写出来的做法**。全部违反已锁定令牌或已验收语汇。

1. **不要给首页入口大卡铺 `background: c.brand` 实底**（或任何占面积 > 30% 的品牌蓝实底）。品牌蓝在本系统的契约是**强调色**，面积色只有 `#000F17`（顶栏）与 `#F5F4F5`（页面底）。
2. **不要给大卡的强调条写 5px 及以上**，也不要让**同一页出现第二张 4px 强调条**卡。4px 是「全页唯一」的声明，置顶决议固定 3px，不可互换。
3. **不要在首页入口区块使用 `YellowMark` / `c.yellow`**。黄色的用途是「小面积标记」，且本页已被置顶决议与里程碑占用；新增一处会让首页出现三个黄色源，最强的那个反而失效。
4. **不要用红/黄/绿表达「资料完整度」或任何 D1–D5 维度的命中情况**。低完整度**不是错误**，它是「还没写完」。命中/未命中只用 `c.brand` 与 `c.textDisabled`/`c.text3`（第 6.5 节三种中性视觉）。
5. **不要把需求计数（待处理/进行中/已完成）改成 `<Pill semantic="warning">` 或 `error`**。计数是业务量级不是稳定性状态；本系统的红黄绿只属于「系统健康度 / 状态」语汇，且已在首页健康度快照里被占用。**中性数字 + 中性点**是唯一表达。
6. **不要在表单里使用胶囊输入框**。表单容器必须 `className="dp-form"`，靠它把 `.ant-input` / `.ant-select-selector` / `textarea` 强制回 6px。**漏掉这个 className 会让表单变成一排胶囊**，与「控件 6px / 按钮胶囊」的双档圆角规则冲突。
7. **不要在字段下方用 `c.error` / `c.warning` 做「填写过程中的实时提示」**。实时提示一律 `c.text3` + 边框 `c.brandBorder`。只有用户点击提交、被校验拦下时，才允许 `Form.Item` 用 error 语义。**「还没写」不是错误，「提交失败」才是。**
8. **不要给 BRD agent 做「一次列出 5 项待改」的清单式回复**，也不要在气泡里出现「得分 / 扣分 / 满分」字样。定位是协作者：**每条气泡最多 1 条建议**，且必须先肯定已填内容。
9. **不要给评分面板用整数档位跳变**（0 / 25 / 50 / 75 / 100）。D3 有 0.5 权重，必须支持**任意百分比**（如 68%），进度条按实际值渲染。
10. **不要在需求提交页新增第二个一级导航项或新的顶栏入口**（C4：顶栏 T2 档 1012–1271px 内容余量只有 19px）。入口方式只有两个：首页大卡、工作台 tab；投放路径只有 `#/workspace/demand`（C6）。
11. **不要把公开列表放到表单下方（折叠/隐藏/懒加载）**，也不要做成「默认收起」的 `<Collapse>`。C3 的判据是「同屏可见」；藏起来 = 黑洞 = 用户回去走 IM。
12. **不要给 `Panel` 加阴影**。静止态卡片只有 1px 边框、无阴影、hover 才抬升（`.dp-card--hover`）。新增卡一律照此；**不要用 `shadowFloating` 做「重点卡」**——重点靠强调条表达，不靠投影。
13. **不要在新增区块新增任何 CSS 类 / 色值 / 半径 / 阴影常量**。色值只在 `theme.js` 与 `global.css`；半径只用 999/8/6/12；阴影只用 `shadowRaised`/`shadowFloating`。第 5.2 节的焦点环是**唯一**允许新增的一条 CSS 规则（无障碍必需）。
14. **不要用 `textDisabled #B3B7B9` 做任何说明文字、占位符、组标题或未选中胶囊的文字**。它只有 2.04:1。占位符/说明用 `c.text3 #667085`。
15. **不要把数字、编号、百分比、时间交给比例字体**。需求编号（`REQ-2026-0921`）、完整度（`68%`）、字数（`已写 32 字`）、计数（`12`）一律 `dp-num`/`dp-mono`（C11）。**漏一个就会在列对齐时露出来。**
16. **不要在 375 下让状态摘要改成竖排**（3 段会变成 132px 高），也不要让按钮行溢出。三段 `flexWrap:'wrap'` + `minWidth:88`，按钮行 `flexWrap:'wrap'`。
17. **不要把轻量档做成「BRD 档的省略版」**（例如显示一个灰掉的进度条或禁用字段）。轻量档是**独立的一条轻路径**：4 字段 + 响应承诺条 + 无评分。它不该看起来像「残缺的 BRD」。
18. **不要引入任何网络请求、真实 LLM 调用或后端接口**（C8）。agent 全部脚本化，且**必须**在卡头保留「脚本化原型」披露胶囊（C7）。

## 10. 文案语气守则

三面三种语气，**不能混**：面 1 是**服务台**（告诉你能办什么、多久办完），面 2 是**引导**（帮你写清楚，不是审你），面 3 是**协作者**（站在你这边一起补材料）。

### 面 1 · 首页入口大卡（服务台语气）

**正面示例（3）**
1. 标题：「有需求，从这里提交」——短、动词开头、指向明确。
2. 承诺：「提交后 2 个工作日内由受理人回应并指派，进度在提交页实时可见。」——给出**具体时限 + 具体可见性**。
3. 摘要标签：「待处理 / 进行中 / 已完成」——三个词都是**状态**，不是评价。

**反面示例（3，具体的坏文案）**
1. ❌「需求中心 · 一站式数字化服务门户」——「一站式 / 门户」是营销黑话，用户读完不知道能办什么事。
2. ❌「点击提交，让需求不再等待！」——感叹号 + 空许诺，「不再等待」等于没承诺。
3. ❌「需求受理率 98%，平均响应 1.2 天 👍」——① 无来源的考核数字；② emoji 在内部工具里是噪声；③ 把「响应」包装成 KPI 会让人怀疑数据。

### 面 2 · 需求提交页（引导语气）

**正面示例（3）**
1. 现状字段提示：「描述你遇到的**现象**就行，先不用想怎么解决。」——明确**降低门槛**，解除「我得想好方案」的压力。
2. 验收标准标签：「验收 / 成功标准（选填，写不出可以先跳过）」——把「选填」和「可以跳过」说两遍，因为它确实是大家最怕的一项。
3. 提交后反馈：「已提交，受理人会在 2 个工作日内联系你。编号 REQ-2026-0932，随时回来查进度。」——**给编号**（可追溯）+ 给预期 + 给退路。

**反面示例（3）**
1. ❌「请详细描述您的需求背景、业务价值与预期收益」——「业务价值 / 预期收益」是给业务方出的论文题，会直接劝退提交。
2. ❌「验收标准（必填）：请填写可量化的验收指标」——① 设成必填违反已定决策；② 「可量化指标」是 PM 语言，业务方写不出。
3. ❌「您的需求将由系统自动评估并分配优先级」——「自动评估」暗示被算法审判，用户会开始揣测规则而不是写清问题。

### 面 3 · BRD agent 侧栏（协作者语气）

**正面示例（3）**
1. 首次进入：「先写现状就行，想到哪写到哪，我帮你理。」——**先解除压力**，再谈其他。
2. 单条建议：「『加个导出按钮』更像解决办法——挪到『期望结果』里；现状那段写清现在是什么现象，受理人就能判断该不该做。」——**肯定 + 一条建议 + 说明为什么**，全程不说「扣分」。
3. 完整度达标：「资料齐了，我没什么要改的。提交吧。」——**懂得停下**，不为显得有用而硬提建议。

**反面示例（3）**
1. ❌「检测到 5 项问题，总计扣 32 分，请逐项修正后提交。」——「检测 / 扣分 / 逐项修正」完全是评分官口吻，且一次列 5 项会让用户直接关掉。
2. ❌「你的描述不够清晰，建议参考以下 BRD 模板第 3.2 节……」——① 「不够清晰」是**对人的评价**；② 让业务方去读模板等于把活推回去。
3. ❌「当前完整度 34%，低于部门平均水平 71%。」——**横向比较是最伤人的一种表达**，会让人直接放弃提交而不是补齐资料。
