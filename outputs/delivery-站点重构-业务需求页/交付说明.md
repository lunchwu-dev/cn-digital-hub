## 二、几个值得你知道的设计判断

**1. 异常告警不用红色。**
项目有一条硬规则：红/黄/绿只出现在 `#/ops` 的「稳定性状态」区。理由是红黄绿是红绿灯隐喻，天然携带绩效评价意味，与门户「禁止跨人比较」的立场冲突。
所以楼层里的「异常告警」用**品牌蓝图标 + 中性数字**，靠「待跟进」这个词传达紧急度，而不是靠颜色。这是**主动克制**，不是漏做。

**2. 责任人放在格子里，不藏在列表里。**
你的原话是「异常告警需求待跟进事项**及责任人**」。若格子里只有数字，责任人要下钻进列表、再逐行扫右端才能拼出来 —— 等于把你点名的信号藏了两级。现在直接写在格内（`责任人 顾一鸣`），多人时退化为 `责任人 N 人`，把「具体是谁」留给下钻列表。

**3. 反馈融合后，入口不依赖关键词。**
Agent 面板的「可以这样问」里有一条显式的 **「提个反馈」**。点它直接进入反馈表单，不经过语义识别。
原因：早期版本靠关键词匹配判断「用户是不是在提反馈」，实测会把「SSO 接入有什么常见问题？」这类**知识提问**误判成反馈。现在关键词只是快捷方式，不是唯一通路。

**4. 需求行不做成可点。**
需求详情没有独立路由，点进去无处可去。给一个点了没反应的行、还让它键盘可达，比不可点更糟 —— 那是个谎言。真正的入口是上方「新增需求」。

**5. 双档表单。**
轻量档（权限类，4 项必填，不评分）vs 完整档（功能/集成，8 项，有完整度引导）。一刀切 BRD 会赶走内部工程师，纯表单又让业务说不清需求。

## 四、本轮的测试自证（为什么这个「全绿」可信）

每条新增断言都用**变异测试**证明过它会红，不是只跑绿：

| 变异 | 改了什么 | 结果 |
|---|---|---|
| M1/M2 | 删掉 `order:3` 规则 / `display:contents` → `block` | 红，随后还原 |
| M3 | 重命名 `dp-floor-cell` | 红（楼层 5 格 → 0） |
| M5 | 注入**类挂**语义色 `.dp-floor-cell .dp-num{color:#e3262f}` | 红（15 处命中） |
| M7 | 把裸话题词「问题」加回反馈词表 | 红（列出 3 条被劫持的问句） |
| M8 | 改掉「提个反馈」chip 文案 | 红 |
| M9 | 把 `adviceTopic` 退化为「只认 current」 | 红（2 条，指向 acceptance/scale） |
| M10a | 楼层不再渲染责任人 | 红（只红「明示责任人」1 条） |
| M10b | 责任人颜色改成语义红 | 红（只红「中性灰」1 条） |

过程中修掉的**真实缺陷**（不是测试问题）：
- **反馈意图劫持**：`replyFor()` 第一优先匹配反馈词表，而旧词表含裸话题词，实测 3 例误判（含 1 例漏检）
- **`adviceTopic` 死比较**：原实现只返回 `'current' | null`，导致规范要求的「建议已高亮 → 字段 agent 收起」这条防重复规则**实际只对 1/6 个话题生效**

## 六、已知取舍（不影响使用）

1. **轻量档没有全局建议卡**。全局 assistant 卡只在完整档渲染；轻量档只有字段级 agent。这是刻意的 —— 轻量档只有 4 项，加一张全局卡反而增加噪音。
2. **「业务需求」与「BRD」用词**：栏目名统一叫「业务需求」，完整档内部提到「完整 BRD」。前者是业务语言，后者是填空模板名，暂未强行统一。
3. **楼层计数为示意数据**（页面上已注明）。基准日取 `META.updated`（2026-09-17），异常告警按 4 条规则实时计算。
