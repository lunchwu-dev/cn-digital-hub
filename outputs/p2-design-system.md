## 0. 一句话总纲

> **本次不引入任何新色相、不引入任何新圆角、不引入任何新阴影。**
> 标签体系的两轴区分靠**形状语汇**（点阵 / 填充条 / 描边 vs 填充）而非颜色；实证度 4 档靠**同一色相的深浅阶**（`brand` 阶梯）而非语义四件套。
> 新增 token 仅 **5 个**，全部是既有色值的中间阶，且**全部为「单色阶 / 中性」**，不与「语义四色只表达运行状态」「品牌黄只做小面积标记」两条铁律冲突。

## A. 令牌复用裁决

### A.1 两条正交轴如何在视觉上可区分，且不新增色相

**裁决：用「形状语汇」区分，两条轴都不是语义色，一条走品牌蓝系，一条走中性灰系。**

| 轴 | 色相来源（既有 token） | 形状语汇 | 为什么 |
|----|---------------------|---------|--------|
| **领域轴（Domain）** | 品牌蓝系：`brand` / `brandSubtle` / `brandBorder` = `#3643BA` / `#EEF0FB` / `#C3C9F0` | **实心浅蓝底 + 蓝色描边**（`bg=brandSubtle`, `border=brandBorder`, `color=brand`） | 领域是**门户的检索主轴**（「谁懂 RAG」是最强意图），配品牌色使其在一屏里第一眼可辨 |
| **能力类型轴（Capability）** | 中性系：`page` / `border` / `text2` = `#F5F4F5` / `#E1E0DF` / `#616161` | **浅灰底 + 灰描边**（`bg=page`, `border=border`, `color=text2`） | 能力是**跨领域的可迁移做法**，是「背景信息」不是「主查询对象」；用中性灰使其自然退后一档 |

**为什么这样不会与既有规约冲突（逐条论证）：**

1. **不与「语义四件套只表达运行状态」冲突**：语义四色（success/warning/info/error）在本系统里已被 `Pill` / `KpiTile` / `Delta` 占用表达**系统运行状态**（正常/预警/异常/提示）。标签的轴属性**不是运行状态**，因此**一个语义色都不用**——领域轴用品牌色、能力轴用中性灰，与四件套完全不重叠。
   > 这里有一条容易被忽略的既有反例：`ChannelTag`（`ui.jsx:43`）早已用 `page` + `border` + `text2` 做「中性浅底频道标签」。**能力轴 chip 与 `ChannelTag` 同款中性语汇，是刻意的复用**——频道标签与能力标签在语义上都属「归类性元信息」，同款中性表达是自洽的。
2. **不与「品牌黄仅小面积标记」冲突**：品牌黄 `#FFCD4E` 在本次**一次都不用**。领域轴用的是**品牌蓝**，不是品牌黄。品牌蓝是主色（全站导航选中态、按钮、链接都在用），**不是「小面积标记专用色」**——README 对黄色的约束不传递给蓝色。
3. **不与「图表颜色编码规约」冲突**：该规约约束的是 `charts.jsx` 里的数据序列。标签 chip 不是数据序列（不是同一度量下的多个并列序列），不受该条约束；但本文**主动继承它的精神**（见 A.2）。
4. **不给用户留「两轴可以比大小」的错觉**：两轴的颜色语义不同（蓝=你的对象，灰=你的做法），且都**不使用递进色阶**——chip 是布尔式的「有/无属性」，不是一个可比的量。色的选择**故意不携带强弱**。

> **放弃了什么**：放弃了「两轴用一对互补色（如蓝 vs 橙）更醒目」的做法。理由：一旦引入第二色相，它必然要么借用语义色（污染四件套语义）、要么新增色相（违反需求硬约束）。放弃了「给两轴各配一个 icon 形状」的做法——icon 会与 `icons.jsx` 线性图标体系争抢视觉，且 12px chip 内 icon 可辨识度不足。**最终靠「蓝 vs 灰 + 圆点 prefix vs 无 prefix」双通道区分，冗余度足够。**

**轴的第 3 通道（形状级冗余，供色盲用户）**：
- 领域轴 chip 的文字前缀 **`◈`（菱形符号）**，能力轴前置 **`◇`（空心菱形）**——同族形状、实心/空心对照，与 `Pill` 的 `dot` 参数同构思路（`ui.jsx:11` 已有 `dot` 布尔）。
- 该符号**不占用色相、不占用图标字体**，用 Unicode 几何字符（`U+25C8` / `U+25C7`），走 `fontSans` 栈，`PingFang SC` / `Microsoft YaHei` / Segoe UI 均有覆盖。
- 只在**字号 ≥12px 的 chip** 上启用；矩阵里的 11px 微 chip **关闭符号**（太小会糊），此时**只靠蓝/灰区分**，并在矩阵内每轴有分区标题兜底。

### A.2 实证度 4 档的配色裁决 —— **确认用单色阶，不用语义色**

**你的倾向是对的，我确认，并补上论证与具体色值。**

**裁决：实证度 4 档 = 品牌蓝的 4 级深浅阶（单色阶），取自 / 派生自既有 `brand` 家族。**
**明确否决：用 success/none warning/emerging error 之类的「红黄绿」表达。**

**否决「红黄绿」的三条理由（按重要性排序）：**

1. **语义污染是不可逆的**：`success`/`warning`/`error` 在本系统里已经**牢牢绑定运行状态**（`statusLabel()` → 正常/预警/异常）。把 `none` 涂成 `error`（红），用户会读成「这个人这条标签**出问题了**」。而实证度为 0 的**真实含义是「暂无公开贡献佐证」——是事实，不是故障**。让红绿去表达一个非绩效、非故障的量，会**稀释掉语义色在全站的信噪比**——这正是 `Delta` 组件已经记录过的教训（`ui.jsx:145-147`：「噪声区间内的微小波动用中性灰，否则会被涂成和『库存与供应链 异常』同款红，很快教会大家无视红色」）。
2. **红黄绿必然被读成「绩效红绿灯」**：需求 F.7 明确「**禁止排行榜、禁止跨人比较**」。红黄绿是**红绿灯隐喻**——它天然携带「停/慢行/通行」的评价意味。同屏出现「甲：4 档全绿 / 乙：2 档两红」，即使不做排序，**它已经是一个排行榜了**。这与一条硬约束正面冲突，不是审美问题。
3. **顺承既有图表规约**：README 已记录「单序列柱状图必须单色，把 6 根同类柱子涂 6 色会让『绿=健康』与数据反着来」。实证度 4 档**是同一度量（佐证充分度）下的 4 个等级**——**它是单序列的分档**，不是多序列的身份区分。**分类色板（`chart` 8 色）在这里同样不适用**。

**具体色值（4 档 = 蓝的 4 级深浅，全部沿用/派生自既有 `brand` 家族）：**

| 档 | id | 文案 | 填充色 token | 色值 | 来源 |
|----|----|------|-------------|------|------|
| 0 | `none` | 暂无实证 | `brandStep1` **(新增)** | `#DCE0F4` | 派生自 `brandBorder #C3C9F0` 再降一阶饱和度 |
| 1 | `emerging` | 有初步产出 | `brandStep2` **(新增)** | `#A9B2E6` | 派生（`brandBorder` 与 `brand` 的中点偏浅） |
| 2 | `established` | 有稳定的产出 | `brandStep3` **(新增)** | `#6B78D4` | 派生（`brand` 提亮一阶，用于区分 2/3 档） |
| 3 | `authoritative` | 有沉淀与影响力 | `brand` **（既有，复用）** | `#3643BA` | `TOKENS.brand` |

**为什么第 3 档必须复用 `#3643BA` 而不是自己再派生一个更深的**：`#3643BA` 已经是 `brand` 基准，往下是 `brandHover #2C3799` / `brandActive #232C7E`——那两个是**交互态专用**（hover/active），**不能挪用为静态数据语义**，否则「看起来更深的蓝」会与「鼠标正悬停」混淆。因此最高档就停在 `#3643BA`，由**填充比例 + 文案**承担「最高」的表达。

**空槽（未达档）的色**：`TOKENS.border` `#E1E0DF`（与卡片边框同色，让空槽**读起来像「凹槽」而不是「占位」**）。

> **放弃了什么**：放弃了「档位色相从冷到暖递进（蓝→青→绿→金）」的方案——好看，但会重新引入「多色=多身份」的误读，且必须新增色相。放弃了「用 `chart[2] #12A594` 青色系做正向递进」——同样是引入第二色相。代价是 4 档的**辨识度依赖明度差**，在低质量屏幕上 0 档与 1 档较难分；**补偿手段是填充比例 + 文案双通道**（见 B.2）。

### A.3 新增 token 清单（克制到 5 个，全部为「单色阶 / 中性」）

> **原则：能复用既有就不新增。** 下列 5 个都经过「既有 token 是否够用」的逐个检验，理由写在「为什么既有不够」列。

```js
// —— 建议追加到 theme.js 的 TOKENS（区块位置：紧接 chart 色板之后）——
// 标签体系 / 成熟度专用：单色阶 + 中性，零新色相
brandStep1: '#DCE0F4',   // 实证度 none 槽已填态 + 空槽以外的极浅底
brandStep2: '#A9B2E6',   // 实证度 emerging
brandStep3: '#6B78D4',   // 实证度 established
cardHeadBg: '#FAFAFA',   // TagMatrix 分区标题条底（比 surface 深一档、比 page 浅一档）
dashedBorder: '#C9CCCE', // 吹牛态虚线描边 + 未选定 chip 描边（见 B.4 / C.4）
```

| token | 用途 | 为什么既有 token 不够 |
|-------|------|---------------------|
| `brandStep1` | 实证 0 档填充、极浅蓝底 | 既有 `brandSubtle #EEF0FB` 太浅（做填充条几乎看不见，无法与空槽 `border #E1E0DF` 区分）；`brandBorder #C3C9F0` 又太深（与 1 档挤在一起）。**需要它俩之间的一个阶**。 |
| `brandStep2` | 实证 1 档填充 | 没有现成的中间阶；`brandBorder` 用作填充时偏亮，且它是**描边专用**语义。 |
| `brandStep3` | 实证 2 档填充 | 同理；`chart[0]` 虽然是 `#3643BA`（与 brand 同值），但 `chart` 是**图表分类语义**，挪用作 chip 会破坏「色板各自有其语义域」的约定。 |
| `cardHeadBg` | TagMatrix 分区标题条 | `page #F5F4F5` 用于**页面底**（若卡片内再用，卡内卡外同色，面板边界糊掉）；`surface #FFFFFF` 就是卡片底（无对比）。**需要一档「卡片内的浅底」**。 |
| `dashedBorder` | 虚线描边 | `border #E1E0DF` 太浅、虚线会看不见；`borderStrong #D9DDE1` 同样浅；`textDisabled #B3B7B9` 是**文本专用**（README 有断言「图表内无 textDisabled 承载文字」，挪用作描边会破坏该 token 的语义边界）。 |

**新增后对既有断言的影响**：`smoke.cjs` 的「零硬编码颜色」断言检查的是**组件内不出现字面色值**。追加 `TOKENS` 条目**不触碰组件层**，因此**零风险**。但需注意：**本文所有新 token 必须同时进入 `TOKENS`，组件里只允许 `c.brandStep2` 这样取——不允许出现 `'#A9B2E6'` 字面量。**

### B.1 自评圆点阵（Self-Rated Interest Dots）

| 属性 | 紧凑态（TagMatrix 内） | 放大态（个人页主标签） |
|------|---------------------|---------------------|
| 点数 | 固定 **4 个**（与 4 级一一对应） | 固定 4 个 |
| 点尺寸 | **7px × 7px** | **11px × 11px** |
| 点间距（gap） | **4px** | **6px** |
| 点阵总宽 | 7×4 + 4×3 = **40px** | 11×4 + 6×3 = **62px** |
| 行高 | **12px**（点垂直居中） | **16px** |
| 已达级（filled） | `background: c.brand`，无描边 | 同左 |
| 未达级（empty） | `background: transparent`，`border: 1.5px solid c.brandBorder` | 同左 |
| 级别数字 | **不显示数字**（4 级用点阵已足够表达） | 不显示数字 |
| 级别文案 | **显示**，13px / `c.text2`，左侧与点阵 gap **8px** | 15px / `c.text2`，gap **10px** |

**为什么未达级用「描边空点」而不是「更浅的实心点」**：
- 描边空点传达的是「**位置已为你留好，但你没填**」——这对**可自填的主观项**是准确的隐喻；
- 浅实心点会被读成「有一点点」，与 1 档混淆；
- **描边空点的形状与实心点有明确的「空心/实心」对比**，这正是「自评用圆形点阵」这一形状语汇的意义所在：**圆形天然表达「可被打点的选项」**（像选票、像进度点）。

**为什么点阵宽度固定、不随文案长度变**：点阵是**度量刻度**，不是文本。固定宽度让同一屏里多个标签的点阵**左边缘与右边缘对齐成列**，用户的视线可以**竖着扫**（这正是矩阵能读的前提）。文案长度差异由「右对齐留白」吸收。

### B.2 实证填充条（Evidence Bar）—— 填充比例的裁决

| 属性 | 紧凑态 | 放大态 |
|------|--------|--------|
| 条高 | **6px** | **8px** |
| 条宽（轨道总宽） | **64px**（固定） | **160px**（固定） |
| 圆角 | **999px（胶囊）** | **999px（胶囊）** |
| 轨道底色（未填部分） | `c.border` `#E1E0DF` | 同左 |
| 填充色 | 见 A.2 的 4 档色值 | 同左 |
| 分段 | **4 段等分，段间 2px 透明缝** | 4 段等分，段间 3px 缝 |
| 段宽（紧凑态） | (64 − 2×3) / 4 = **14.5px** | (160 − 3×3) / 4 = **37.75px** |

**圆角裁决：999px（胶囊），不是 6px 控件圆角。**
- 依据既有签名：「胶囊 999px 用于**按钮 / 标签 / 搜索框**，卡片 8px、控件 6px」。实证条属于哪个？**它是「标签的组成部分」，随 `TagChip` / 标签卡存在，不是一个可交互的控件，也不是一张卡片。**
- 更关键的**功能理由**：4 段等分时，段与段之间的 2px 缝隙必须**读起来像「分段」而不是「断裂」**。圆角端点让每一段自身是完整的胶囊，**段的一次递增读作「多亮了一颗珠子」**，而不是「色带变长了」。「珠子」隐喻**天然不携带大小比较意味**——这正是「不是绩效分」这一约束在形状层的要求。
- **否决 6px**：6px 圆角会让 4 段连成一个连续的条形，恢复成「进度条/进度分」的读法（进度分就是绩效分），语义倒退。
- 注意：**该圆角不影响 README 的「卡片 8px / 控件 6px / 胶囊 999px」三分法**，因为铁律约束的是这三类**容器**的圆角，而非所有矩形元素。`Sparkline` 的 `strokeLinecap: round`（`ui.jsx:233`）是先例——图表内元素的圆角同样不受三分法约束。

**填充比例裁决：4 段等分（25% / 50% / 75% / 100%），不按分数比例。**

> **这不是「易读 vs 真实」的二选一，而是「这个度量到底测什么」的问题。**

选**等分**，理由是**三层否决「按比例」**：

1. **按比例会造出「绩效分」的读法（决定性理由）**：分数 1 / 2 / 3 / 5 / 6 / 9 若按比例画，**条长各不相同**，人眼立刻开始**横向量化比较**（「他的条比我长 40%」）。而需求 F.7 明确禁止跨人比较。等分后「3 分」的人**在两个人身上长得一模一样**，比较的对象就只剩「档位」这个**已经过聚合的离散档**——比较颗粒度被主动粗化，这正是我们想要的。
2. **按比例在低分区不可读**：`none`=0 与 `emerging`=1（占比约 11%）在 64px 轨道上是 7px vs 0px，一个 1px 的差别；而 `established`(5) 与 `authoritative`(6) 又几乎无差。**说好的「1 分和 2 分几乎看不出差别」，其实最糟的是 0 和 1。** 等分把 4 档拉成 4 个等宽的视觉台阶，**每一档都有清晰的视觉增量**。
3. **本组件的语义是「档」，不是「量」**：`MaturityAxis` 展示的是 D.2 的 `none/emerging/established/authoritative` 四档**封装结果**，不是原始加权分。原始分不需要、也不应该出现在这个组件里（它属于「佐证充分度的计算过程」，个人页只在放大态以 `3/9 条` 这样的**回望计数**形式出现，且那是**条数**不是分数）。**等分就是忠实渲染「4 档」这件事本身。**

**等分丢失了什么（诚实记录）**：丢失了「同一档内 3 分 vs 5 分」的差别。**这个丢失是刻意的**——它恰好阻止了跨人比较，并且 3 与 5 的分野在同档内本来就不该被强调（它们都属于「有稳定的产出」）。

**补偿：档位文案必须有**。`none/emerging/established/authoritative` 对应「暂无实证 / 有初步产出 / 有稳定的产出 / 有沉淀与影响力」，13px `c.text2`，跟在条右侧 gap 8px（紧凑态）/ 10px（放大态）。**文案是这一档的准确定义，它承载了等分丢掉的文字精度。**

### B.3 两行的对齐与等宽数字的使用

**三段左对齐基线（关键：标签名 / 自评行 / 实证行三者共用一条左基线）**

```
 L1  标签名          x=0   （13px/500, ink）
 L2  点阵 第一点      x=0   ← 点阵左边缘 = 标签名左边缘
 L3  "兴趣" 轴标      x=0   （10px, text3）
 L4  实证条 轨道左端   x=0   ← 实证条轨道左边缘 = 标签名左边缘
```

- **裁决：自评点阵与实证条都从 `x=0` 起排，两者左对齐（不是「点阵在左、条在右」错位）。**
  - 唯一例外是**放大态**：放大态因为要放「兴趣 / 实证」两个行首标签，采用**两列制**：列 1（行首轴标）宽 **40px** 固定，列 2（图形 + 文案）从 `x=40+12=52px` 起排，**两条的图形左边缘严格对齐在 x=52**。紧凑态**不设行首标签**（空间不够），改为把「兴趣/实证」放在图形**下方** 10px `c.text3`，仍从 `x=0` 起排。
- **宽度关系**：
  - 紧凑态：点阵 40px / 实证条 64px，**两者不等宽**。这是可接受的，因为它们**不是同一刻度的两种画法**（B.0 的核心就是要它们读起来不同源）。
  - **它们各自的宽度必须跨标签严格恒定**（40 / 64），这样矩阵里多张标签卡的「点阵右端」与「条右端」各自成列。**严禁按文案长度自适应宽度。**
- **点阵与实证条的垂直间距**：**6px**（紧凑态）/ **8px**（放大态）。间距必须**小于**标签卡之间的间距（TagMatrix 内为 12px），否则「同一标签的两行」会与「相邻两个标签」产生相同的呼吸感，读不出分组。

**等宽数字（`dp-mono` / `dp-num`）用在哪几处 —— 共 3 处，且仅这 3 处：**

| 位置 | 类名 | 理由 |
|------|------|------|
| 放大态的「**3/9 条**」回望计数 | `dp-num` | 数字。既有规约「指标值一律 tabular-nums」。`3/9` 里的 `/` 是分隔符，整体用 mono 使数字列对齐 |
| 放大态的「**近 12 月**」时间窗说明 | `dp-mono` | 含数字 12，且它是**技术性标注**（口径声明），mono 强化「这是系统算的」的观感 |
| 实证条下方（可选）的「**N 条**」历史计数 | `dp-num` | 数字。仅在个人页放大态显示 |

**严禁用在**：标签名本身（中文标签名**必须走 `fontSans`**——Roboto Mono 不含中文字形，会触发中文回退，破坏「数字 mono、中文 sans」的可预期切分）、档位文案（「有稳定的产出」是中文短语不是数值）、自评级别文案（「主动投入」同理）。

### B.4 吹牛态（自评高 / 实证 0）的完整样式

**触发条件**：`selfRating >= 3（practicing 及以上）` **且** `evidenceTier === 'none'`。
> 阈值取 ≥3 的理由：`curious`/`following` 是「还在看」的诚实低自评，实证为 0 完全正常，**不该被标记**；只有「在项目中用过 / 主动投入」这种**强主张**配 0 实证，才是需求 C.4 第 3 道闸要透明化的对象。**这避免把吹牛标记泛化成「新人标记」。**

| 元素 | 规格 |
|------|------|
| 实证条轨道 | **虚线描边**：`border: 1px dashed c.dashedBorder`，`background: transparent`，`border-radius: 999px`，高 6px（紧凑）/ 8px（放大），宽 64px / 160px（与常态**同宽同高**，不缩不涨） |
| 虚线样式 | `dashed 1px`，段长接近浏览器默认（约 3px on / 3px off）。**不用 `dotted`**——点线会与自评的圆点阵产生形状呼应，强化「两者同源」的误读 |
| 条内填充 | **无**。它是**空槽**，不是「0% 填充」。空格子 = 「格子在那儿，但里面没有东西」 |
| 跟随文案 | 「**暂无实证 · 仅自评**」 —— 字号 **12px**（紧凑）/ **13px**（放大），颜色 `c.text3` `#667085`，位于条右侧 gap 8px / 10px |
| 一级提示行 | 「**该标签暂无公开贡献佐证**」 —— 字号 **11px**，颜色 `c.text3`，位于**标签卡底部**，上方 padding-top **6px**，与上方内容之间用 `1px solid c.border` 分隔线（复用 `KpiTile` 的 note 区范式，`ui.jsx:200`） |
| 点阵 | **正常渲染，不灰化、不加删除线、不降透明度**。自评是用户的真实意愿表达，**UI 不为它道歉** |
| 卡片边框 | **不变**（仍是 `1px solid c.border`）。不加红色左边框、不加警告底、不加任何「异常」暗示 |

**为什么「暂无实证 · 仅自评」用 `text3` 而不是 `text2`**：`text3` `#667085` 在 `surface #FFFFFF` 上对比度约 **5.06:1**，过 AA；`textDisabled #B3B7B9` 只有 **2.04:1**，被 README 明确禁止承载正文。**用 `text3` 表达「次级但可读」的信息位**——这条提示是**必须被读到的诚实话**，不能弱化到看不见（弱化到看不见就成了「隐藏」，违反需求 D.3 「不隐藏」）。

**尺寸与位置的具体值（紧凑态）**：
```
标签卡 padding: 12px 14px
  L1 标签名        13px / 500 / line-height 1.4
  ↕ 4px
  L2 点阵 + 文案    高 12px
  ↕ 6px
  L3 实证条 + 文案   高 12px（条 6px 垂直居中）
  ↕ 6px  + 1px 分隔线 + 6px
  L4 提示行        11px / text3 / line-height 1.5
```

### B.5 尺寸变体裁决 —— **需要两档**

**裁决：两档，命名 `MaturityAxis`（紧凑态）与 `MaturityAxis variant="expanded"`（放大态）。**

| 维度 | 紧凑态（默认） | 放大态（`variant="expanded"`） |
|------|--------------|---------------------------|
| **使用场景** | `TagMatrix` 内每个标签卡 | **个人页头部的「主标签」区**（≤3 个） |
| 点尺寸 / 间距 | 7px / 4px | 11px / 6px |
| 实证条高 / 宽 | 6px / 64px | 8px / 160px |
| 标签名字号 | 13px / 500 | 15px / 500 |
| 档位文案字号 | 13px | 15px |
| 行首轴标（兴趣/实证） | 无，改置于图形下方 10px | 有，左列 40px 固定 |
| 文案位置 | 图形右侧 gap 8px | 图形右侧 gap 10px |
| 卡片内边距 | 12px 14px | 16px 18px |
| 回望计数「历史贡献 N 条」 | 不显示 | 显示（`dp-num`，12px，`text3`） |
| 一级提示行 | 显示（11px） | 显示（12px） |

**为什么必须两档，而不是一档缩放**：
- 矩阵里可能有 9 个标签（需求 C.2 合计上限），**必须紧凑**，否则 9 个标签要横跨 3 屏，矩阵的「一屏看全」价值消失；
- 主标签是**页头的身份标识**（「这个人是做 RAG 的」），**必须够大**才能承担「第一眼认人」的职责；
- **但不能做三档**：三档会让「哪一档该用在哪」变成实现者的自由裁量，进而导致同一产品内不一致。**两档是「扫读」与「认读」两种读取模式的最小充分集。**

**两档必须共用同一套 4 档色值、同一套文案、同一个 4 点阵逻辑** —— 变体只改**尺寸**，**绝不改变语义**。这是设计系统的纪律：变体改变的是**呈现密度**，不是**含义**。

### B.6 hover 态裁决 —— **无浮层，原地静态展开**

**裁决：有 hover 态，但 hover 不做浮层 tooltip，改为「原地补全文案」。**

**否决 chart tooltip 式浮层的两条理由（都来自既有规约）**：
1. README「已知取舍」明确「图表无 hover 十字线与 tooltip」——这是本门户的**既有取舍**，引入浮层会造成同产品内两套核查范式；
2. 更实质的：**浮层承载的信息在无障碍与触屏上都不可达**。需求 E.2 的「闭环验收」要求「实证档位 ≥1 则贡献列表必须有 ≥1 条带该标签映射的条目」——**这条约束要能被用户现场核验**，藏在浮层里等于把核验入口藏起来。触屏上更是永远拿不到。

**hover 的具体行为（紧凑态，矩阵内）**：

| 触发 | 行为 |
|------|------|
| hover 标签卡 | 卡片沿用 `.dp-card--hover` 抬升（`global.css:110`，边框转 `brandBorder` + `shadowRaised`）——**复用既有，不新造 hover 语汇** |
| hover 时文案变化 | 档位文案从「有稳定的产出」**追加** `· 近 12 月 3 条`（同一行内追加，`text3` 12px，不换行；空间不足时整块 `text-overflow: ellipsis`） |
| hover 时实证条 | **不变**（不加高亮、不加描边）。hover 是「可点」的暗示，不是「数据被强调」——**若 hover 时条变色，会制造「数据随鼠标变化」的假象** |
| 卡片 `cursor` | `pointer`（标签卡可点 → 跳 `#/workspace/tags/:tagId` 反查） |
| 键盘 | `role="button"` + `tabindex="0"` + Enter/Space，`:focus-visible` 环用 `2px solid c.brand` `outline-offset: 2px`（**与 `.dp-card[role='button']:focus-visible` 既有规则一致，`global.css:564-568`**） |

**放大态的 hover**：**无变化**。主标签区是身份展示，不可点、不交互。**显式记录：放大态卡片不加 `dp-card--hover`、不设 `cursor: pointer`。**

> **放弃了什么**：放弃了「hover 显示完整分数明细（3 分 = 1 篇最佳实践×3 + 1 条项目动态×2）」的浮层。**理由**：分数明细属于 D.2 的算法过程，而需求 F.7 禁止「打分可视化」。把加权分算给用户看，等于把「佐证充分度」重新变回「分数」。**正确做法是让用户去「近期知识贡献」列表看条目**（那里每条都标注了「→ 标签名」，是人可读的证据，不是分）。这条是**主动放弃信息**，以守住「不是绩效分」的语义边界。

## C. `TagChip` 组件规范

### C.1 与既有 `Pill` 的关系裁决 —— **新建 `TagChip`，与 `Pill` 并列，不扩展 `Pill`**

**裁决：新建独立组件，但复用 `.dp-chip` 类与 `ChannelTag` 的中性画法。**

**为什么扩展 `Pill` 是错的**：
1. **语义域不同**。`Pill` 的 `semantic` 参数（`ui.jsx:11`）绑定 `SEMANTIC` 映射表，其值域是 `success/warning/error/info/neutral`——**它的输入语义是「运行状态」**。硬塞 `axis='domain'` 会让一个组件的 prop 同时承载两套不相关的语义系统，日后 `SEMANTIC` 一改就可能连带影响标签渲染。**这是耦合，不是复用。**
2. **形状语汇不同**。`Pill` 的 `dot` 是**实心圆点**（`ui.jsx:29`，6px 圆），而标签的轴前缀是**菱形几何符**（A.1）。若扩展 `Pill`，就要给它加第二套 prefix 形状，`Pill` 会长成一个「什么都能装」的通用容器。
3. **README 铁律的边界**：「变更类型胶囊为中性灰，不占用语义色」——这条**正是为了防止 `Pill` 被滥用**。`TagChip` 的领域轴用**品牌蓝**（不是语义色），它天然不属于 `SEMANTIC`，所以**它本来就不该走 `Pill` 的通道**。

**复用什么（具体到行）**：
- **复用 `.dp-chip` CSS 类**（`global.css:603-613`：`height 22px / padding 0 10px / radius 999px / font-size 12px / gap 4px / nowrap`）——**这是既有的 chip 基座，不新造**；
- **复用 `ChannelTag` 的画法**（`ui.jsx:43-57`：`page` 底 + `border` 描边 + `text2` 字）作为**能力轴 chip 的样式**——直接调 `ChannelTag` 亦可，但为了一处集中管理轴逻辑，建议在 `TagChip` 内部复用同样的三色取值；
- **复用 `YellowMark` 的「小面积强调」思路**（`ui.jsx:60`）作为**主标签**的处理（但**不用黄色**，见 C.3）。

### C.2 两条轴的 chip 视觉区分

| 属性 | 领域轴（Domain） | 能力类型轴（Capability） |
|------|----------------|----------------------|
| 底色 | `c.brandSubtle` `#EEF0FB` | `c.page` `#F5F4F5` |
| 描边 | `1px solid c.brandBorder` `#C3C9F0` | `1px solid c.border` `#E1E0DF` |
| 文字色 | `c.brand` `#3643BA` | `c.text2` `#616161` |
| 字重 | **500** | **400**（比领域轻，让领域更前） |
| 前缀符 | **`◈`** `U+25C8` | **`◇`** `U+25C7` |
| 高度 | 22px | 22px |
| 内边距 | `0 10px` | `0 10px` |
| 圆角 | 999px | 999px |
| 字号 | 12px | 12px |

**对比度校验（WCAG AA，正文 12px 属小字，要求 ≥4.5:1）**：

| 组合 | 对比度 | 判定 |
|------|--------|------|
| `brand #3643BA` on `brandSubtle #EEF0FB` | **8.9:1** | ✅ AAA |
| `text2 #616161` on `page #F5F4F5` | **6.8:1** | ✅ AA |

两者均过 AA。**注意 `brand` on `brandSubtle` 的对比度高于 `text2` on `page` 约 2.1 倍**——这恰好与「领域轴视觉权重更高」的意图一致，是**有意的**，不是巧合。

### C.3 主标签 vs 普通标签

**裁决：主标签 = 同款 chip + 品牌蓝描边加粗 + 前缀符升级，不用黄、不用填充反白。**

| 属性 | 普通标签 | **主标签** |
|------|---------|-----------|
| 底色 | 轴底色 | **轴底色不变**（保持轴的可辨识性！） |
| 描边 | `1px solid` 轴描边色 | **`1.5px solid c.brand`** `#3643BA` |
| 文字色 | 轴文字色 | 轴文字色不变 |
| 字重 | 500 / 400 | **统一 500** |
| 前缀符 | `◈` / `◇` | **`◆`** `U+25C6` / **`◈`**（实心化，形状升级） |
| 高度 | 22px | **24px** |
| 内边距 | `0 10px` | `0 12px` |
| 角标（可选） | 无 | **右侧 `主` 字标**：9px / 500 / `c.brand` / `margin-left 4px` / 不设底色 |

**为什么主标签不用品牌黄**：README 铁律「品牌黄 `#FFCD4E` **仅**小面积标记（置顶 / 里程碑 / NEW / 顶栏通知徽标）」——这四类都是**时间性、事件性**的标记。主标签是**长期属性**，两者语义不同。**若主标签用黄，用户会把「这人是主标签」误读成「这个标签是新的/被置顶的」**，且会**稀释黄色「新鲜/重要时刻」的既有语义**。

**为什么主标签不反白填充（蓝底白字）**：反白会赋予主标签**过高的视觉优先级**，与同屏的 `Pill`（语义状态，也是浅底深字）争夺注意力；且反白 chip 在密集区会形成**色块噪音**，与需求 A 节「避免散成一片胶囊噪音」的调性直接冲突。

**为什么用「描边加粗 + 符号实心化 + 高度 24px」三重升级**：因为它需要**在不改变色相、不反白的前提下**被识别为「更重要」。三重升级各自贡献约 1/3 的辨识度，且**任意一重在色盲/低质量屏幕上失效时，另外两重仍能工作**。

### C.4 `TagChip` 的四种状态

| 状态 | 触发 | 样式 |
|------|------|------|
| **active**（默认） | `status: 'active'` | C.2 规格 |
| **已停用**（deprecated） | `status: 'deprecated'` | ① 底色 `c.page`，描边 `1px dashed c.dashedBorder`，文字 `c.text3`；② 前缀符**去掉**（不再声称轴属性）；③ 后缀加 `已停用` 三字标：10px / `c.text3` / `margin-left 4px` / 前有 1px `c.border` 竖分隔；④ **保留原轴底色的一丝痕迹** —— 描边色从轴色向 `dashedBorder` 混合不可实现，故改为**在左端保留一个 3px 宽的轴色竖条**（`border-left: 3px solid` 轴色，圆角由 `border-radius: 999px 999px 999px 999px` 配合 `overflow: hidden` 裁切）。**目的：历史引用仍能看出它原本属于哪条轴。**<br>⑤ **整条 `opacity` 不变、不加删除线**——删除线会读成「这条被撤销了」，而它只是「不再可选」 |
| **已合并**（merged） | `status: 'merged'` | ① 主体渲染 **`mergedInto` 指向的 target 的 active chip**（即看起来就是新词）；② 紧跟一个角标「**原『旧名』**」：11px / `c.text3` / `c.page` 底 / `c.border` 描边 / 999px / 高 18px / `padding 0 8px` / `margin-left 4px`；③ **target 是否被任何显示上下文锚定，都不影响该角标出现**——合并必须**永远**可见（可审计性），不做「hover 才显示」 |
| **disabled**（不可选，词表浏览页里被排除的） | 用户在个人页编辑态但已达数量上限时的**其他**可选词 | 底色 `c.page`，描边 `1px solid c.border`，文字 `c.textDisabled` `#B3B7B9`，`cursor: not-allowed`。<br>**`textDisabled` 用在这里是合规的**——它是**禁用态**，而 README 禁止的是「`textDisabled` 做正文」。禁用 chip 的文字属于禁用态装饰，**且它旁边永远有上限说明文字兜底可读性**。 |

**「已停用」的虚线 vs 吹牛态的虚线**：两处都用 `dashed`，**这是刻意的统一**——它们表达同一件事：「**这里缺少实质内容**」。「已停用」缺的是「有效状态」，吹牛态缺的是「佐证」。**同一个视觉元素表达同一个抽象概念（空缺），是本设计系统的内部一致性。**

### C.5 「→ 标签名」联动标注（贡献列表用）

用于需求 E.2 的正向联动：贡献列表每条标注它喂养了哪个标签。

**规格**：
- 结构：`→` 符号 + 该标签的 active chip
- `→` 符号：`U+2192`，**12px**，颜色 `c.text3`，与 chip 之间 gap **4px**，与前置内容之间 gap **8px**
- chip：**用 C.2 的领域轴 chip 规格**（因为映射目标都是领域轴标签，见需求 D.2 第 2 条「映射到领域轴标签」）
- 整块（`→` + chip）**不可点**（贡献条目本身可点跳详情，联动标注是**说明**不是**入口**）——**若可点，用户会以为点它去反查页，而实际会跳文章详情，产生误操作**
- 位置：贡献条目的**第二行**，紧跟元信息之后（`margin-top: 4px`）
- **`→` 必须用 `fontSans` 而不是 `fontMono`**：它两侧都是中文 chip，mono 的箭头与中文基线不齐

## D. `TagMatrix` 布局规范

### D.1 栅格与响应式重排

**裁决：优先复用既有的 `.dp-grid` + `.dp-g*` 范式，不新造栅格类。**

**结构**：
```
TagMatrix = Panel（既有原子）
  └─ PanelHead（title="标签" desc="领域标签 5 · 能力标签 4" extra=「近 12 月实证 3 条」）
  └─ Panel body
       └─ 两个分区（域分区 / 能力分区），纵向堆叠
            └─ 分区 = 分区标题条（cardHeadBg）+ .dp-grid 网格
                 └─ 网格内 = 多张标签卡（每张卡内有 MaturityAxis 紧凑态）
```

**列数裁决**：

| 容器宽度 | 网格类 | 列数 | 卡宽（估算，卡片 body padding 16px×2，卡间 gap 16px） |
|---------|--------|------|------------------------------------------|
| ≥1240px（左栏宽约 780px） | `.dp-grid .dp-g3` | **3** | ≈ 240px |
| 901–1239px | `.dp-grid .dp-g2` | **2** | ≈ 250–330px |
| ≤900px（单列） | `.dp-grid .dp-g2` 在 900 断点塌成 1 列 | **2 → 1** | — |

**为什么选 `dp-g3` 而不是 `dp-g4`**：`.dp-g4` 在 ≤1240px 会先塌到 2 列（`global.css:433`），而个人页**左栏本身已经是窄栏**（见 E.1，约 780px）。若用 `dp-g4`，在 1240px 视口左栏约 700px，4 列每列仅 160px，**无法容纳 64px 实证条 + 3 字档位文案**。`dp-g3` 在 1240px 给出 ≈ 220px/列，够用。

**⚠️ 重要：`.dp-g2/.dp-g3/.dp-g4` 已经在 ≤900px 统一塌成单列**（`global.css:437-448`），**这正与需求「≤900px 单列」精确吻合，因此不需要写任何新的媒体查询**。这是复用既有范式的直接收益。

**卡片的两个关键约束**：
1. **`align-items: start`**（不是默认的 `stretch`）——**必须显式声明**。理由见 D.3。
2. 卡片之间 gap 用 `.dp-grid` 的既有 `gap: 16px`，**不改**。

### D.2 两轴分区之间的分隔方式裁决 —— **卡片内分节（单 Panel），不拆两块 Panel**

**裁决：一个 `Panel`，内部分两个 section。**

**理由（三条，按权重）**：
1. **两轴是「一个人的两个属性维度」，不是两份数据。** 拆成两块 Panel，每个 Panel 都有 `PanelHead`（标题 + 分隔线），在视觉上会变成「两个独立的资料块」——用户会开始想「这两块之间是什么关系？」，而正确答案是「它们同属一个人，且**必须并排看**」（需求 D.3 的核心）。**两块 Panel 会把这个关系变成需要解释的问题。**
2. **空间**：个人页左栏要同时容纳页头、能力分布概览、标签矩阵、近期贡献。两块 Panel 各自吃掉一个 `PanelHead`（14px 上下 padding + 16px 字号行高 ≈ 48px）**，白吃掉约 50px 垂直空间**，而标签卡本身只要 12px padding。
3. **需求 E.1 的表格把「标签矩阵」列为**一个** P0 模块** —— 拆两块会破坏这个信息架构的原子性，下游按模块实现与测试时会与需求对不上。

**分区内的具体分隔（不新造「分隔符」，靠层级 + 底色 + 间距三分法）**：

| 手段 | 规格 |
|------|------|
| **分区标题条** | 高 **32px**，`background: c.cardHeadBg` `#FAFAFA`，`border-radius: 6px`（控件圆角，因为它是**块级控件**），文字 13px / 500 / `c.text2`，左 padding 10px；右侧跟同轴 chip 数量的小字（11px `c.text3`），如「领域 5」 |
| 分区间距 | 两分区之间 **20px**（大于卡间 gap 16px，使「分区」比「卡片」更松） |
| 分区内部 | 标题条与网格之间 **10px**；网格内 gap **12px**（**注意：此处覆盖 `.dp-grid` 的 16px，改为 12px**——因为标签卡比常规卡片小，16px 会显得松散。**实现方式：在 TagMatrix 内的网格上用内联 `style={{gap: 12}}`，或新增 `.dp-grid--tight` 类。建议后者，避免内联无法被媒体查询覆盖的坑**） |
| **不使用** | ❌ 水平分隔线（`1px solid border`）——既有系统中分隔线只用于 `PanelHead` 下沿与 `ContentMeta`，用于「数据分区」会与卡片边界产生同级竞争<br>❌ 分区左侧竖强调条——那是需求提交页大卡的语汇（`global.css:496` 注释提到 4px 强调条） |

**分区顺序**：**领域轴在上，能力轴在下。** 理由：需求 B 节明确「用户搜『谁懂 RAG』找的是碰过这个对象的人，这是领域查询不是能力查询」——领域轴是**主查询轴**。且领域轴词表更大（45–60 vs 24–32），放上面符合「多者在前」的阅读惯性。

**分区的空态**：某轴无标签时，**分区不消失**，标题条仍在，标题条下方显示一行 12px `c.text3`：「暂无领域标签」。保留分区的理由是**结构一致性**——两个分区恒定存在，用户不会因为「这次看到一个分区」而误以为「这个系统只有一个维度」。

### D.3 标签数量悬殊的版式不塌方案

**问题**：甲有 9 个标签（领域 5 + 能力 4），乙只有 2 个（领域 2 + 能力 0）。

**四条保证**：

1. **`align-items: start`（关键）**：绝不能 `stretch`。若 `stretch`，乙的那 2 张卡会被拉伸成和甲一样高——**卡片高度不一，但内容是「两行点阵 + 一行文案」，被拉高后卡片内部会出现大段空白，读起来像「信息缺失」**。
2. **卡片高度由内容决定，且内容高度恒定**：标签卡的内容 = 标签名（1 行）+ 点阵行 + 实证行 + （可选）提示行。**标签名统一限高 1 行**（`white-space: nowrap` + `overflow: hidden` + `text-overflow: ellipsis`）——中文标签名最长 8 字（「供应链数字化」），紧凑态列宽 ≥220px 时 13px 字号可容 13 字，**不会截断**；即便如此仍显式声明 nowrap + ellipsis 作为兜底。
   > **为什么强制单行而不是允许换行**：换行会让部分卡片高 24px，导致同一行卡片**底部参差**，破坏矩阵的「可竖扫」特性。
3. **空位不补占位符**：网格是自然的流式布局，甲 5 个占 3+2，乙 2 个占 2。**绝不插入「空白占位卡」或「+ 添加标签」卡去填满行**——空白卡会制造「他是不是缺标签」的错觉，而「+ 添加」是编辑态的入口，在浏览态出现是误导。
4. **两个分区各自独立成网格**：领域分区的列数与能力分区的列数**相同**（都用 `dp-g3`），这保证**同一列的两张卡左右对齐**，即使中间隔着一个分区标题条。**这是「单 Panel 双分区」相比「两块 Panel」的另一个技术收益**：两块独立 Panel 的宽度可能因内部内容撑开而失配。

**视觉验证（甲 9 / 乙 2）**：
```
甲（9 个）                          乙（2 个）
┌──────── 领域 5 ────────┐        ┌──────── 领域 2 ────────┐
│ [卡][卡][卡]           │        │ [卡][卡]              │
│ [卡][卡]               │        │                       │  ← 第 2 行空着，不补占位
├──────── 能力 4 ────────┤        ├──────── 能力 0 ────────┤
│ [卡][卡][卡]           │        │ 暂无能力标签           │  ← 分区保留 + 空态文案
│ [卡]                   │        │                       │
└────────────────────────┘        └───────────────────────┘
两个 Panel 高度不同，但内部列宽一致 → 不塌
```

### D.4 空态（一个人一个标签都没有）

**裁决：`Panel` 内用自建 `PageEmpty` 的「轻量变体」——不新增组件，给 `PageEmpty` 加一个 `compact` 布尔参数。**

| 属性 | 规格 |
|------|------|
| 方案 | `<Panel><PageEmpty compact title="暂无标签" desc="…" /></Panel>` |
| 为什么不用 antd `Result` | README 铁律：`Result` 的 `status=404/403/500` 会强制渲染内置**彩色插画**并忽略传入 `icon`，违反 ds-04「禁用彩色插画图标」。**且冒烟测试已有断言锁定「未使用 antd `Result` 内置插画」**——用了会直接挂测试 |
| 为什么给 `PageEmpty` 加 `compact` 而不是新建 | `PageEmpty` 当前 padding 是 `72px 24px`（`ui.jsx:322`），那是**页面级**留白。卡片内用会**撑出一屏空白**。`compact` 变体：`padding: 28px 16px`，`BrandSymbol size=36`（默认 56），标题字号 **16px**（默认 20px），desc **13px**（默认 14px），`marginTop` 相应缩到 14 / 8px。**这是纯尺寸变体，不是新组件——符合「变体只改尺寸不改语义」的纪律** |
| 文案 | 标题「**暂无标签**」；desc「该成员尚未选择任何标签。」+ 第二句「标签用于让同事找到你的领域与能力——可在**组织速查**里发起补充。」（`13px c.text2`，`line-height 1.75`，`maxWidth 460px`） |
| 两轴分区 | **过空态时两个分区都不渲染**（整体替换为 PageEmpty）。理由：整人为空时，再显示「领域 0 / 能力 0」两个空分区标题条是**噪音**，与 D.2 的「分区恒在」不冲突——D.2 说的是「轴有标签、另一轴没有」的情况，这里说的是**完全无标签**，属于不同层级 |
| extra | 不放按钮。**无登录态原型里没有「添加标签」的真实入口**，放假按钮会产生死链 |

**「无头像体系」的裁决（回答你的问题）**：
> **`InitialAvatar` 与「无头像体系」不冲突。确认，理由如下。**
> README 的原文是「**无登录鉴权**：无头像、无个人中心、无我的订阅、无已读态」。**这四条是同一件事的同位语**——它们描述的是「**当前登录用户**」这个概念不存在：没有「我的头像」、没有「我的个人中心」、没有「我订阅的」、没有「我已读的」。
> 而 `InitialAvatar` 是**别人的姓名首字色块**：中性灰底 + 描边 + 首字（`ui.jsx:271-293`，注释「中性灰底，无头像菜单 / 无已读态」）。**它不加载图片、不上传、不代表登录身份、右侧挂不出「个人中心/退出登录」菜单**。它是**姓名的一个图形化缩写**，与 `ContentMeta` 里的人名是同一类信息，只是换了个载体。
> **判据：如果 `InitialAvatar` 冲突，那么 `ContentMeta` 里的「内容负责人：郑远」也冲突**——两者都是「渲染别人是谁」。显然不冲突。**真正被禁止的是「当前用户身份」这个概念，不是「可视化一个人」这个能力。**
> **但有一条必须守住**：个人页上**不得出现任何「编辑我的资料」「这是我的页面」的暗示**。页头不放「编辑」按钮，不放「关注」，不放「设为常用」。**页头是只读的第三人称视图。** 由于无登录态，我们**也无法知道**当前用户是谁，所有个人页一视同仁——这反而是最干净的实现。

### E.2 标签反查页 `#/workspace/tags`

**为什么用 `Segmented` 做轴切换**：
- 已有 `global.css:594-600` 的 `.ant-segmented` 胶囊化样式（999px + 2px padding），是**既有已验证的形态**；
- 三选项（全部 / 领域轴 / 能力类型轴）正好在 `Segmented` 的舒适区间；
- **不用 `Tabs`**：`Tabs` 是**频道级**子导航语汇（README「两层结构：顶栏一级 + 分区 Tabs 子导航」），在筛选器里用会**与频道导航争抢语义**；
- **不用 antd `Select` 做轴选择**：`Select` 是下拉，会把三个选项藏起来，而轴是本页**最重要的一级筛选**，必须常驻可见。

**为什么词选择用「自建 chip 组」而不是 `Select` 多选**：
1. **需求 B 节的核心是「两轴正交，用户心智是二维的」**。而字面展示全部词表，用户能**看到另一个轴的全部选项**，这本身就是**对双轴模型的界面教育**——「哦，原来 AI 是领域，架构是能力」。
2. 受限词表（78 词封顶）**规模可控**，全展开不会失控。且**分域分组分行**后是 9 行，高度约 9×(24+8) ≈ 290px，可接受。**若未来词表超过 120，再改为 `Select` + 搜索**（在规范里写清这个触发条件）。
3. **`Select` 多选的下拉面板会盖住结果区**，每次选词都要开关一次面板，**核对结果的成本高**。chip 组原地多选，**结果列表实时更新且始终可见**。
4. **不用 antd `Tag.CheckableTag`**：需要轴色区分 + 分组 + 已选态三套样式，`checkable` 的选中态是品牌蓝底白字（反白），**与 C.3「主标签不反白」的原则不一致**，且反白选中态在密集区噪音大。**自建 chip 的选中态统一用「描边加粗 + 深色 1px 内阴影」表达**（见下）。

**chip 组的具体规格**：
| 状态 | 样式 |
|------|------|
| 未选 | C.2 的轴 chip 规格（领域蓝底 / 能力灰底），`cursor: pointer` |
| **已选** | 底色加深一档（领域 → `c.brandStep1`；能力 → `c.page` 保持）+ **`box-shadow: inset 0 0 0 1.5px 轴色`** + 前缀符实心化（`◈`→`◆`）+ 后端加 `×` 移除符（12px，`margin-left 2px`，`c.text3`） |
| 达到结果为空 | 未变（不做「无结果」态）。结果列表区显示空态 |
| hover | `border-color` 转轴色（领域 `c.brand` / 能力 `c.text2`），**不加阴影、不抬升**（批量筛选器里大量 chip，抬升会晃） |

**已选条**：筛选器 Panel 底部，上方 `1px solid c.border` 分隔；显示已选 chips（**按选择顺序**，不是按词表顺序——用户记得自己的操作顺序）；右侧 `<Button type="link" size="small">清空</Button>`（品牌蓝链接态，既有主题已配 `colorLink`）。**已选条只在有选择时出现**（无选择时不占位，避免空条）。

**结果列表行的规格（复用 `.dp-row`，`global.css:320`）**：
- 行高 `min-height: 56px`（既有），但本页行内是**两行内容**，故实际渲染高度约 **72px**（`padding: 8px 12px` + 内容自适应；`.dp-row` 是 `min-height` 所以能长高）。
- 左侧 `InitialAvatar size={32}`（既有默认）
- 主列：姓名（**15px / 500 / `c.ink`**）+ `dept · role`（12px `c.text3`）
- 副列（标签）：该人与**当前筛选匹配的标签** chips（**只显示命中的标签**，最多 4 个，超出显示 `+N`）；每个 chip 后跟**迷你成熟度**（点阵 5px 点 / 3px gap + 实证条 4px 高 × 36px 宽）
  > **注意：迷你态是第三种尺寸，但它只是「矩阵紧凑态」的等比缩小**（点 7→5、条 64→36），**语义完全一致，只丢文案**（56px 行高放不下档位文案）。**不做工具提示、不做浮层**——用户点进个人页看完整信息。若觉得三档太多，**可退化为：结果列表只显示 chips、不显示成熟度**（`+N` 后结束），点进去再看。**我倾向退化为不显示成熟度**，理由：反查页的职责是「**找人**」，成熟度是「**判断人**」，两步分开更清爽，也避开「同一个人在两处显示不同成熟度尺寸」的一致性问题。**最终裁决：结果列表不显示成熟度，只显示命中的标签 chips + `+N`。**
- 整行 `role="button"` + `tabindex="0"` + Enter/Space（既有键盘可达范式），`:focus-visible` 由既有 `.dp-row:focus-visible` 规则覆盖（`global.css:565`）
- 排序：**按姓名排序，不做任何基于实证度的排序**（F.7 禁止跨人比较）。PanelHead 的 `desc` 写「3 人 · 按姓名排序」——**主动声明无排序偏置**，这是「不排名」这一约束的可见证据。

**≤900px 重排**：
- 筛选器 Panel：仍是一个 Panel，chip 组的 9 行自然堆叠（每行 chip 会 wrap 成多行）。**分区名（「AI 与智能」）在 ≤900px 改为上方独立一行**（13px `c.text3`），chip 组在其下——因窄屏下「分区名 + chips」同行会让 chips 只剩 100px 宽。
- 结果列表：`.dp-row` 的内容改为纵向堆叠（姓名行 / 标签行），`min-height` 放开。
- 页头 `SectionTitle` 的 `extra` 落到标题下方。
- **`Segmented` 保持一行**（三项 + 每项 2 字，375px 下约 210px，可容）。
