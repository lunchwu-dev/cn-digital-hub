## 二、致命问题

### F1｜盘点表声称"没有遗漏实体"，但门户有 3 处内容域完全不在 mock.js 里

**证据**：
- 文档第 53 行断言：*"34 个实体 = 13 生产域（28 个实体）+ 9 派生域……**没有遗漏实体**"*。
- 但实际 grep 结果（`^export const` in mock.js）是 **35 个导出**，不是 34——文档连自己的分母都数错了（见 F3）。
- 更严重的是：门户里有 3 处内容域**根本不来自 mock.js**，而是硬编码在组件里：
  1. **顶栏通知列表**（`portal/src/components/TopBar.jsx:34-38`，`const NOTICES = [...]`，3 条通知 + "近 7 天 · 3 条"计数）。文档通篇未提。TopBar 自己写明"通知中心为原型示意，接入消息服务后开放"——这正是**一个待裁定的数据源**，却不在 22 个域的清单里。
  2. **首次访问引导 TOUR_STEPS**（`portal/src/App.jsx:25-42`，4 步引导文案）。这是随版本维护的门户自带内容，无人负责、不在清单。
  3. **门户元信息之外的水印/页脚披露文案**：水印来自 `META.watermark`（已盘点为 P06），页脚"本原型所有数据均为示意数据 · 非真实运行值""内部系统 · 请勿外传"是 `App.jsx:187-188` 硬编码——这类"门户自述文案"是上线后必须删改的配置项，文档未涉及。

**影响**：文档的标题就是"**完整**设计所有数据源"，且一页结论第 1 条明确宣称"没有遗漏实体"。通知域尤其关键——它是产品方案里"订阅与通知机制"落二期的直接指向物，若不在本期盘点表，二期接手时这一格就是空的（`04-delivery-notes.md:215` 那条教训："分工里谁都以为别人会验的格子，那个格子一定是空的"）。

**修复处方**：
1. 在 A-2 派生域后新增一节 **A-3「界面内嵌、非 mock 供给的内容域」**，至少列入：`NOTICES`（通知列表）、`TOUR_STEPS`（引导文案）、页脚披露文案。每个给出承载位置（文件:行号）。
2. 对通知域裁定：建议标 **M5 派生/外部代理**（来自待建的消息服务，本期为占位），Owner 待定；引导文案标 **M4 极低频人工**，Owner 归门户 Owner（周敏）。
3. 删除或改写"没有遗漏实体"这句结论——它现在是不成立的。改为"mock.js 的导出已全覆盖；另补充 3 处非 mock 内容域"。

### F2｜§一页结论第 2 条与 D01 的定性**直接自相矛盾**，且方案没意识到

**证据**：
- 文档第 12 行（一页结论）：*"**没有任何一个内容域适合「纯手工维护但日更」**"*。
- 文档第 25 行（D01 表）：公告与决议，"变更频率 **高频（日级，事件驱动）**"，C 节裁定 **M4 全人工**。

M4 定义（B-1）="必须人工撰写与维护，无结构化源可依"，人工介入点="全流程"。所以 D01 = "纯手工维护 + 日级" = **正是一页结论宣称"没有任何一个内容域适合"的那种组合**。文档自己造了一个反例，又把它放在 A-1 第一行。

**这暴露的真实问题**：作者实际想说的是"**日更义务**"（定期定量产出）与"**事件驱动**"（有事才发）是两回事——公告是后者，所以人工可持续。**但这个关键区分，方案通篇没有讲清楚**。第 12 行说的是"日更"，D01 栏写的是"高频（日级）"，两个词被混用，读者（尤其是执行工程师）会得出"公告要每天人工发"的错误结论。

**影响**：一个自我矛盾的结论句会把整份文档的可信度拉低；工程师按字面执行会误判公告的运营负担。

**修复处方**：
1. 把第 12 行改写为：*"没有任何一个内容域适合'纯手工维护且**有定量日更义务**'。日更只允许出现在自动域；人工域的内容产出必须是**事件驱动**（有事才发），而非'每天必须发 N 条'。"*
2. 在 B-1 模式的"变更频率"维度里，把 **"频率"细分为「触发方式」**两列：`事件驱动` vs `节律驱动`。D01/D02/D04 均为事件/节点驱动，D05–D07 为节律驱动。这样"高频"不再被误读为"日更义务"。
3. 在 D01 行补一句限定："高频"指事件到达频率，非产出义务。

## 三、重要问题

### I1｜决策树 Q3 的"M2 **或** M3"不是结论——框架在最高频的边界案例上给不出答案

**证据**：B-2 决策树 Q3（文档 86-88 行）："需要人的判断 → **M2 或 M3**"。
**实测 `projectUpdates`**（文档 120 行自己也承认这是边界）：Q1 有权威源（Jira/Meego）→ Q2 有 API → Q3 **需要判断**（"评审结论""PoC 进入第 2 阶段"）→ 得到"M2 **或** M3"。
**问题**："或"不是结论，是把决策推回给读者。而 M2（填链接自动抓取）与 M3（人写正文+系统补字段）的实现路径、工作量、Owner 责任完全不同。

**修复处方**：Q3 的"是"分支必须再问一层，给出可判定的判据。建议改为：
```
Q3 需要人的判断？
 └─ 是 → Q3b：判断所需的**正文**是否已在某个系统里写好了？
          ├─ 是（源系统里已有这段文字，只是要搬过来）→ M2（抓链接/ID）
          └─ 否（门户是第一撰写地，源系统没有这段文字）→ M3（人写）
```
用此判据复测：`projectUpdates` 的进展正文通常**首先写在门户/手工表**，Jira 只有状态 → 应得 **M3**（唯一解），文档的"M3 半自动"结论恰好正确，但**是被猜对的，不是框架推出来的**。

### I2｜探活悖论未被覆盖："探活失败 ≠ 服务挂了"

**证据**：D07/D12 都主张用探活得状态。E-1 第 2 条（171 行）**提到了**"要区分'服务挂了'还是'探活脚本挂了'"，但**只在风险段落提，没进框架**。
**实测 `toolGroups.status` 的探活脚本自身挂掉**：按现有 B-2 决策树，Q3 不需要判断 → M1 全自动。但 M1 的"全自动"给出了一个**假信号**（脚本挂了却显示"正常/离线"）。框架没有"未知态"这一档。

**修复处方**：在 B-1 模式谱系中为所有 M1 探活类增加一个**必备状态维度**：`success / warning / error / **unknown(探活失联)**`。并在 D07 行注明：`stabilityItems` 的 `status` 枚举当前只有 `success/warning/error`（mock.js:452-457），**缺少 `unknown`**——落地时必须扩展，否则探活脚本挂掉时门户会显示上一个已知状态，等于说谎。这条要写进 E 节的风险对策，不能只留在"多数团队会低估"的泛泛之谈里。

### I3｜M2 的前提条件被高估："填链接自动抓取"对需登录的源站不成立

**证据**：C 节 D10b（127 行）、D10 设计链接走 M2。E-2（179 行）只提了"链接腐烂（源站改版）"，**没提"源站需登录"**。
**实测**：`designLinks` 里 `dl-01` 是"设计令牌（Figma Variables）"（mock.js:587），`dl-02` 是组件库。Figma、语雀、Confluence、Jira **几乎全部需要登录鉴权**才能读取内容——无登录的 M2 抓取对它们是**不成立**的。而门户明确"无登录鉴权"（E-3）。

**修复处方**：
1. 在 M2 定义（B-1）里加**前提条件**："M2 仅适用于**匿名可访问**的源页面；需登录的源只能走 (a) 服务端持凭据代抓 或 (b) 降级为纯跳转（M4 目录 + 外链）"。
2. D10b 的"确定"信心等级应下调为"**待验证**"，并进 D 节问题：新增 **Q8「设计资产/知识库源站是否支持匿名只读或服务端代抓？」**。
3. E-2 表格新增一行失败形态："**M2 抓取撞登录墙** —— 无法匿名访问，抓取永远返回登录页，解析出空内容"。

### I4｜"信心等级"标注的"待验证"项，与 D 节问题**不能一一对应**

**证据**：C 节标"待验证"的域 = D02、D03、D04、D05、D06、D07、D13（共 7 处）。D 节问题 = Q1–Q7（7 条）。
**逐条映射**：Q1→D02、Q2→D05/06/07、Q3→D03/04、Q4→D13。**D10b 的 M2 前提（I3）无处对应**（这是我要新增 Q8 的理由）；另有一个反向悬空——
- **D04 里程碑**：C 节标"待验证"，理由是"挂到项目管理系统同一项目下自动同步状态"。D 节**没有一条问题直接问"里程碑的权威源是什么"**——它被隐含在 Q3（Jira/Meego）里，但里程碑（产品路线图节点）与项目进度（Jira issue）**未必同源**。

**修复处方**：把 C 节每个"待验证"标注后**加括号引用问题号**（如"D02 待验证（见 Q1）"），并在 D 节末尾加一句自查："以下待验证项暂无对应问题：___"。当前应填：D04（部分悬空）、D10b（见 I3）。补 Q8、Q9 后归零。

### I5｜P01 待补队列的依赖闭环是断的：反馈数据"从哪来、存哪、谁保证不丢"三问全空

**证据**：P01（43 行）=「由 FAQ 反馈 + Agent 兜底提问事件计算」。E-2（180 行）承认"采集 ≠ 闭环"。
**实测（这是最硬的代码证据）**：`portal/src/pages/Knowledge.jsx:196-211` 的 `markHelpful`——点"没帮到我"时，只做了 `setBacklog(...)`（**组件内 useState 局部状态**）和弹 toast。`faqs` 里的 `helpful/notHelpful` 计数（mock.js:600-601 等，如 `helpful:46`）是**静态值，点多少次都不变**；刷新页面 backlog 全部丢失；**没有落库、没有 localStorage、没有任何持久化**。`store.js` 仅被 App.jsx 用于记 tour 是否看过（App.jsx:126/149），与反馈无关。
**也就是说**：P01 的"负反馈事件"在当前实现里**根本不存在**——它是一个纯 UI 幻觉。文档把 P01 定为"确定"信心，但它依赖的源头是空的。

**修复处方**：
1. P01 信心从"确定"下调为"**待建设**"，并在 A-2 表格"数据来源"列写明具体的**采集契约**：事件名、字段（`faqId, helpful:bool, ts, dept?`）、存储位置（建议 `feedback_events` 表或埋点平台）、保留期。
2. 在 D11 行（FAQ 复合模式）补明反馈计数的**写入路径**：`faqs.helpful/notHelpful` 必须由反馈事件**聚合回写**，而非人工维护——当前 mock 是静态值，落地时这是**必改项**。
3. E-2"反馈闭环断裂"补充对策：明确"**反馈写入 → 计数聚合 → 待补队列 → Owner 认领 → 关闭**"五步各自的 Owner，否则仍是只进不出。

### I6｜交付给工程师的文档**没有任何工作量/工期区间**——这是致命缺失（按执行标准）

**证据**：D 节问题表（150-162 行）对每个"有 API → M1"的分支只描述**形态**（"走 M1，可做版本时间线"），**无一个数字**（人天、周、S/M/L）。E-1 提到了"多数团队会低估工作量"（171 行）却没给量。
**为什么致命**：本文档的产品方案原文（`03-product-solution.md:229`）把这里定义为"**本期最大成本变量**"。一份自称覆盖"最大成本变量"的方案，却无法回答"最大成本是多少"。工程师拿到手无法排期，主理人汇编时也无法回答甲方"要多久"。

**修复处方**：
1. D 节每条问题表的"设计分支"列**增加一列工作量的粗估区间**（S ≤3 人天 / M 1–2 周 / L 3–5 周 / XL >5 周），给出**判定依据**（如"M1 直连 Grafana 只读 API：L——含联调、权限、指标口径对齐"）。
2. 在 C 节末尾或新增 F 节，给一个**总工作量区间表**（最乐观/最悲观两列，随 Q1–Q4 答案浮动）。哪怕给"锚点"（如"全部 M1 打通 ≈ 6–10 周"）也远胜于零。
3. 明确一期 MVP 的**集成预算上限**，并标出超出上限时砍哪些域。

## 四、建议改进

### A1｜Q1 关键问题：`opsCharts` 含 `series`/`x` 数组，与 E-3"只拉聚合 L1"的边界表述不能自洽（对应审查问题 Q10）
文档 E-3（186 行）说"只拉聚合后的 L1 指标，不拉原始时序明细"。但 `opsCharts.availability.series`（mock.js:419-423）是**三条 7 点序列**，`opsKpis.spark` 是 **7 日七点序列**（mock.js:349）——这是**时间维度明细**，不是单点聚合值。
**建议**：把边界表述精确到"**只拉按天/小时粒度的聚合序列，不拉秒级/请求级原始点位**"，并在 D06 行注明序列粒度（7 点/日 = 按天聚合）。否则工程师会以为"只读 1 个标量接口"，实现时发现还要拉序列，工作量翻倍。

### A2｜`agentReplies` 定性为"M5 派生"会误导实现者（对应审查问题 Q11）
**证据**：mock.js:1019-1045 的 `agentReplies` 是**手写的 `match:['sso','单点',...]` → 固定 `text`** 映射表。它没有任何"从 D09/D10/D11 抽取"的自动机制。
**问题**：定性为"M5 派生"暗示"知识库更新后 Agent 回复自动跟着变"，但当前实现是**人工配置的关键词-文本对**。
**建议**：改为双态表述——**MVP 阶段：M4 人工配置**（关键词→文本，须与 FAQ 对齐措辞）；**二期接 LLM：M5 派生**。否则实现的工程师会以为不用维护这张表。

### A3｜`pinnedResolutions` 与 `announcements` 的字段差异说明"两种内容"（对应审查问题 Q3）
**证据**：`pinnedResolutions`（mock.js:20-47）有 `meeting` / `effective` / `body` / `pinned`；`announcements`（172-222）没有，只有 `feature/isNew/channel/date/tags`。二者内容有重叠（an-002 是 Q3 积分决议的摘要版，pinnedResolutions[0] 是同一决议的完整版），但**形状不同**。
**建议**：在 A-1 的 D01 行补一句：该域实为**两个视图/两种内容形态**——"公告"（事件通知，`announcements`）与"决议"（评审产出，带 `meeting/effective/body`，`pinnedResolutions`）。**同一 Owner 可以，但要说明决议的权威源是"技术评审会记录"**，其 `effective` 日期驱动 E 节提到的"7–30 天自动归档"。

### A4｜E-3 已正确约束身份类数据源，但应显式点名 `orgPeople` 的 email 字段
