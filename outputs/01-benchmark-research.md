# 调研底稿 01 · 外部标杆与本议题可迁移的结论

> 主理人（画统筹）整理，用于支撑迪卡侬中国 Digital 公告栏的产品方案。
> 三路调研：① 企业内部门户/公告栏 IA ② 内部开发者门户（IDP）范式 ③ 观测性看板与企业内 AI 助手。

---

## 一、结论前置：四条可迁移的判断

| # | 结论 | 对公告栏的直接含义 |
|---|------|-------------------|
| 1 | **门户失败的首要原因不是功能少，而是"内容没归属、没生命周期"** | 10 个模块必须每个都指定 Owner 与更新节律，否则半年后必然荒废 |
| 2 | **"公告"是分层结构，不是一长串列表** | 公告区必须做"重点区 + 一般列表"两层，而不是时间倒序平铺 |
| 3 | **工具导航的正确形态是"服务目录"而非"链接墙"** | 每个工具要有：用途、Owner、SLA/状态、申请入口——这是 Backstage 的核心洞察 |
| 4 | **实时看板要分层，且不要试图在门户里做重型监控** | 门户里放 L1（SLO / 错误预算 / 健康度），下钻回 Grafana 等专业工具 |

## 二、企业内部门户 / 公告栏（Intranet & EIP）

**标杆做法**

- **公告版面分层**：重点公告用大卡片/图文区承载（必读、制度变更、系统维护），日常公告走下方列表 + 分类 + 日期。同一份内容可在首页跑马灯、区块轮播、弹窗等不同版型复用（一次维护、多处呈现）。
- **导航的七类要素**：全局横向导航、局部导航、移动端快捷链接条、工具类导航（设置/个人资料/收藏）、动态导航（按用户组或订阅高亮）、橱窗式导航（页面内链接/按钮）、面包屑。
- **三次点击原则**：如果用户三次点击内找不到目标内容，IA 就需要迭代。
- **治理三件套**（最容易被忽略、也最决定成败）：
  - 命名规范（页面/频道/文件夹统一规则）
  - 内容模板（政策公告、团队介绍、项目报告等标准模板）
  - 元数据强制字段（标签、内容所有者、最后审阅日期）
- **角色定义**：内容所有者（对准确性/及时性负责）、站点管理员（结构/权限）、审批人（政策与合规类发布前审批）。
- **内容瘦身经验值**：成熟门户改造平均可裁掉 60–80% 的页面（某跨国企业从 900 页压到 250 页）。
- **公告的管控维度**：可见范围（全员/部门/岗位/个人）、责任归属（责任部门/责任人）、留存周期（7–30 天临时 / 1 年 / 永久归档）。这三项是公告区别于群消息的本质。

**对本项目的启示**

- 公告栏要解决的"高时效信息离散"，本质是把**非正式渠道（IM/邮件）的传播**替换为**正式渠道的可追溯分发**。因此"已读/触达"与"归档检索"是刚需，不是加分项。
- 10 个模块平铺是反模式。应按**用户任务**而不是**内容来源**来分区。

## 三、内部开发者门户（Spotify Backstage / Spotify Portal）

**它解决的痛点与本议题高度同构**：工程师找不到东西、每个新项目从零开始、标准无人遵守、隐性知识永远是隐性的。

**核心构件（可映射到公告栏）**

| Backstage 构件 | 作用 | 映射到公告栏 |
|---|---|---|
| Software Catalog | 所有服务/API/资源一个可搜索目录，**带明确 Owner**、依赖图、技术标准 | → 模块 8「常用入口/工具导航」应做成「工具与服务目录」 |
| TechDocs | docs-as-code，文档与代码同仓，集中渲染 | → 模块 6「最佳实践」的长文承载形态 |
| Soundcheck | 把工程标准编码成自动检查与指引 | → 模块 3「体验与设计规范」的**可执行化**（检查清单/自动校验，而不只是文档） |
| Scaffolder / Templates | 从标准化起点一键起项目，零重复零漂移 | → 模块 10「需求提交入口」的进阶形态 |
| AiKA (Engineering Intelligence) | 建在目录上下文之上的 AI 知识助手 | → 模块 9「Agent for Digital」 |
| Insights | 跟踪平台采用率 | → 公告栏自身的运营指标 |

**关键洞察**：门户的价值密度 = **上下文基础设施**（谁拥有什么、依赖是什么、标准在哪）的完整度。语言模型时代的 Agent 之所以能干活，前提也是这层上下文存在。所以**先做目录与元数据，再做 Agent**——顺序不能反。

**同行价格锚点**：Spotify Portal 商用版 12 个月合约 $35,000 起。自建的成本优势明显，但治理成本不可低估。

## 四、观测性看板（SRE / Observability）

**分层模型（从宏观到微观）**

- **L1 Executive**：SLO / SLI / Error Budget —— 回答"系统是否够好"
- **L2 Service**：RED 模式（Rate / Errors / Duration）—— 回答"哪个服务出问题"
- **L3 Infrastructure**：USE 模式（Utilization / Saturation / Errors）—— 回答"哪台机器/哪个资源瓶颈"

**硬规则（反模式 vs 实践）**

| 反模式 | 实践 |
|---|---|
| 满屏同等权重的图表 | 用大字号/大色块突出 SLO 状态 |
| 把所有指标塞进一屏 | 按逻辑分组，用变量做下钻 |
| 随意配色 | 语义化配色：**只有异常时才用红色** |
| 展示平均延迟 | 展示 P50/P95/P99 或延迟热力图（平均值会掩盖长尾） |
| 单页超过 20 个 panel | 每块看板 5–7 个关键 panel，深挖链接到次级看板 |
| 实时查原始高基数数据 | 预聚合（Recording Rules） |

**对本项目的启示（重要取舍）**

- 公告栏里的监控区**不应该**是运维值班看板，而应该是**面向部门全员的 L1 健康视图**：核心系统可用性、SLO 达成率、错误预算余量、当班/责任人。
- 正确的做法是**门户做 L1 概览 + 一键下钻到专业监控系统**，而不是把 Grafana 嵌进来。嵌入内容技术上脆弱、视觉上割裂、维护上双份。
- 复用迪卡侬既有的**绿 = 正常 / 黄 = 预警 / 红 = 异常**语义，且**不要**与股市"红涨绿跌"的约定混用（本项目是运维语义，不涉及行情）。

## 五、企业内 AI 助手（Agent for Digital）

**可参考的量化收益（同业公开案例）**

- 某工业企业上线内部知识 Agent 后：3 个月内内部支持请求减少 **68%**，**92%** 用户能在 60 秒内找到信息，新人上手周期缩短 **45%**，用户满意度 **87%**。
- 北陆电力（PKSHA AI Helpdesk）：在 Teams 内提供服务，并用**有人应答日志反哺自动生成新 FAQ**。
- 某互联网企业 HR 问答 Agent：咨询响应从平均 48 小时降到 15 分钟，HR 事务性工作占比从 70% 降至 35%。

**落地路径（四条共识）**

1. **分阶段**：单部门试点 → 打通协作工具 → 跨部门扩展 → 反馈闭环自学习。不要一次全铺开。
2. **必须给来源**：RAG + 原文引用是信任的基础，无溯源的答案在企业场景不可用。
3. **必须接实时数据**：纯静态知识库会迅速过时，Agent 需要能查实时业务数据（如项目进度、系统状态）。
4. **反馈闭环是命脉**：负反馈 → 知识缺口识别 → 内容补齐，这个循环跑不起来，Agent 三个月就废。

**已知短板（要提前设计对策）**：领域深度不足、答案可解释性差、动态数据融合不足。

**对本项目的启示**

- 模块 9 的正确设计是 **「结构化 FAQ（高质量种子）+ Agent（对话入口）+ 反馈闭环（缺口回流）」三位一体**，而不是"放一个聊天框"。
- **Agent 是 FAQ 的消费端，也是 FAQ 的生产端**——用户问了但答不好的问题，应该自动进入"待补知识"队列，指派给对应 Owner。这是公告栏从"静态知识库"升级为"活知识系统"的关键机制。
- 因此 Agent 的 **MVP 门槛不是模型能力，而是它有没有可检索的知识底座**。知识底座 = 模块 1/3/4/5/6 的沉淀物。这也再次说明：**内容先于 Agent**。

## 六、给设计阶段的三个硬约束（我会写进给下游的交接单）

1. **每个模块必须有 Owner 与更新节律**，界面上要可见（"内容负责人 / 最后更新"），这是防荒废的唯一手段。
2. **信息架构按用户任务分区，不按内容来源平铺**；首页必须能回答"现在最重要的事是什么"。
3. **实时数据与 AI 能力都走"概览 + 下钻"**，门户不做重型嵌入；MVP 阶段用入口聚合而非原生实现。
