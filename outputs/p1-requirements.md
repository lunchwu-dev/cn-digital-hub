## B. 标签体系的维度模型（核心裁决）

### B.1 一句话结论

**采用「2 条正交轴」模型：`领域轴（Domain）` × `能力类型轴（Capability）`，二者都是扁平一级维度（不做二级）。** 而不是「一长串扁平标签列表」，也不是「领域 + 子领域」的树。

- **领域轴（Domain）= 业务 / 技术对象**：AI、供应链、门店、会员增长、电商、数据平台、平台与安全…
- **能力类型轴（Capability）= 你在这个领域里干什么**：工程技术、产品设计、项目管理、数据工程、设计系统…

一个标签 = **（领域 × 能力类型）的一个落点，但标签本身只归属其中一轴**。例如「RAG」→ 领域轴（AI 领域下的技术对象），「提示词工程」→ 领域轴（AI），「系统架构」→ 能力类型轴（工程技术）。

### B.2 真问题 1：「技术栈」与「AI 领域」必然重叠 —— 明确裁决

**问题**：RAG、Agent、向量检索这类词，既像「技术栈」又像「AI 领域」，不裁决就会同屏出现两次。

**裁决规则（三层，按顺序执行）：**

> **规则 R1（对象优先）**：一个标签若**指向一个具体技术对象/系统/算法**（RAG、Agent、向量检索、SSO、埋点、电子价签），它归 **领域轴**。理由：对象是「被作用的客体」，用户搜「谁懂 RAG」时找的是「碰过这个对象的人」，这是领域查询不是能力查询。
>
> **规则 R2（动作优先）**：一个标签若描述**一种可迁移的做法/能力/方法**（系统架构、性能优化、需求拆解、A/B 实验设计），它归 **能力类型轴**。理由：这类能力跨领域复用，绑死在某一领域会造成大量重复词。
>
> **规则 R3（互斥闸门）**：**同一个词字符串只能存在于一条轴**（靠全局 `TAG_DICT` 的唯一 id 保证，不允许两条轴的候选词表出现同名字符串）。若一个词同时满足 R1 和 R2（如「模型微调」既是算法对象又是工程动作），**以 R1 为准归领域轴**，能力类型轴只保留「模型工程」这样的上位动作词——**宁可领域轴多一个词，也不允许一词两处**。

因此最终形态：**「技术栈领域」不作为独立维度存在**，它被拆解为「领域轴里的技术对象词」+「能力类型轴里的工程动作词」。「AI 领域」是**领域轴下的一个域分组**，其中的「RAG / Agent / 向量检索」是领域标签，**不会**再在别处出现。

> **放弃了什么**：放弃了「技术栈」作为独立维度的直觉命名。代价是领域轴会比较大（见 C 节数基）；收益是彻底消灭重叠，用户不会看到同一能力两处冒头。

### B.3 真问题 2：一条「领域」轴 + 一条「能力类型」轴 —— 判断与理由

**判断：采用双轴，不采用扁平多维列表。**

| 方案 | 判断 | 理由 |
|------|------|------|
| A. 扁平多维度列表（技术/AI/产品/项目管理平铺） | ❌ 否决 | 维度语义不齐（AI 是业务领域，项目管理是角色），平铺后无法解释「为什么 RAG 和项目管理是并列的」；且筛选器无从组织，反查页会做成一坨 chip 墙。 |
| B. 领域 × 能力类型 双轴 | ✅ **采纳** | 两轴**正交且语义同质**：领域回答「做什么对象」，能力回答「以什么方式做」。用户的心智模型天然是二维的——「我要找**懂 RAG 的**（领域）**后端**（能力）」。反查页因此可以做「领域筛选 × 能力筛选」交叉，而不是一列平铺。 |
| C. 单轴大词表 | ❌ 否决 | 词表会爆炸到 100+，且无法支持交叉筛选，违背本次核心诉求「谁懂 RAG」。 |

> **放弃了什么**：放弃了「一条轴最简单」的工程便利。双轴需要数据模型支持 `{ axis, domainGroup }`，但这是本次核心价值所在，值得。

### B.4 真问题 3：维度数量与层级

**裁决：一级维度 = 2 条轴（领域 / 能力类型）；每条轴内部用「域分组（Domain Group）」做**无层级感的视觉分组**，不做二级标签节点的树。**

- 领域轴：4–5 个**域分组**（AI 与智能、业务系统域、数据域、平台与基础设施、组织与流程域）。分组**只是词表归类标签**，**不是可选的标签**——用户选的是域分组里的具体词，不选分组本身。
- 能力类型轴：3–4 个**能力族**（工程技术、产品与设计、数据与分析、项目管理与协作）。同样只做归类，不可选。
- **不做二级的理由**：二级标签会让「谁懂 AI」这种粗粒度反查落空（必须点到二级才有人），且维护成本指数上升。**分组用于 UI 折叠与词表组织，不参与检索层级**。
- **爆炸控制**：见 C 节，词表总量封顶，靠「受限词表 + 管理员维护」硬控，不靠用户自律。

### B.5 真问题 4：管理学维度（产品设计 / 项目管理）是否适合做「标签」

**裁决：**
- **产品设计 → 适合，归「能力类型轴 / 产品与设计族」。** 它是可迁移的**能力**（写 PRD、拆需求、画流程、做 A/B 实验），跨领域复用，适合做标签。
- **项目管理 → 部分适合，需拆分：**
  - 「**项目管理**」这个纯职责词 **不作为能力标签**（它是角色，人人都有，标签失去区分度）。
  - 但拆出的**具体动作**「**需求拆解与排期**」「**跨团队协同**」「**里程碑管理**」**可以作为能力标签**，因为它描述可辨识的做法而非头衔。
- **判据**：**「角色」让人人都是，标签要让人人不同。** 与 `orgPeople.role` 字段重复的职责描述（「产品经理」「技术负责人」）**一律不做标签**——角色已经有专门的字段承载，标签只承载「能力/领域」，两者不交叉。这条同时是 C 节防注水的第一道闸。

> **放弃了什么**：放弃了「项目管理」作为一个大标签的直观性。代价是用户可能要选 2–3 个动作词；收益是标签有区分度，反查页有意义。

## C. 标签的数基与生命周期

### C.1 候选词表数基（量级建议）

| 轴 | 域分组 / 能力族 | 候选词量级 | 说明 |
|----|----------------|-----------|------|
| 领域轴 | 5 组 | **合计 45–60** | AI 与智能 8–10、业务系统域 12–14、数据域 8–10、平台与基础设施 8–10、组织与流程域 6–8 |
| 能力类型轴 | 4 族 | **合计 24–32** | 工程技术 8–10、产品与设计 6–8、数据与分析 5–6、项目管理与协作 5–6 |
| **合计** | 2 轴 / 9 组 | **约 70–90 词** | 这是**全量词表**上限，不是人均。受限词表，管理员维护。 |

> 量级依据：现有 10 人样本的人均真实极值约 4–6 个标签，70–90 词表可支撑数十人规模且允许长尾覆盖。**词表封顶 90，超过必须先合并再新增**（见 C.3）。

### C.2 单人每个维度的标签数量上限

- **领域轴：每人不超 5 个。**
- **能力类型轴：每人不超 4 个。**
- **合计上限 9 个**，且**「主标签」不超过 3 个**（主标签在个人页头部高亮、进入标签反查页的一级展示）。

**理由**：上限是**防注水的结构性闸门**，比在下游做算法降权更有效。5+4 让每人必须取舍，标签才有信息量。**放弃了「不限量让用户自由表达」**——受限词表 + 硬上限是本次已拍板方向（决策 2）的自然延伸。

### C.3 新增 / 废弃 / 合并机制（管理员维护）

标签字典（`TAG_DICT`）每条记录：`{ id, label, axis, group, status, aliases[], createdAt, mergedInto }`。

| 操作 | 规则 |
|------|------|
| **新增** | 仅管理员。需指定 axis + group，并**通过 R1/R2/R3 唯一性校验**（与现有词字符串/别名查重）。直接落 `status: 'active'`。**硬约束：本次不设「待审核（pending）」中间态**——成员只能在现成词表里选，想要新词一律走管理员手动新增。词表的 `status` 枚举**收敛为 `active / deprecated / merged` 三态，不得扩展**。（G.1 已由用户拍板为「甲」。） |
| **废弃（deprecate）** | 保留记录，`status: 'deprecated'`，**从新选择列表中消失**，但**历史引用仍渲染**（灰显 + 「已停用」）。**禁止物理删除**——否则历史个人页会出现空洞。 |
| **合并（merge）** | 保留被并词记录，写 `mergedInto: <targetId>`，`status: 'merged'`。**历史数据不重写**，改为**渲染期解析**：遇到 merged 标签，显示 target 的 label + 「原『旧名』」角标。这样合并是**无损、可逆**的（把 `mergedInto` 清空即回滚）。 |

> **关键决策：历史数据用「渲染期重定向」而不是「数据迁移重写」。** 理由：① 原型无后端，重写 mock 不可持续；② 可逆、可审计；③ 合并语义对用户透明（他看到的永远是最新词 + 出处）。**放弃了「一次性迁移脚本」**——对当前无后端架构是过度工程。

### C.4 防注水（自评兴趣度允许自主填报前提下的滥用防护）

四道闸，从结构到行为：

1. **词表闸**（最强）：受限词表 + 唯一性校验，无法自造新词博眼球。
2. **数量闸**：C.2 的 5+4 / 主标签 ≤3 硬上限。
3. **双轴互证闸**（本次核心）：**自评兴趣度高但没有对应实证度时，UI 不隐藏、但主动标记为「仅自评」**（见 D.3）。让「吹牛」在视觉上有成本，靠同侪透明而非惩罚。
4. **变更留痕闸**：自评标签每次变更记录 `updatedAt` + 变更人，个人页显示「标签更新于 X 天前」。**频繁刷标签的人**在组织速查里会表现为「标签常年变动」，形成软性社会约束。

> **放弃了什么**：放弃了「管理员审批每个人的每次标签变更」的重流程。理由：10–数十人规模，审批成本 > 收益；透明 + 结构约束已足够。（注：用户已拍板本次不做任何用户侧审批态，见 C.3；若规模显著扩大再议。）

## D. 双轴成熟度的具体定义（核心）

### D.1 自评兴趣度（Self-Rated Interest）

**4 级**（刻意用**偶数**，逼用户在两端做取舍，避免无脑选中间「3/5」）：

| 级别 | id | 文案口径（措辞是「兴趣/意愿」，不是能力） | 说明 |
|------|----|-------------------------------------------|------|
| 1 | `curious` | **有点好奇** —— 想了解，还没深入 | 最低 |
| 2 | `following` | **持续关注** —— 看得多，偶尔动手 | |
| 3 | `practicing` | **在项目中用过** —— 有实战，愿意深入 | |
| 4 | `advocating` | **主动投入** —— 长期投入，乐意带人 / 分享 | 最高 |

> **措辞纪律**：**全程不出现「擅长 / 精通 / 掌握 / 熟练」**——那是能力词，会与实证度语义打架。四级全部落在「兴趣—投入—意愿」语义域。这是决策 1「两条都显示」能否自洽的前提。

### D.2 实证度（Evidence Score）—— 可落现有 mock 的算分规则

**数据源**（全部来自现有 mock，不新增数据）：

| 证据类型 | 字段 | 权重 | 备注 |
|---------|------|------|------|
| 知识贡献 · 最佳实践 | `bestPractices.author` | **3** | 裸名，最高价值（沉淀了可复用知识） |
| 知识贡献 · 文章 | `articles.*.author` | **3** | 裸名（与 bestPractices 有重叠，见下方去重） |
| 项目动态负责 | `projectUpdates.owner` | **2** | 「组 · 姓名」需解析 |
| 公告 / 决议负责 | `announcements.owner` | **2** | 「组 · 姓名」需解析 |
| Release 负责 | `releaseNotes.owner` | **1** | 裸名，频次高、单条价值低 |

**算分（对某个人的某个标签）：**

1. **解析 owner/author → 人员**：
   - 若为「组 · 姓名」→ 取 `·` 后姓名去空格；
   - 若为裸名 → 直接匹配 `orgPeople.name`；
   - **未匹配到 orgPeople 的（如「周立」）→ 不计入任何个人，但计入部门级总数**（幽灵贡献者不入个人页，避免虚假归属）。
2. **贡献条目 → 标签的关联**：条目的 `tags` / `category`（如 `bestPractices.category: '供应链'`、`announcements.tags: ['门店']`）映射到领域轴标签。映射表由**管理员在词表的 `aliases` 里维护**（如 `供应链` → `供应链数字化` 这个领域标签）。
3. **单标签实证分** = Σ（该人**带此标签映射**的证据条目 × 权重）。
4. **分档（4 档，与自评对齐）**：

| 档 | id | 阈值（加权分） | 文案 |
|----|----|--------------|------|
| 0 | `none` | 0 | **暂无实证** |
| 1 | `emerging` | 1–2 | 有初步产出 |
| 2 | `established` | 3–5 | 有稳定的产出 |
| 3 | `authoritative` | ≥ 6 | 有沉淀与影响力 |

> 阈值依据：现有 10 人样本里，`郑远` 有 1 篇最佳实践(3) + 1 条项目动态(2) = 5 → `established`；`何嘉` 有 1 篇最佳实践(3) + 1 条公告(2) = 5 → `established`。样本分布可自然落在 1–3 档，阈值可达性经过实测校验。

### D.3 两条轴如何同时显示而不打架 + 吹牛的表达

**显示形态：双行并排的「双轴条」，而不是叠成一个分数。**

```
领域 · AI
  兴趣   ●●●○  主动投入        ← 自评（描边圆点，品牌蓝）
  实证   ▓▓▓░  有稳定的产出    ← 实证（实心填充条，中性灰→品牌蓝）
```

- **视觉区分靠「形状 + 色彩语义」而非数值**：自评用**圆形点阵**（表达主观、可任意填），实证用**矩形填充条**（表达客观、由系统算）。形状不同 → 用户不会误把两者相加。
- **自评高但实证为零（吹牛）**：UI **不隐藏、不降权、不报警**，而是**诚实并列**：
  ```
  兴趣   ●●●●  主动投入
  实证   ░░░░  暂无实证 · 仅自评        ← 灰字 + 虚线描边，明确「这条只有你自己说的」
  ```
  并在个人页该标签卡右下角给一行中性提示：「**该标签暂无公开贡献佐证**」。**用透明替代惩罚**——这既是诚实表达，也是 C.4 的防注水闸门。
- **实证高但自评低**：同样诚实显示，且**反向提示**「系统检测到你有该领域贡献，是否更新兴趣？」——把实证当作**自评的召回入口**。

> **放弃了什么**：放弃了「合成一个综合成熟度分」（如「兴趣 0.4 + 实证 0.6」）。理由：决策 1 明确要「两条都显示」，合成会丢失信息且易被理解为绩效；双轴条信息最全，代价是 UI 更重（用户已拍板接受）。

### D.4 实证度的时间衰减与陈旧问题

**引入时间窗，裁决如下：**

- **默认时间窗：近 12 个月**（滚动窗口）。理由：知识贡献的价值半衰期约 1 年，超过则从「当前活跃度」退化为「历史履历」。
- **两段式表达**：
  - **近期实证**（近 12 个月）→ 决定实证度的**当前档位**（D.2 的 4 档）。
  - **历史累计**（12 个月以外）→ 不消失，单独以「**历史贡献 N 条**」回望计数展示在个人页，**不参与档位计算**。
- **实现**：mock 里所有证据条目**已有 `date` 字段**（`bestPractices.updated`、`announcements.date`、`releaseNotes.date`、`projectUpdates.date`），可直接做窗口过滤，零额外数据。
- **参考基准日：固定常量 `EVIDENCE_AS_OF = '2026-09-17'`（已定案）。** 所有「近 12 个月」窗口一律以该常量为「今天」计算，**不使用运行时真实日期**。该常量**同时是 jsdom 断言的基准**——断言必须能在**任何运行日复现**（若改用真实日期，mock 数据会随时间滑出窗口，实证度将逐日贬值直至归零，断言必然不稳且 demo 崩坏）。

> **放弃了什么**：放弃了「永久累计不衰减」。理由：不衰减会让「很久前写过一篇」的人永远占着最高档，反查页失去「谁现在在行」的价值。

## E. 个人主页的信息架构

### E.1 模块顺序与优先级

> 版式参考既有 `ArticleDetail.jsx`（Breadcrumb + 标题 meta + 主内容 / 侧栏），但个人主页是**左窄右宽的双栏**（标签矩阵为主角）。

| 优先级 | 模块 | 内容 | 版式 |
|--------|------|------|------|
| **P0** | ① **基本信息** | `InitialAvatar` 大头像 + 姓名 + `dept` + `role` + `location` + `email`（`dp-mono`）+ **主标签 ≤3**（品牌蓝高亮） | 页头通栏，Breadcrumb 之上 |
| **P0** | ② **标签矩阵** | 双轴分区（领域轴 / 能力类型轴），每标签一张小卡：标签名 + **双轴成熟度条**（D.3 形态）+ 「仅自评」标记 | 左栏主区（宽），网格排布 |
| **P1** | ③ **近期知识贡献** | 该人作为 `author/owner` 的 `bestPractices` / `articles` / `projectUpdates` / `announcements` / `releaseNotes` 条目列表，**每条标注它喂养了哪个标签**（联动，见 E.2） | 右栏（窄）或标签矩阵下方通栏 |
| **P2** | ④ **能力分布概览** | 一行小结：「领域 N 个 · 能力 M 个 · 近期实证 K 条」+ 可选迷你 `Sparkline`（近 6 月贡献密度） | 标签矩阵顶部或页头右侧 |
| **P2** | ⑤ **协作触点** | 该人负责的工具（`toolGroups.owner` 命中）——「他维护的 Grafana 看板」等 | 右栏底部，可空 |

> **顺序理由**：受众第一动机是「认人 + 判断这人懂什么」→ 基本信息与标签矩阵必须首屏；「近期贡献」是**佐证**，第二位；概览与协作是增强，垫底。**放弃了「贡献列表优先」**——那是内容平台的顺序，不是找人场景的顺序。

### E.2 「近期知识贡献」↔ 标签体系的联动（硬约束）

**联动规则（双向、明确、可断言）：**

> **正向（贡献 → 实证度）**：个人页「近期知识贡献」里的**每一条**，都必须在 UI 上显式标注它贡献给了**哪个标签**（chip：「→ RAG」）。这条标注**不是装饰**，它就是 D.2 实证度的计算来源——个人页上「实证度」的每一分，都能在贡献列表里被追溯到具体条目。
>
> **反向（实证 → 提示）**：当某标签的实证度 > 0 但该人**未自评**该标签时，贡献列表对应条目旁显示提示「**你有一条该领域贡献，可补充兴趣标签**」。
>
> **闭环验收**：个人页上**任一标签的实证档位 ≥1，则「近期知识贡献」区块内必须有 ≥1 条带该标签映射的条目**。（这是设计规约，也是 jsdom 可断言的约束——见 tests 扩展建议。）

这条联动的实现：`bestPractices.category` / `announcements.tags` / `projectUpdates.tags` → 经词表 `aliases` 映射到领域标签 id；贡献列表渲染时反向查映射，输出「→ 标签名」。

### E.3 入口（两条，均必须）

| 入口 | 现状 | 改造 |
|------|------|------|
| **组织速查行** | `OrgView()` 的 antd `Table` 行**不可点**（实测确认） | 给「成员」列加可点单元格，或整行 `onRow` 绑点击 → `go('#/workspace/people/<id>')`。**复用既有键盘可达范式**：`role=button` + `tabindex=0` + Enter/Space（参考 `smoke.cjs` 里 `.dp-row[role="button"][tabindex="0"]` 的既有断言口径）。 |
| **全局搜索人员分组** | `SEARCH_INDEX` **无人员**（实测确认，6 个 group 全不含人） | 在 `buildIndex()` 新增 `orgPeople.forEach` → `{ group: '人员', title: name, desc: dept + ' · ' + role + ' · ' + tags.join('/'), path: '#/workspace/people/' + id, kw: name+dept+role+email+tags }`。分组名「**人员**」，排在最前（找人是最强意图）。 |

### E.4 路由建议（符合 `#/seg/sub/id` 三段式）

| 页面 | 路由 | 符合约定的理由 |

## F. 边界与不做的事（明确不做）

1. **不做登录 / 鉴权体系改造**——沿用现有原型无登录态设定。
2. **不做真实权限控制**——标签可见性一律「部门内公开」，不实现字段级权限。
3. **不做组织架构树 / 汇报关系图**——只做个人主页与标签，不做 org chart。
4. **不做后端 / 真实持久化**——标签与自评仍是 mock 数据 + 前端状态，刷新即回默认（沿用现有 `store.js` 范式）。
5. **不做标签的全文自造（自由输入）**——已拍板受限词表。
6. **不做用户侧标签审批流**——管理员维护，但不做多级审批工作流（见 G.1）。
7. **不做绩效 / 排名 / 打分可视化**——实证度是「佐证充分度」，**不是绩效分**，禁止排行榜、禁止跨人比较排序。
8. **不做标签的自动打标 / ML 推荐**——映射靠管理员 `aliases` 词表，纯规则。
9. **不引入任何新依赖**——不引图表库（沿用 `charts.jsx` 手写 SVG）、不引 router、不引状态库。
10. **不改既有 5 个频道的既有内容与版式**——只做加法（新页面 + 2 处入口增强）。
11. **不破坏现有 53 项 jsdom 断言 + CDP 出图回归**——尤其「导航 5 项」「零硬编码色」「零 console.error」「胶囊签名」。

## G. 三个开放问题 → 已由用户拍板（全部采纳「甲」案）

> 以下三项均已**定案**，不再是开放问题；保留权衡记录仅供回溯。

### G.1 标签新增是否需要「待审核」中间态？—— **定案：不做（甲）**

- **背景**：决策 2 定了「受限词表 + 管理员维护」，但没说**成员申请新词**的路径。
- **权衡**：
  - **甲（不做待审核）**：成员只能在现成词表里选，想要新词只能找管理员。**简单、零新状态、零新 UI**；代价是长尾需求响应慢。
  - **乙（做 `pending` 待审核态）**：成员可提交新词申请 → `status:'pending'` → 管理员审核生效。**响应快、有参与感**；代价是新增一个状态机 + 一个管理员审核 UI（范围扩大）。
- **定案**：**甲**。成员只能在现成词表里选，新词走管理员。`status` 枚举收敛为 **`active / deprecated / merged` 三态，不得扩展**（已落入 C.3 硬约束）。

### G.2 实证度的「时间窗基准日」如何固定？—— **定案：固定常量（甲）**

- **权衡**：
  - **甲**：固定常量 `EVIDENCE_AS_OF = '2026-09-17'`。**稳定、可断言、demo 永远好看**；代价是与真实日期脱节。
  - **乙**：用运行时的真实日期。代价是 mock 滑出 12 个月窗口后实证度全归零、demo 崩坏、断言不稳。
- **定案**：**甲**。`EVIDENCE_AS_OF = '2026-09-17'`，**同时作为 jsdom 断言的基准**，断言必须能在任何运行日复现（已落入 D.4）。

### G.3 个人主页的 id 用「邮箱前缀」还是「拼音姓名」？—— **定案：邮箱前缀（甲）**

- **权衡**：
  - **甲（`email` 前缀，如 `min.zhou`）**：唯一性已验证，URL 友好，零数据改动。
  - **乙（拼音姓名，如 `zhoumin`）**：更可读，但**需新增字段且要处理重名**。
- **定案**：**甲**。`orgPeople` **不新增 id 字段**；在 `mock.js` 导出派生函数 **`personId(email)`**，路由与搜索索引共用（已落入 E.4）。
