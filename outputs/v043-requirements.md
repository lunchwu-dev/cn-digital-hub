**必须向用户澄清的一处（我已给默认值，不停下来等）**：用户说「技能标签卡片不用分组展示」——**「不分组展示」≠「删除分组这一事实」**。详见 §3.2，我建议**去掉分组标题条与分组网格，但保留每张卡上那一行 11px 的分组名小字**。理由：分组名是唯一的「类目上下文」，删了标签就变成一堆无归属的词；且 11px 小字在横排卡上几乎不占屏效，删它换不来屏效、只换来信息缺失。

## 2.【核心】「近期工作内容」板块的数据模型设计

### 2.1 数据源形态：推荐 (a) 独立数据表 `JIRA_ISSUES`

| 方案 | 评价 |
|------|------|
| (a) 独立表 `JIRA_ISSUES`（扁平列表，按人聚合） | **【推荐】** |
| (b) 在 `orgPeople[].workItems[]` 下挂 | 不推荐 |

**推荐 (a) 的理由**：
1. **已有先例且已验证**：`ALL_EVIDENCE = collectEvidence()`（`mock.js:1269`）就是「独立扁平表 + 按 `personName` 聚合」的形态；`getPersonProfile`（`mock.js:1326`）已有成熟的按人过滤逻辑。新增 `JIRA_ISSUES` 走同一模式，**心智负担与实现成本都最低**。
2. **Jira 数据的真实形态就是「issue 为中心」**：一条 issue 天然携带 `assignee`（负责人）字段，而不是「人的属性」。挂到 `orgPeople[].workItems[]` 会**倒置真实关系**——未来若要加「同一 issue 多协作人」「按项目聚合」等视角，人挂任务会立刻掣肘。
3. **`orgPeople` 是「人员花名册」，应保持纯净**：它是路由、搜索索引、组织速查的共用底座（`personById`、`personId` 都依赖它）。往里塞动态业务数据会污染「静态花名册」的语义，也让 `getPersonProfile` 的演化成本变高（要同时处理 person 与 tasks）。

**但必须遵守一条纪律**：issuse 的 `assignee` 用 **`personId`（email 前缀）** 关联，**不是姓名**。理由：`orgPeople` 里姓名是中文、可能重名，而 `personId` 是全仓唯一径（`mock.js:1002`）。**绝不重蹈 `ALL_EVIDENCE` 用 `personName` + `parseOwnerName` 字符串匹配的覆辙**——那条路径已经付出过「幽灵贡献者周立」「『何嘉 ·』分隔符残缺」两个坑的代价（`mock.js:1115-1124`）。新表用结构化外键，从源头避免。

### 2.2 字段清单（逐字段）

| 中文名 | key | 类型 | 示例 | 必填 | 说明 |
|--------|-----|------|------|------|------|
| 任务名称 | `title` | string | `会员积分规则迁移到自然年` | ✅ | Jira issue 标题，单行裁剪（`white-space:nowrap` + ellipsis） |
| Jira 单号 | `key` | string | `MEM-2184` | ✅ | **同时用作 React key 与稳定标识**（唯一、天然有序）。格式 `项目前缀-数字` |
| 当前状态 | `status` | enum | `'todo' \| 'inprogress' \| 'review' \| 'blocked'` | ✅ | **4 态**（见下）。渲染为 Pill/状态点 |
| 预期交付时间 | `due` | string `'YYYY-MM-DD'` | `'2026-10-08'` | ✅ | **格式必须与 `EVIDENCE_AS_OF` 一致**（`YYYY-MM-DD` 纯日期字符串，便于字典序比较） |
| 所属项目/迭代 | `project` | string | `'会员中心'` 或 `'Q4 迭代 3'` | ✅ | 建议存**中文业务名**（与现有 `demandSystems` 用中文 label 的口径一致），不存 Jira 工程 key |
| 优先级 | `priority` | enum | `'P0' \| 'P1' \| 'P2'` | ❌ 选填 | **建议保留但只做极弱展示**（见 §2.5） |

**我判断该「加」与「不加」的**：

- **`impact`（影响范围）—— 明确不建议加。** 理由：本次已经因为「近期工作内容 + 近期知识贡献同层」而屏效紧张；再加一个影响范围字段，卡片会从「任务名 + 一行元信息」膨胀成三行，与用户「提高屏效」的诉求相悖。**Jira 的原始信息里，同事最关心的是「在做什么」和「什么时候好」——影响范围是次要的。** 若未来要，放 v0.4.4。
- **`assignee` / `assigneeId` —— 需要，但是查询键而非展示字段**：`assigneeId`（personId）用于按人聚合，`assignee`（姓名）用于可能的展示。**至少要有 `assigneeId`。**
- **`type`（任务类型：Story/Bug/Task）—— 选填不建议**：与「优先级」重复承担「这是什么性质的活」的表达，且 Jira 类型词（Story/Bug）对本项目的中文受众是英文噪音。**若一定要，用「需求 / 缺陷 / 优化」三态中文**，不放英文。
- **`updated`（最后更新时间）—— 建议加但不必上屏**：作为数据完整性保留，未来做「久未更新」提示有用。

### 2.3 「预期交付时间」的格式与排序规则

- **格式**：`'YYYY-MM-DD'` 纯日期字符串（**不带时区、不带时间**）。理由：① 与全仓既有日期口径（`EVIDENCE_AS_OF`、`articles[].updated`）一致；② 纯日期字符串可**直接字典序比较**，与 `getPersonProfile` 里 `a.date < b.date` 的既有做法同构，零额外解析。
- **排序规则（确定性的、可复现的）**：**按 `due` 升序（越近越靠前）**；`due` 相同时按 `priority` 降序（P0→P2）；再相同时按 `key` 字典序升序。**三级键保证全序、无随机。**
- **禁止**按 `status` 分组（那会变成第二套分组，与「去掉分组」的版面方向冲突），也**禁止**按状态排前（会让「已完成」浮顶，而用户要的是「当前及未来」）。

### 2.4 时间窗定义：「当前以及未来 1 个月」的精确口径

**我给出的可复现口径**：

> 以固定基准日 `EVIDENCE_AS_OF = '2026-09-17'` 为「今天」。
> 时间窗 = `[AS_OF, AS_OF + 1 个月]` = **`2026-09-17` 至 `2026-10-17`（含端点）**。
> 窗口右界用**加 1 个自然月**计算（不是加 30 天），并**在数据层写死为一个派生常量**。

**关键判断（我用显式取值，不动 `EVIDENCE_AS_OF` 语义）**：

- **新开常量，但复用同一个基准日值**：建议 `export const WORK_WINDOW_AS_OF = EVIDENCE_AS_OF;`，再派生 `export const WORK_WINDOW_END = '2026-10-17';`（**直接写死右界字符串**，而不是运行时 `new Date` 加月份）。
  - **为什么写死右界而不是运行时计算**：`new Date('2026-09-17').setMonth(+1)` 涉及月末溢出（如 1-31 加一月会滚到 3-3）与时区解析差异，是「看起来对但边界会漂」的经典坑。写死字符串 = 零解析歧义、断言可逐字复现，与 `EVIDENCE_AS_OF` 同一个哲学。
  - **为什么不改 `EVIDENCE_AS_OF` 本身去扩容**：那会牵动 12 个月实证窗（`withinWindow`），风险外溢。两个常量共享同一基准值即可，互不干扰。
- **「当前」的定义**：**必须是「状态未完结」，不是「日期 ≥ 今天」。** 即 `status ∈ {'todo','inprogress','review','blocked'}` 视为「当前仍在进行」。理由：一条 `due` 已过但仍是 `inprogress` 的 issue 依然是「当前工作」，按日期筛会把逾期在办的任务漏掉——那恰恰是同事最该看到的。
- **因此窗口筛选规则 = 两条件**：① `status` 未完结（排除 `done`）；② `due ∈ [AS_OF, WORK_WINDOW_END]`。
  - **但需要一条兜底**：「逾期未完结」的（`due < AS_OF` 且未完结）**是否显示？** 我的默认值：**显示，但排在正常任务之后，并加一个极弱的「已逾期」提示**。理由：漏掉逾期任务等于对协作方撒谎（「他没在手忙什么」）。**若用户嫌复杂，退一步：本期先只显示窗口内的，逾期任务放 v0.4.4**——但我倾向前者，因为不一致的「当前工作」视图是危险的。

### 2.5 字段数上限与空态

- **上限：每人最多 5 条**（按上述排序取前 5）。理由：① 用户明确要「提高屏效」；② 该板块与「近期知识贡献」同层，两栏并排，条数过多会把楼层撑得极高；③ `personTags` 已确立「上限 ≤9」的先例，任务限 5 与之一致克制。**超出 5 条时**：不显示「查看更多」（个人主页是只读快照，不做二级页），改为在 PanelHead 的 `extra` 里显示真实总数（如「8 条 · 显示近 5」）。
- **空态**（该人 0 条任务）：文案走「中性、不制造缺失感」的路子，与既有空态口径一致：
  > 「暂无在办任务。任务数据来自 Jira 的负责人字段，仅展示当前至未来 1 个月的排期。」
  - **不要写成「该成员没有工作」**——这类措辞会让页面读起来像绩效批评（全站铁律：不作为绩效评价）。空态只说「暂无排期数据」，不评价人。

## 3. 楼层重排后的版面结构

### 3.1 新楼层顺序（自上而下）

| 楼层 | 内容 | 变化 |
|------|------|------|
| **楼层 1** | 员工个人信息（hero：头像 + 姓名 + 部门/职务/联系） | **沿用 v0.4.2 通栏单列，不动** |
| **楼层 2** | **技能标签**（横向流式，`flex-wrap`） | **大改**：去分组标题条 + 去组内网格 → 单层横排；**位置从「主体左栏」提到 hero 正下方通栏** |
| **楼层 3** | **近期工作内容（左）｜ 近期知识贡献（右）** | **新组合**：两者同层两栏 |

**与 v0.4.2 的结构差异（必须让施工方看清）**：
- v0.4.2 是「hero 通栏 → （技能标签 1.85fr ｜ 知识贡献 1fr）同层两栏」= **2 层**。
- v0.4.3 是「hero 通栏 → 技能标签通栏 → （工作 ｜ 贡献）同层两栏」= **3 层**。
- **即：技能标签从「与贡献同层的左栏」抽出来，独占楼层 2；贡献与新模块组成楼层 3。** `.dp-g-profile`（1.85fr/1fr）不再承载「标签/贡献」关系，而是承载「工作/贡献」关系——**若沿用旧比例，等于让「工作」压过「贡献」**，见 §3.3。

### 3.2 楼层 2「横向楼层」布局细节

**布局方式：`flex-wrap` 流式，不用固定列数 grid。**
理由：用户要「横向楼层、提高屏效」。`flex-wrap` 让标签卡按自身内容宽度自适应排列，短标签（如「RAG」「埋点」）不会被 `grid` 强制拉成等宽大格，整行能被填满——**这正是「提高屏效」的实现手段**。固定 3/4 列 grid 会在标签长短不一时留下参差空白，反而不省。

**标签卡尺寸建议**：
- **宽度：`auto`（由内容决定）+ `min-width: 132px`**。132px 能容下「需求拆解与排期」这类 7 字标签 + 点赞，且短标签不至于窄到读不出。
- **高度：固定 `auto`，但通过内容约束稳定在约 68–72px**（标签名 13px 一行 + 分组名 11px 一行 + 档位条 ≈ 8px + 上下 padding 12px×2）。**建议不写死高度**，用 `padding: 10px 12px` + `gap` 控制；写死高度会在中文标签换行时截断。
- **间距：`gap: 10px`**（比 v0.4.2 的 12px 更紧，服务屏效；但不要低于 8px，否则卡与卡粘连、读不出边界）。
- **每行约放 6–8 张卡**（在 1400px 内容宽下）——这是「横排提高屏效」的量化目标。

### 3.3 分组信息：保留还是删除？——**我的判断：保留分组名小字，删除分组结构**

用户原话「技能标签卡片**不用分组展示**」——我的解读与建议：

| 做法 | 我的判断 |
|------|---------|
| 删除「分组标题条 + 按组分段 + 组内网格」 | ✅ **该删**。这是「分组展示」的本体，正是用户嫌复杂、占屏效的东西。 |
| 删除标签卡上那行 11px 的分组名小字（`t.tag.group`，`ui.jsx:809-811`） | ❌ **不该删**。 |

**论证**：
1. **「不用分组展示」针对的是「结构」，不是「信息」**。用户抱怨的是「7 个组、每组一个标题条、每组分一段」这种**层层套嵌的展示结构**，不是「这张卡属于哪一类」这个事实本身。
2. **分组名是唯一的类目上下文**。横排之后，标签卡的排列顺序仍需一个依据（否则就是乱序堆叠）。保留分组名小字 = 用户扫一眼就知道「这是工程类的标签」；删掉 = 一堆无归属的裸词，反而更难读。
3. **成本几乎为零**：11px / `text3` 一行小字在横排卡上仅占约 17px 高度，**删它省不了多少屏效，却损失了信息**——不符合「性价比」判断。
4. **它还承担排序的可见性**：横排虽不分组，但**排序仍按 `SKILL_GROUPS` 组序 → 档位降序**（沿用 `getPersonProfile` 现有排序，`mock.js:1376-1395`），同组标签自然相邻。保留了分组名小字，用户才能理解「为什么这几个挨在一起」。

**结论**：**去掉分组容器与标题条，保留卡内分组名小字，保留按组序的排序**。这样既满足「不用分组展示」，又不丢信息、还能省下每条标题条的屏效。

### 3.4 楼层 3 两栏宽度配比

**建议：等宽 `1fr / 1fr`，不沿用 1.85fr/1fr。**

理由：
- v0.4.2 的 1.85fr/1fr 编码的是「标签为主、贡献为辅」的主次关系。v0.4.3 楼层 3 是**两个平级的信息模块**（都是「这个人在做什么」的一个侧面：前瞻=工作、回顾=贡献），**没有主次**，非对称配比会凭空制造一个不存在的层级。
- 两块内容体量相当（都是列表：任务 5 条上限 vs 贡献若干条），1fr/1fr 更稳、更易读。
- **落地建议**：新增 `.dp-g-duo { grid-template-columns: minmax(0,1fr) minmax(0,1fr); }`，并纳入 ≤900px 塌缩块。**不要直接改 `.dp-g-profile`**——`.dp-g-profile` 已被 `mutation.cjs:177` 与 `shots.cjs` 几何门锁定为 1.85fr/1fr，改动会连带击穿变异自证与几何断言（见 §5）。
- 若两栏高度不齐，`align-items: start`（保持顶部对齐），不要让短的一栏被拉伸。
