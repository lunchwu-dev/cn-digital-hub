## 0. 三条指令的收敛读法（结论前置）

用户说的是三件事，但本质只有一件半：

| # | 用户原话 | 真实诉求（我的解读） |
|---|---------|--------------------|
| 1 | 双轴太复杂，改成**统一技能标签树 + 成熟度**，标签树不区分适配岗位 | **砍掉一层正交结构**。从「领域×能力」两个轴，降为**一棵树**。用户认为「两个轴」本身就是复杂度的来源，而不是轴里条目太多。 |
| 2 | 个人主页只留：基础信息 + 技能标签与成熟度（主）+ 近期知识贡献（辅） | **做减法**。「不用其他内容了」是硬约束——被点掉的（能力分布概览、协作触点、底部注释等）要真的删，不是折叠。 |
| 3 | 页面布局更有个人主页的特征 | 现布局是「文章详情页」的复制品（左正文/右 232px 侧栏），**缺少一个 hero 主体**。要的是主次分明、以「这个人」为中心的第一屏。 |

**一句话总纲**：v0.4.1 = **单树化**（结构） + **主页化**（版面） + **减法**（内容）。这是一个「**简化版本**」，不是「增强版本」。任何让页面变复杂、条目变多的实现方向都与指令 1、2 相悖。

## 2. 【重点】单树的结构设计约束研判

### 2.1 我对「分组方式」的专业结论

主理人初步判断是「分组维度应从按岗位族切改为按能力域/能力层级切」。我的结论是：

> **方向对一半。『按能力域/能力大类切』应当采纳；但『能力层级』不应当作为分组的第二维度，只能作为「成熟度」这一条独立纵向信息存在。**

理由：

1. **「不区分适配岗位」= 分组名里不能出现职位词**。这是用户意图的硬边界。任何形如「研发岗 / 产品岗 / QA 岗」的分组名都在字面上违背指令 1，一律禁止。
2. **分组必须「跨岗位共享同一棵树」**。产品经理和 QA 工程师都应能在同一棵树上打标签——树是「技能地图」，不是「岗位目录」。所以分组名必须是**能力领域的名词**，而不是**角色的名词**。
3. **但「能力层级」不能做分组**。用户原句是「技能标签树**以及**成熟度」——「以及」是并列连词：树是水平维度（是什么技能），成熟度是垂直维度（对这项技能到哪了）。如果把「层级」塞进树的分组（初级/中级/高级组），就**把成熟度重复编码进了结构**，等于又造了第二个轴——用户刚砍掉的「两个轴」会以「分组层级」的形式复活。**层级只能由成熟度表达，树只负责「技能是什么」。**

**因此：单树 = 一维分组（能力域，水平）+ 一维评价（成熟度，纵向）。二者不正交、不叠加、层级只出现在成熟度里。**

### 2.2 建议的分组清单（单树 · 按能力域切）

我建议**直接复用现有 `CAP_GROUPS` 的 4 个能力族作为树的顶层分组**，因为：① 这 4 个族本身已是「能力域」口径，天然岗位中立；② 已验证 25 个 `c-*` 标签能无歧义落入其中；③ 改动面最小，施工风险低。

| 组序 | 组名 | 语义 | 与相邻组的关系 |
|------|------|------|---------------|
| 1 | **工程技术** | 构建与交付软件系统的能力：架构、前后端、质量、可靠性、安全 | 偏「造东西」 |
| 2 | **产品与设计** | 定义与塑造产品形态的能力：产品、交互、研究、规范、内容、视觉 | 偏「定义东西」 |
| 3 | **数据与分析** | 让数据可用的能力：数仓/管道、分析、建模、指标设计、算法 | 偏「度量东西」 |
| 4 | **项目与协作** | 让一群人把事做完的能力：拆解排期、里程碑、跨团队、带人、沟通 | 偏「推动事情」 |

组间关系是**并列且无优先级**（不排序、不隐含高低），顺序仅作渲染稳定性用。

> 备选方案（我更倾向但不强推）：把「工程技术」再拆出「质量与测试」独立成组（含测试与质量、代码评审、可靠性设计），共 5 组。理由是 QA 工程师在 4 组方案里只能落在「工程技术」下沉底，「测试与质量」被淹没在架构/前后端里，不利于 QA 岗位的自我认同。**但这只是分组粒度问题，不改变『按能力域切』这一原则**，可由设计系统专家二选一。

### 2.3 现有 72 个 active 标签的归属映射规则

（72 = 领域 47 + 能力 25；另有 deprecated 2 + merged 1 不在 active 计数内）

**规则 A —— `c-*` 能力标签（25 个）：100% 无歧义套用。**
它们本就有 `group` 字段，且 `group` 值恰好等于上述 4 个能力族。映射即 **原样保留 group**，只去掉 `axis` 字段。示例：`c-architecture→工程技术`、`c-ux→产品与设计`、`c-modeling→数据与分析`、`c-mentoring→项目与协作`。

**规则 B —— `d-*` 领域标签（47 个）：需要「去业务化」清洗，不能原样保留。**
这是**最关键、也是最容易被施工方做错的一点**。现有领域分组大量是**业务/系统对象**（`门店 POS`、`会员积分`、`电子价签`、`迪卡侬 App`、`SSO 统一身份`、`Grafana 看板`），它们不是「员工技能」，而是「业务系统名字」。直接搬进技能树会导致：产品经理的标签页里出现一串他根本不「会」的系统名词，标签退化成「我在哪个项目待过」。

映射需要**两条子规则**：

- **B1（保留并升级）**：本就是能力语义的领域项，直接升为技能标签。
  - `d-design-system 设计系统` → **产品与设计**（能力：可制定并维护设计系统）
  - `d-metrics 指标体系` → **数据与分析**
  - `d-tracking 埋点` → **数据与分析**（能力：埋点方案设计）
  - `d-observability 可观测性`、`d-cicd CI/CD 流水线`、`d-cloudnative 云原生`、`d-gateway API 网关`、`d-config 配置与发布` → **工程技术**
  - `d-stability 稳定性工程`、`d-security 安全与合规`、`d-dataquality 数据质量` → 归 **工程技术**（质量/可靠性语义）
  - `d-demand 需求管理`、`d-collab 跨部门协同`、`d-ops-process 研发流程`、`d-portal 内部门户`、`d-content-ops 内容运营` → **项目与协作**
  - `d-docs 知识沉淀`、`d-onboarding 新人上手` → **项目与协作**（带人/传播语义）

- **B2（业务系统项 → 两条出路，必须二选一，不可硬塞）**：
  - **出路一：归入最贴近的能力域**——把「系统对象」翻译成「对系统所需的能力」。例：`门店 POS` / `自助结账` / `电子价签` / `线上商城` / `会员小程序` / `订单与履约` / `供应链数字化` → **工程技术**（这些是「交付过的系统域」，对工程师是工程经历、对 PM 是业务设计经历）。`会员增长` / `促销与优惠` / `会员与 CRM` / `内容运营` → **产品与设计**。`实时计算` / `数据仓库` / `经营看板` / `A/B 实验平台` / `数据平台` → **数据与分析**。
  - **出路二：判定为「非技能」，从树里降级/合并**——`SSO 统一身份`、`Grafana 看板` 这类是**具体产品名**，不是可迁移技能，应合并进 `平台与基础设施` 对应的能力标签（SSO→安全与合规/身份能力；Grafana→可观测性），或标 deprecated。

**规则能否无歧义套用？——诚实回答：不能 100% 无歧义，B2 的「出路一 vs 出路二」存在人工判断。**
A、B1 可机械套用；B2 里约 15–20 个业务系统项需要**逐个人工定夺归属**。这不是缺陷，而是「双轴→单树」必然要付的清洗成本：**把「业务域」这一层冗余结构真正消解掉，而不是改个名字继续留着。**

**我的具体建议（给设计系统专家的最小风险路径）**：
- 先在**单树**里只放 A + B1 的标签（约 25 + 16 = 41 个），保证树干净、语义统一；
- B2 的业务系统项**另起一个「业务领域」分组挂在树的最末端**（视作「我熟悉的业务对象」，与技能组在语义上明确区分），或直接弃用。**关键是不能把 `门店 POS` 和 `前端工程` 平铺在同一个技能组里**——那会让单树重新变得像 v0.4 一样难读。

### 2.4 明确反对的分组方式及理由

| 反对方案 | 反对理由 |
|---------|---------|
| **按岗位族分**（研发岗 / 产品岗 / 设计岗 / QA 岗） | **直接违背指令 1 字面**。用户明说「不区分适配岗位」。且岗位族分组下每类人只看到自己那三五条，标签体系从「找人的地图」退化成「岗位目录」，跨岗位协作时找不到人。 |
| **按能力层级分**（初级 / 中级 / 高级） | 把「成熟度」重复编码进树结构，等于把砍掉的第二个轴以分组形式复活。层级**只能**由 MaturityAxis 表达。 |
| **保留双轴只换名字**（如把「领域轴/能力轴」改叫「A 类/B 类」） | 换汤不换药。用户抱怨的是「两个轴」这个结构本身，不是轴的名字。 |
| **按标签热度/使用人数分** | 动态分组导致同一标签位置漂移，破坏「稳定可预期」的定位；且隐含「热门=重要」的价值判断，与「不作为绩效评价」的声明冲突。 |
| **按字母/拼音序平铺（无分组）** | 72 个标签平铺成一坨，比双轴更不可读。用户要的是「统一」，不是「无序」。 |

### 2.5 单树带来的结构性副作用（必须转达施工方）

- **`axis` 字段必须彻底消失**：不仅从 `TAG_DICT` 删，还要从 `TagMatrix`（`tags.filter(t => t.tag.axis === 'domain')` 的分区渲染）、`TagBrowse`（`axisFilter` 三段 Segmented）、`TagChip`（`AXIS_GLYPH` ◈/◇）、`MaturityAxis` 调用点、`PersonProfile` 全部清理。**残留任何一处 axis 都会造成半新半旧的不一致。**
- **实证闸门自动消失**：`mock.js` 的 `collectEvidence()` 里 `if (hit && TAG_BY_ID[hit].axis === 'domain')` 这条闸门，单树后应改写为「只要命中即计入」。**后果**：原本拿不到实证的 `c-*` 标签开始有实证，**「吹牛态」与「收敛态」的分布会变**（部分原本的吹牛态会变成有实证，部分原本 collapse 的标签会显形）。这会**直接影响依赖屏幕计数的测试断言**（如 `_boast.txt`、`_acc-*.txt` 所代表的门控）。**这是本次唯一的「非视觉」行为变更，施工后必须重算并显式更新所有相关断言的期望值，不可只求测试变绿。**
- **`primaryTags` 里 `d-*`/`c-*` 混用不受影响**：已核实 `personTags` 是按人 `tagId→selfRating` 映射，本身轴无关，**数据层不用按人重写**。

## 3. 【重点】个人主页的布局层次建议

### 3.1 结论：什么才算「有个人主页的特征」

> **个人主页的特征 = 有一个「人」的 hero 区，其余内容都是它的注解。**
> 现状的病灶不是「区块不好看」，而是**四个区块视觉权重完全相同**——页头、标签矩阵、贡献列表、注释四块一样重，读起来像「一篇文章被塞了四个卡片」，不像「一个人的名片被展开」。

### 3.2 建议的视觉层次（三层）

| 层 | 内容 | 版面地位 | 信息密度 | 理由 |
|----|------|---------|---------|------|
| **L1 · Hero（第一屏主角）** | 头像 + 姓名 + 部门/职务/联系 + **主标签（≤3 个，含成熟度）** | **通栏、最大字号、最重视觉** | 低（大留白、大字号） | 这是「这个人是谁」的唯一答案区。用户指令 2 说「基础信息板块 + 技能标签与成熟度呈现为主」——**hero 应当把「人」和「他的 3 个招牌技能」合在一起**，而不是把标签甩到下面的矩阵里。 |
| **L2 · 技能主体（页面重心，面积最大）** | **统一技能标签树 + 成熟度**（按 4 个能力域分组呈现） | **通栏居中，占据页面最大面积** | 中高（标签卡密集） | 「呈现为主」= 这块是**信息主体**，面积上必须最大；但视觉「重量」应低于 hero（用更小的卡、更浅的底），靠**面积**而非**字号**取胜。 |
| **L3 · 辅助（右侧或底部，可窄）** | **近期知识贡献**（每条标注喂养了哪个标签，保持联动） | 次要，窄栏或下方通栏 | 中 | 用户明确说「为辅」。现状把它放在 232px 右栏其实是对的，**问题在于它和标签矩阵平级**——应降为从属。 |

### 3.3 具体版式建议

- **放弃 `.dp-g-article`（1fr / 232px 两栏）**。这是文章详情页的栅格，被个人主页复用是 v0.4 的「借用」，正是「像文章不像主页」的根因。建议改为**「Hero 通栏 + 主体两栏」**：Hero 占满宽度；下方 `技能树（宽）| 贡献（窄）` 两栏比例约 `1.6fr / 1fr`（或 `1.8fr / 1fr`），窄栏不小于 280px 否则贡献标题会挤成两行。
- **Hero 内的成熟度要「放大但克制」**：主标签用 `MaturityAxis variant="expanded"`，但只放 ≤3 个——hero 是**精选**，不是全部标签的预览。
- **技能树区做视觉降噪**：分组标题条沿用现有 `cardHeadBg` 样式，但标签卡从「3 列大卡」可考虑改为**更紧凑的行内 chip**，让「树」的层级感（4 个组）压过「卡片」的独立感。**注意：这是可选优化，核心是「hero 立起来」，不是重画标签卡。**
- **删除**（用户说「不用其他内容了」）：P2 ④ 能力分布概览（`领域 N 个 · 能力 N 个 · 近 12 月实证 N 条` + Sparkline）、P2 ⑤ 协作触点（负责的工具）、底部「本页为只读视图…」注释行。这些是 v0.4 的堆料，与用户「做减法」的意图直接冲突。

**判断取舍**：我**不建议**把「协作触点」保留成折叠区——用户说得很直白「不用其他内容了」。保留折叠区等于没删。若真舍不得，最多把「该人负责的工具」压成 hero 里的一行极淡文本（如「负责 N 个工具」），但**默认方案是删**。

## 4. 歧义与默认值

| # | 指令 | 歧义 | 我的推荐默认值 |
|---|------|------|---------------|
| 1 | 「统一的技能标签树」 | 「树」是**分层树**（组→子组→标签）还是**一层分组**（组→标签）？ | **默认：一层分组**（4 个能力族 → 标签）。理由：用户嫌复杂，加层级=加复杂度，违背意图。若后续需要子组，也应作为 v0.4.2 的独立需求，不在本次做。 |
| 2 | 「标签树不区分适配岗位」 | 是「不给标签绑定岗位标签」，还是「分组名里不出现岗位」？ | **默认：两者都要**。树的分组名、层级一律不出现职位词；同时标签定义**不新增** `roles` / `applicableRoles` 字段。 |
| 3 | 「成熟度」 | 现有成熟度是**双证据模型**（自评 4 档圆点 + 实证 4 段轨道），这是 v0.4 的招牌。用户说「成熟度就好」——**是保留双轨，还是收敛成单一档位？** | **默认：保留双轨模型，不合并**。理由：用户只说「用成熟度」，是在**对比「(领域轴+能力轴)×成熟度」的复杂度**，不是要改成熟度本身；「吹牛态/收敛态」是 v0.4 刻意保留的诚实标记，删掉是功能倒退。**但需在实现后确认双轨在有实证的 `c-*` 标签上仍读得通**（见 2.5 副作用）。 |
| 4 | 「近期知识贡献为辅」 | 是**数量上少**、**位置上靠边**，还是**视觉上更淡**？ | **默认：三者都做**——保留全部近期条目（不截断，因为「近期」本身已有限），放置于窄栏，视觉降为次级。**不新增「查看更多」入口**。 |
| 5 | 「不用其他内容了」 | 「其他内容」的边界——是否包括 Breadcrumb 和底部只读声明？ | **默认：删正文级区块（能力概览/协作触点/底部注释），保留 Breadcrumb**（导航必需，不是「内容」）。 |
| 6 | 「更有个人主页的特征」 | 参考对象是谁？(LinkedIn / 企业通讯录 / GitHub Profile) | **默认：企业通讯录名片 + 名片式 hero**，不是 LinkedIn 社交档案（内部工具，无需关注/点赞/动态）。判定标准：**第一屏不看滚动，就能答出「这人是谁、擅长什么」**。 |

## 5. 边界与不做的事（防范围蔓延）

v0.4.1 **明确不做**：

1. **不做分层树 / 多级子分组**——一层分组足矣，加层级=加复杂度=违背指令 1。
2. **不改成熟度模型本身**——`SELF_RATINGS`、`EVIDENCE_ORDER`、`EVIDENCE_COPY`、`boast`/`collapse` 渲染语义全部保留；只允许因轴闸门消失而**被动**产生的档位分布变化（并把断言同步更新）。
3. **不新增任何交互**——不加关注、收藏、编辑、点赞、私信、导出、分享。个人主页仍是只读的第三人称视图。
4. **不重做视觉规范**——token、组件、配色、字体一律沿用 v0.4；本次只是**结构与版面**调整，不是视觉重做。**不新增颜色/字号/间距 token。**
5. **不动其他页面**——首页、新闻、工作台、需求入口、知识库等不受影响；只动个人主页 + 标签浏览 + 标签反查三处的轴相关逻辑。
6. **不重写 `personTags` 数据**——按人组织的数据本身轴无关，只需处理 `TAG_DICT` 的 `axis` 字段与分组。
7. **不做移动端专门设计**——沿用现有 ≤900px 单列塌缩即可。
8. **不给 B2 类业务系统标签做大规模新增**——本次是「清洗降级」而非「扩充词表」；若确有新增需求，另开 v0.4.2。
9. **不做标签的岗位映射表**——绝不允许为了「兼容各类岗位」而反向建立「岗位→应该有哪些标签」的对照表，那是变相的双轴复活。

## 6. 交付给下游的关键提示（一句话版）

- **给设计系统专家**：砍 `axis`，单树的分组请用「能力域」而非「业务系统域」；`d-*` 里的业务系统项需要逐个清洗（B2 规则），这是本需求最需要专业判断的地方。
- **给原型施工方**：三处轴逻辑（TagMatrix / TagBrowse / TagChip）必须同步清理；`collectEvidence` 闸门去掉后，**「吹牛态/收敛态」屏幕计数会变，所有相关测试断言必须重算而非硬调绿**；个人主页请放弃 `.dp-g-article` 栅格，改「Hero 通栏 + 主体两栏」。
- **给评审方**：验收时请专查两条——① 树里有没有岗位词（有即违背指令 1）；② 「不用其他内容了」被删除的区块有没有换个壳留着（留着即违背指令 2）。
