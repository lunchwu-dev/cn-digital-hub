## 0. 总结论（前置）

| # | 用户原话 | 真实诉求 | 我的判断 |
|---|---------|---------|---------|
| 1 | 技能标签是不是可以和个人信息**糅合成一个大的楼层**，标签及成熟度的卡片可以**再轻量化一些** | ① 两楼层合并为一；② 标签卡降重量 | 该做。**但用户用了「是不是可以」——这是征询语气，不是硬命令**；且合并会击穿 2 条核心结构门（见 §1.3 / §5），须连同测试一起改。 |
| 2 | 近期工作内容**设定为独占楼层**，显示**未来 8 周的资源占用**，以**资源甘特图**呈现，每周一个格子 | ① 工作楼层独占；② 由「近 1 月任务清单」改为「8 周占用甘特」 | 该做。**「独占」隐含拆掉 v0.4.3 的 `.dp-g-duo` 双栏**（工作不能再与贡献同层）——这是本轮**测试冲击最大**的一处（M13/M14 变异 + shots 几何门全挂在 `.dp-g-duo` 上）。 |

**一句话总纲**：v0.5 = **楼层糅合（1+2 层并一层）** + **卡片减重** + **工作楼层改为 8 周资源甘特并独占**。这是**结构重排 + 新数据模型**，不是视觉重做。

**三个「必须改」的硬约束（用户想法里有三处需修正，理由见对应章节）**：
1. **「未来 8 周」的周口径必须写死**，不能运行时 `new Date()` 推周——本项目已因「不可复现」栽过三次（`mock.js:1293-1296` 有明证）。
2. **「独占楼层」= 必须拆 `.dp-g-duo`**，不能保留「工作｜贡献」并排；否则「独占」名不副实。
3. **卡片轻量化不得以「删分组名」为主手段**——分组名行是唯一的类目上下文，且被门⑤（`smoke.cjs:1786-1793`）逐卡断言；轻量化应走**内边距 + 行合并**，做到「减重但不丢信息」。

## 2. 楼层重构方案：个人信息 + 技能标签糅合为一层

### 2.1 两个候选

**候选 A —— 上下带式（单 Panel，推荐）**
单楼层 = 一个 `.dp-card`（沿用 hero 的 Panel 壳），内部上下两带：
- 上带「身份带」：头像 + 姓名 + 组别/职务 + 地点/邮箱（沿用 `.dp-person-head-main`）；padding 由 `24px 28px` 收到 `18px 22px`。
- 下带「技能带」：`.dp-tag-floor` 横排标签卡（**保留类名与卡结构**）；上方一条 `1px` 内分隔线。
- 合规脚注移至该 Panel 底部。

**候选 B —— 左右分栏式（单 Panel 内横排）**
单楼层 = 一个 `.dp-card`，内部左右两栏：左 ~280px 身份块（头像 + 姓名 + 组别 + 邮箱），右为 `.dp-tag-floor` 标签流。

### 2.2 推荐：**候选 A**，理由

1. **屏效最高**：标签流拿到**整幅通栏宽度**（1440 下约 1300px，可容 8~10 张卡/行）；候选 B 把标签流压到约 1000px，且左栏在窄屏还要塌缩——B 的收益只存在于宽屏。
2. **身份视觉权重不损失**：`fontSize:24` 的姓名 + `64px` 头像在通栏下是楼层主标题；候选 B 把它们塞进 280px，姓名大字在窄栏里会被挤压，个人主页的「主角感」反而下降。
3. **测试改动最小**：A 保留 `.dp-person-head-main`、`.dp-tag-floor`、标签卡与 `width:64` 档位条**全部原样**，只改「外层包装」；B 需要新写分栏 CSS + 新的断点塌缩，测试面更大。
4. **与既有决策一致**：v0.4.3 已裁定「技能标签独立通栏、提高屏效」；A 是它的自然延续，B 是倒退成狭窄栏。

> **A 的落地要点**：`TagMatrix` 建议拆成「数据/呈现」两层，或加 `embedded` prop——糅合楼层**不应出现两个 Panel 头**（hero 无 PanelHead，标签带也不应有「技能标签」标题条，否则又是一层结构）。标签带用一行极简 meta 取代 PanelHead，例如 `技能标签 · 8 个 · 近 12 月记录 N 条`（12px text3，一行）。

## 3. 卡片轻量化方案（具体数字）

### 3.1 保守方案（推荐）：**减重 ≈22%，零信息损失**

| 项 | 现状 | 改为 | 省 |
|----|------|------|----|
| 卡内边距 | `padding:'10px 12px'` | `padding:'8px 10px'` | 高 4px |
| 标签名字号/行高 | 13px / 1.4 | 13px / **1.35** | ≈0.7px |
| 点赞高度 | `height:22`（TagLike） | `height:20` | 2px（行高由 22→20 决定） |
| **分组名行 + 档位行合并为一行** | 分组行 `2+16.5` ＝ 18.5px，档位行 `4+6` ＝ 10px，**合计 28.5px** | 单行 `2 + max(16.5, 5)` ＝ **18.5px**：`[档位条 64×5]──gap 6──[分组名 11px]` | **10px** |
| 档位条高度 | `height:6` | `height:5` | 计入上行 |
| **档位条宽度** | `width:64` | **保持 64（勿动）** | —（见下） |
| `minWidth` | 132 | **保持 132** | —（见下） |

**结果**：单卡高 `8 + 20 + 18.5 + 8` ≈ **54.5px**，较现状 ≈70.5px **降 22.7%**。

**两条「不能动」的红线（施工方务必遵守）**：
- **`width:64` 不可改**：`smoke.cjs:1593`、`smoke.cjs:1952`、`smoke.cjs:2350` **三处**以 `width: 64px` 为选择器锚点读档位条；改宽度＝同时击穿 3 条门。
- **`minWidth:132` 不可降**：绑定约束是 7 字标签「需求拆解与排期」（`TAG_DICT` `c-planning`）＋ 点赞；`132px` 已被 `smoke.cjs` 隐式依赖（卡宽稳定）。降 minWidth 会截断长标签，得不偿失。

### 3.2 激进方案（备选）：**再砍 18.5px（合计 −48%），但丢信息**

即**删掉分组名行**。代价：
- 丢失唯一「类目上下文」与「横排为何如此排序」的可见性（横排序仍按 `SKILL_GROUPS` 组序，但用户看不懂为何相邻）；
- 击穿 `smoke.cjs:1786-1793` 门⑤（逐卡断言「含 11px 分组名」）。

**我的取舍**：**不推荐**。用户要的是「轻量化一些」（程度副词），不是「极简」；保守方案已达成「明显更轻」且**零信息损失**，没有理由用信息换 18px。**若用户坚持，须同步把门⑤改为「分组名不上屏」的正向断言**（而不是删了了事）。

### 3.3 轻量化后「丢掉了什么」——**诚实回答：保守方案不丢任何信息**

- 内边距与行合并只压缩**留白**，标签名、点赞数、档位条、分组名**四项全在**。
- 唯一感知变化：卡片更矮更密，单屏可容纳更多卡（1440 下由约 3 行 → 约 4 行）。**这正是「提高屏效」的目标。**
- **可读性风险**：分组名与档位条同行后，组名仍有 `ellipsis`；132px 内「5 字组名 + 64px 条」合计约 55+6+64=125px＋padding 20=145px **略超 132**。**解法（推荐）**：把**档位条放左、组名放右**（组名右对齐 ellipsis），或组名字号 11→10.5。**建议档位条在左、组名在右**——视觉上「先看档位、再读类目」，且组名截断发生在末尾、读感更轻。

## 4. 8 周资源甘特图方案

### 4.1 数据模型

#### 4.1.1 `JIRA_ISSUES` 新增字段

现有字段（`mock.js:1302-1304`）：`key / title / status / due / project / priority / assigneeId`。
**新增 1 个字段 `start`（'YYYY-MM-DD'，任务计划开始日）**，与既有 `due` 构成区间 `[start, due]`。

```js
// 形态样例（周敏 min.zhou）——全部静态字面量，零 new Date()
{ key: 'DS-3102', title: '设计令牌 v2 全站迁移与回归', status: 'inprogress',
  start: '2026-09-15', due: '2026-09-22', project: '设计系统', priority: 'P0', assigneeId: 'min.zhou' },
{ key: 'DS-3110', title: '组件库无障碍标注补齐', status: 'review',
  start: '2026-09-22', due: '2026-09-29', project: '设计系统', priority: 'P1', assigneeId: 'min.zhou' },
{ key: 'DS-3125', title: '深色模式令牌映射评审', status: 'todo',
  start: '2026-09-29', due: '2026-10-06', project: '设计系统', priority: 'P2', assigneeId: 'min.zhou' },
{ key: 'DS-3080', title: '图标线性化收尾（面版图标下线）', status: 'inprogress',
  start: '2026-09-01', due: '2026-09-15', project: '设计系统', priority: 'P1', assigneeId: 'min.zhou' },
{ key: 'DS-3121', title: '设计规范文档站改版', status: 'blocked',
  start: '2026-10-06', due: '2026-10-09', project: '设计系统', priority: 'P2', assigneeId: 'min.zhou' },
```

**为什么用 `start`+`due` 区间，而不是存 `weeks:[1,2,3]` 数组**：
1. **单一事实来源**：周占用是日期的**派生量**；存周数组会与日期各自漂移（改日期忘改周数组＝静默错格）。
2. **真实感**：Jira 的 issue 本来就有 `start/due`。
3. 可行区间 **不设 `weeks`**，由 `weekIndexesOf(issue)` 派生。

#### 4.1.2 8 周窗口的固定日期口径（**写死，禁运行时计算**）

采用**锚定 AS_OF 所在周的周一**的日历周（周一~周日），8 周全部写死：

```js
export const GANTT_AS_OF = WORK_WINDOW_AS_OF; // '2026-09-17'（周四）
export const GANTT_WEEKS = [
  { i: 1, start: '2026-09-14', end: '2026-09-20', label: '09/14' },
  { i: 2, start: '2026-09-21', end: '2026-09-27', label: '09/21' },
  { i: 3, start: '2026-09-28', end: '2026-10-04', label: '09/28' },
  { i: 4, start: '2026-10-05', end: '2026-10-11', label: '10/05' },
  { i: 5, start: '2026-10-12', end: '2026-10-18', label: '10/12' },
  { i: 6, start: '2026-10-19', end: '2026-10-25', label: '10/19' },
  { i: 7, start: '2026-10-26', end: '2026-11-01', label: '10/26' },
  { i: 8, start: '2026-11-02', end: '2026-11-08', label: '11/02' },
];
```

（以上日期经我实算核验：`2026-09-17` 是**周四**；`2026-09-14` 是周一；W8 末 `2026-11-08`；覆盖整 56 天。）

**取值决策与理由**：
- **锚定周一（而非从 AS_OF 起算 7 天桶）**：日历周是受众的既有心智（「本周」「下周」），甘特图按周一排列读起来像真实排期；若按 `09-17~09-23` 切桶，列头会变成「周四~周三」这种非直觉口径。
- **代价（须向用户交代）**：W1 = `09/14~09/20` 含 3 天（09/14~09/16）在 AS_OF **之前**。**这不是 bug**：资源占用视图里「本周（含已过的周一/周二）」是正常且必要的——否则「当前占用」无处安放。
- **口径常量复用 `WORK_WINDOW_AS_OF` 的值**（`EVIDENCE_AS_OF`），**不新建第三个基准日值**；但 8 周窗口**不再复用 `WORK_WINDOW_END`（10-17，1 个月）**——两窗口语义不同（1 月任务清单 vs 8 周资源占用），`WORK_WINDOW_END` 若不再被引用应标注废弃。

#### 4.1.3 派生辅助函数（建议签名）

```js
/** issue 与 8 周窗口的交集周序号（1..8）；无交集返回 [] */
export function weekIndexesOf(issue) { /* 逐周比对 [issue.start, issue.due] ∩ [wk.start, wk.end] */ }

/** 个人甘特：{ rows:[{ key,title,project,due,status,weeks:number[] }], weekTotals:[n×8], total } */
export function getPersonGantt(personIdOrEmail) { /* 筛选 → 排序 → 映射 */ }
```

**纳入规则**：`status !== 'done'`（本项目 4 态均视为在办）**且** `[start,due]` 与 8 周有交集。
**排序**（沿用 `getPersonWork` 的三级键，保证全序）：`due ↑ → priority ↓(P0→P2) → key 字典序 ↑`。
**逾期处理（我的裁定）**：`due < GANTT_WEEKS[0].start` 且**无未来交集**的任务（如现有 `DS-3080`）**不进入甘特**——它属于「回顾」，不属于「未来 8 周占用」。**v0.4.3 的「逾期染日期色」在此视图下自然退场**（见 §4.3）。
**行数上限**：**不截断**（展示全部与 8 周有交集的在办事项）。理由：资源占用视图截断＝失真（总占用行会与可见行不符，自相矛盾）；甘特行高矮（约 28px），本项目单人最多 7 条（陈思远），全量可承受。**`weekTotals` 必须按全部在办任务统计，与可见行严格一致。**
- ⚠️ 这会退掉 v0.4.3 的「上限 5」语义与 `smoke.cjs:1811-1841`（门⑥b）；替代门见 §5。

#### 4.2.2 占用强度表达（3 个待用户确认项之一 · 我的推荐）

**推荐：总占用行用「计数 + 品牌蓝单色阶三档深浅」**
- 计数 0 → 空槽（`c.page`）；1 项 → `brandStep1`；2 项 → `brandStep2`；≥3 项 → `brandStep3`。
- **理由**：① 与 `SystemTier` 既有的「品牌蓝单色阶表达档位、坚决不做红黄绿」完全同构（`theme.js:68-74`）；② 红黄绿是「红绿灯隐喻」，天然携带绩效评判，与全站铁律冲突；③ 用**计数**而非百分比，避免造出「饱和度＝绩效分」的横向比较读法（同 `SystemTier` 不做分数比例的既有决策）。
- **待用户确认**：用户若选「百分比数字」，须注意百分比需要「满负荷」基准，而本项目**不允许定义满负荷**（那是绩效口径）——**我建议明确拒绝百分比**，理由是它会把「资源占用」偷换成「工作量考核」。

#### 4.2.3 一个任务跨多周是否连成色带（3 个待用户确认项之二 · 我的推荐）

**推荐：连成色带**。理由：跨周任务在甘特图里的标准读法就是一条连续的条；若每格独立圆角，视觉会碎成「4 个孤立小方块」，读不出「这是一件事做了 4 周」。**技术代价极低**（首末格加圆角即可）。

| 断点 | 行为 |

## 6. 开放问题

> 每条附我的推荐选项与理由。三处「待用户确认」为已抛给用户的决策，其余为我自行裁定的两难。

**Q1（待用户确认）占用强度怎么表达？**
推荐：**总占用行「计数 + 品牌蓝单色阶三档深浅」**（0 空槽 / 1 = brandStep1 / 2 = brandStep2 / ≥3 = brandStep3）。
理由：与 `SystemTier` 的单色阶决策同构、无红黄绿隐喻、不引入「满负荷」基准。
**明确反对「百分比数字」**：百分比需要一个「100% = 满负荷」的基准，而定义满负荷＝定义绩效口径，触碰铁律。

**Q2（待用户确认）跨周任务是否连成色带？**
推荐：**连成色带**（首末格圆角、中间不圆角、gap:0）。理由：甘特图的标准读法；实现成本极低；不连则读不出「一件事做了 4 周」。

**Q3（待用户确认）标签卡轻量化程度？**
推荐：**保守方案（−22%，零信息损失）**：内边距 `10/12→8/10`、点赞 `22→20`、**分组名行与档位行合并为一行**、档位条 `height 6→5`、**宽度保持 64**、`minWidth 保持 132`。
理由：用户说「轻量化一些」（程度副词），保守方案已明显更轻且不丢信息；激进方案（删分组名）省 18px 却丢类目上下文并击穿门⑤。

**Q4（我裁定）「独占楼层」是否必须拆 `.dp-g-duo`？**
推荐：**必须拆**。理由：用户明确「设定为独占楼层」；若保留「工作｜贡献」并排，则工作未独占。拆后 `.dp-g-duo` 定义**保留为考古**（同 `.dp-g-profile`），DOM 不出现。**代价**：M13/M14 + shots 断言 1d + 探针须重挂（§5.2），这是本轮最大测试工作量。

**Q5（我裁定）甘特行数是否截断？**
推荐：**不截断**。理由：资源占用视图截断＝失真，总占用行会与可见行自相矛盾；甘特行高约 28px，单人最多 7 条可承受。**代价**：退掉门⑥b 的「上限 5」。
