**阶段**：Phase 1 · 需求发现 ｜ **日期**：2026-09-17 ｜ **修订** R1 ｜ **作者**：需求发现分析师 · 许明需
**上游依据**：`outputs/03-product-solution.md`、`outputs/04-delivery-notes.md`、`portal/src/data/mock.js`（**35 个**导出实体，grep 实证）、`portal/src/pages/*.jsx`、`portal/src/components/*.jsx`、`portal/src/App.jsx`
**本次命题**：对门户全部内容域做数据源设计，裁定每个域该走「自动抓取 / 半人工（填链接自动抓取）/ 人工运营 / 其他」

## 一页结论（先看这段）

1. **35 个导出实体可归并为 22 个内容域**（13 个生产域 D01–D13 + 9 个派生/配置域 P01–P09）。另**有 3 处非 mock 内容域**（通知、引导、页脚披露，硬编码在组件里），单列 A-3。真正需要裁定数据源的是 **13 个生产域 + 3 个非 mock 域**。
2. **没有任何一个内容域适合「纯手工维护且承担定量日更义务」的运营方式。** 日更只允许出现在自动域；人工域的内容产出必须是**事件驱动**（有事才发），而非「每天必须发 N 条」。事实型数值（监控、Release、项目进度）必须自动或半自动；叙述型文本（决议、公告、最佳实践、FAQ）必须人工——把它们混为一谈是最常见的错。
3. **本次最大的成本变量不是「有没有 API」，而是「权威源是否唯一」**。所有集成风险的本质是同一件事：门户写一个值、源系统写另一个值，用户发现两边不一致后，就再也不信门户。所以裁定原则的第一条是：**凡是已有权威源的，门户一律不产生内容，只做投影。**
4. **工作量：全部 M1 链路打通约 6–8 周（乐观）／ 12–18 周（悲观），是本期集成预算的主体**。具体区间与砍域顺序见 F 节，随 Q1–Q4 的答案浮动。

## A. 内容域全景清单（13 个生产域 + 9 个派生域）

口径说明：**一个「内容域」= 一类由同一数据源供给、有同一 Owner、遵循同一更新节律的内容**。`mock.js` 的 35 个导出实体中，多个实体常属同一域（如 `announcements` + `pinnedResolutions` 都是「公告与决议」域的不同视图），也有实体是纯配置（筛选器、颜色 map），后者不产生内容，单列为派生域。

> **两列频率的区别**：「触发方式」= 内容是**事件推着走**还是**节律推着走**；「到达频率」= 实际多快出现一条。**「高频」指事件到达频率，不等于产出义务。** 事件驱动的高频域（如公告）不需要有人天天值班写稿；节律驱动的高频域（如监控）必须由系统持续供给。二者混用是执行方误判运营负担的根源。

## B. 运营模式判定框架

### B-1 模式谱系（5 类 + 1 复合）

| 代号 | 模式 | 定义 | 人工介入点 |
|---|---|---|---|
| **M1** | 全自动（系统直连） | 门户定时/实时从权威源拉取，**人工零介入**（除阈值配置） | 无 |
| **M2** | 半自动 - 链接抓取 | 人工只填**来源链接/ID**，系统定时抓取解析 | 填一次链接，之后自动 |
| **M3** | 半自动 - 人工录入 + 系统校验/派生 | 人工写正文，系统补全派生字段（Owner 解析、日期、分类、状态） | 写正文 |
| **M4** | 全人工 | 必须人工撰写与维护，无结构化源可依 | 全流程 |
| **M5** | 派生 / 聚合 | 不直接生产，由其他域计算得出 | 无（依赖上游治理） |
| **M-combo** | 复合（目录 + 状态分链） | 同一模块内，目录走 M3/M4、状态走 M1 | 分链路裁定 |

> **M2 的前提条件（重要，此前被高估）**：M2 只适用于**匿名可访问**的源页面。Figma、语雀、Confluence、Jira 等**几乎全部需要登录鉴权**，无登录的门户**抓不到**。对需登录的源只有两条出路：(a) **服务端持凭据代抓**（门户后端持有凭据，前端仍无登录）；(b) **降级为纯跳转**（M4 目录 + 外链，不做内容抓取）。**见 Q8。**

> **M1 探活类的必备状态维度（探活悖论）**：凡是以"探活"方式判定状态的 M1 域（D07、D12 状态链），状态枚举**必须包含 `unknown`**：`success / warning / error / unknown(探活失联)`。理由是"探活失败 ≠ 服务挂了"——探活脚本自己挂掉时，若没有 `unknown` 档，门户会显示**上一个已知状态**，等于对用户说谎。**当前 `stabilityItems.status`（mock.js:452-457）只有 `success/warning/error`，缺 `unknown`，落地必须扩展。**

### B-2 准入决策树（判定用）

按顺序问，**第一个为「是」的分支即结论**：

```
Q1 该数据是否已有权威源系统（Grafana / CI / Jira / 企微 / HR）？
   ├─ 有 → Q2
   └─ 无 → Q4

Q2 权威源是否提供稳定 API（或可脚本化的接口）？
   ├─ 有 API → Q3
   └─ 无 API，仅有可访问的网页/页面 → M2（链接抓取）
                                    └─ 若连网页都无可解析结构 → M3（人工录入复制）

Q3 该数据是否需要人的判断、语气、或业务解读？
   ├─ 不需要（纯数值/状态/版本号）→ M1（全自动）
   └─ 需要（如"这条决议意味着什么"）→ Q3b

Q3b 判断所需的「正文」是否已在某个系统里写好了？
   ├─ 是（源系统里已有这段文字，只是要搬过来）→ M2（抓链接/ID）
   └─ 否（门户是第一撰写地，源系统没有这段文字）→ M3（人写正文，系统补字段）

Q4 该数据是否是"门户独有、无外部源"的叙述型内容？
   ├─ 是 → 内容是否需要人写？
   │        ├─ 是 → M4（全人工）
   │        └─ 否，可由其他域推导 → M5（派生）
   └─ 否（其实是配置文件/枚举）→ 静态配置（不走运营模式）
```

> **Q3b 的复测（证明它能把"或"变成唯一解）**：`projectUpdates` 走 Q1（有权威源 Jira/Meego）→ Q2（有 API）→ Q3（需要判断）→ **Q3b：进展正文通常首先写在门户/手工表，Jira 里只有状态字段，没有这段文字 → "否" → M3**。结论唯一、可推导。**此前给的"M2 或 M3"是把决策推回给读者——M2（填链接抓取）与 M3（人写正文）的实现路径与工作量完全不同，不能并列为结论。**

### B-3 六维判定表（细粒度仲裁用）

当决策树落在边界（如"M2 还是 M3"）时，用下表打分：**任一维度指向强自动，就应往自动侧靠**。

| 维度 | 倾向 M1/M2（自动） | 倾向 M3/M4（人工） |
|---|---|---|
| **结构化程度** | 天然字段化（数值/枚举/ID） | 自由文本、需版本化管理 |
| **是否有稳定 API** | 有、且有 SLA | 无 API 或接口不稳定 |
| **权威源是否唯一** | 唯一（单点真相） | 多源、需人工裁定口径 |
| **是否需人的判断/语气** | 不需要（事实即结论） | 需要解读、定调、承担责任 |
| **出错代价** | 极高（监控错=误判）→ **必须自动且优先保证新鲜度** | 高（公告错=误导排期）→ **必须人工复核，宁慢勿错** |
| **触发方式** | **节律驱动**（系统持续产出）→ 人工不可持续 | **事件驱动**（有事才发）→ 人工可承受 |
| **到达频率** | 高频（日/小时/分钟） | 低频（月/季） |

> **一个反直觉的判据**：出错代价高 **不** 意味着要人工复核。它意味着要看**错误类型**——监控数值错是「新鲜度问题」（延迟即错），必须自动+高频刷新，人工复核反而加重延迟；公告文字错是「准确性问题」（写错即成害），必须人工。**「高代价」要拆成「怕延迟」还是「怕写错」两个方向，这是本框架最关键的区分。**
>
> **第二个反直觉的判据（本次新增）**：**"到达高频"也不意味着人工不可持续**——要看**触发方式**。公告到达频率是"日级"，但它是**事件驱动**（某件事发生了才发），不是"每天必须发 N 条"，所以 M4 全人工完全跑得动。而监控是**节律驱动**（每 15 秒产一条），人工绝无可能跟上。**频率决定自动化的下限，触发方式决定人工的上限。**

## E. 风险与边界

### E-1 最容易被低估的成本

1. **"权威源不唯一"导致的双写灾难**（最高风险）。门户若在 D02/D03/D05 上自行产生或缓存一份数据，就会与源系统漂移。用户第一次发现"门户显示已发布、系统里还在灰度"，门户的信誉就永久受损。**对策：门户对所有已有权威源的域，只做投影（projection），不做状态机。**
2. **工具状态的全自动探活成本**。`toolGroups.status` 看似简单，但要真正自动，需要对 11 个工具逐一实现探活/健康检查，且要区分"服务挂了"还是"探活脚本挂了"。多数团队会低估这里的工作量。**对策：一期可先做"半自动"——工具 Owner 每月确认一次状态；探活放二期。**
3. **知识域的人工成本是持续性的**，不是一次性。10–15 篇最佳实践、30 条 FAQ 是"种子内容"，真正贵的是 90 天复核 + 待补队列清空这两条**永续运营**。**对策：把"待补队列清空天数 < 7 天"作为首要运营指标（03 文档已定），用指标驱动，而非靠自觉。**

### E-2 最容易失败的环节

| 环节 | 失败形态 | 根因 |
|---|---|---|
| **集成先行、治理缺位** | 花 6 周接通监控 API，但没人维护公告和 FAQ，门户上线即空 | 技术工作可见、治理工作不可见，团队天然偏向集成 |
| **半人工模式的"链接腐烂"** | M2（填链接自动抓取）跑三个月后，源系统改版，抓取全断，且无人知晓 | 抓取失败没有告警；**必须给每条 M2 链路加"连续 N 次抓取失败即告警 Owner"** |
| **M2 抓取撞登录墙** | 对 Figma/语雀/Confluence 配置了 M2，但抓取永远返回登录页，解析出空内容 | 无登录架构下抓不到需鉴权的源；**配置 M2 前必须先验"匿名可达性"**（见 Q8） |
| **反馈闭环断裂** | FAQ 的 `helpful/notHelpful` 采集了，但没人消费 → 待补队列只进不出 | 缺 Owner 指派机制；采集 ≠ 闭环。**当前实现连采集都没有**（见 A-2 P01） |
| **复合域只做了一半** | 工具目录做好了，状态字段还是手填的假绿 | 把 D12 当单一域处理，漏掉状态链路；**探活脚本挂掉时还会显示假绿**（见 I2 unknown 态） |

**反馈闭环五步的 Owner 归属（补齐"只进不出"的缺口）**：

| 步骤 | 动作 | Owner |
|---|---|---|
| 1 反馈写入 | 用户点"没帮到我" → 写 `feedback_events` | 门户前端 + 埋点平台 |
| 2 计数聚合 | 事件聚合回写 `faqs.helpful/notHelpful`、按 `faqId` 排序生成缺口 | 数据平台组（建议定时任务） |
| 3 待补队列 | 高频缺口进入 `faqBacklog`，带 votes/age | 内容运营 · 孙玥 |
| 4 Owner 认领 | 按 domain 指派该领域内容 Owner | 内容运营 · 孙玥（分派人） |
| 5 关闭回流 | 补齐内容 → 出队 → 回流知识库 | 各领域内容 Owner |

> 五步缺任何一环，队列都会只进不出——而它恰是 03 文档定义的**首要运营指标**（清空天数 < 7 天）。

### E-3 明确的能力边界（03 文档已定，此处重申并影响数据源设计）

- **无登录鉴权** → 无法做：已读/订阅/关注、个性化、"公告触达率"。因此 D01 **不能** 依赖"阅读追踪"来证明价值，D11 **不能** 做"个人化 FAQ 推荐"。所有涉及身份的数据源（企微消息触达、HR 员工主体）**只能用于展示，不能用于追踪个人行为**。特别地：**`orgPeople.email` 仅用于展示与复制，禁止用于埋点关联**——这是无登录架构下最容易踩的合规红线。
- **监控只做 L1 + 下钻** → D05/D06/D07 的数据源**只拉按天/小时粒度的聚合序列，不拉秒级/请求级原始点位**；明细一律跳转。注意 `opsCharts.series`（三条 7 点序列）与 `opsKpis.spark`（7 日序列）**本身就是序列数据**，不是单标量——集成时须拉"按天聚合的序列"，若按"读 1 个标量接口"估算工作量会翻倍。这仍显著低于全量时序集成。

## F. 工作量区间与集成预算（此前缺失，按执行标准补）

数据源被 03 文档定义为"本期最大成本变量"，因此必须给出量级。**以下是最乐观（Q1–Q4 全部"有 API"）与最悲观（关键系统无 API、需自建或降级）两档锚点。**

> **列义说明（避免误读）**：「最悲观」指**收益最差时的方案形态**——不一定是工作量最大。有两行会出现"悲观值反而更小"，因为抓不到内容时方案会降级为纯跳转/纯手工，**要做的活反而更少**（D13 无 API → 只维护 10 人名单；D10b 撞登录墙 → 只放外链）。**代价是门户价值下降，不是工期变长。**

| 集成项 | 覆盖域 | 最乐观 | 最悲观 | 判定依据 |
|---|---|---|---|---|
| 监控数据接入 | D05/D06/D07 | 3 周 | 8 周 | 乐观=Grafana 只读 API 现成；悲观=需自建聚合层 + 指标口径逐项对齐 |
| Release / 发布系统接入 | D02 | 1.5 周 | 6 周 | 乐观=发布系统有按系统聚合 API；悲观=多系统各自为政，需人工兜底 + 治理 |
| 项目进度接入 | D03/D04 | 2 周 | 8 周 | 乐观=单源单 API；悲观=Jira+Meego 双源 + 里程碑独立源（Q3/Q9 全否） |
| 人员 / 通讯录接入 | D13 | 1 周 | 0.5 周 | 乐观=企微 API 直连；悲观=无 API，仅手工维护 10 人（反而更省，但需维护人） |
| 反馈事件链路 | P01/D11 | 1.5 周 | 3 周 | 需新建 `feedback_events` 采集 + 聚合回写 + 待补队列打通 |
| M2 抓取链路 | D10b | 1 周 | 0.3 周 | 乐观=可服务端代抓；悲观=撞登录墙，降级为纯跳转（工作量反而降） |
| **合计（硬集成）** | — | **约 6–8 周** | **约 12–18 周** | — |

**一期 MVP 集成预算上限建议：≤ 8 周（1 名后端工程师全职）**。超出时按以下顺序砍域（先砍对"有效性验证"影响最小的）：

1. **先砍 D03/D04 的项目进度接入** → 退化为纯人工列表（03 文档本就定 MVP 只做动态列表，结构化看板放二期）。
2. **再砍 D10b 的 M2 聚合** → 退化为纯外链跳转。
3. **再砍 D13 的人员自动化** → 退回手工维护 10 人关键名单。
4. **最后才砍 D02/D05–D07** —— 这两组是"门户不为空"的地基（信息中心 + 监控），砍了门户就没有存在理由。

> **不砍项**：P01 反馈链路（1.5–3 周）**不可砍**。它成本不高，但它是 03 文档定的**首要运营指标**来源，也是二期 Agent 的活水；砍掉它等于砍掉门户的"生命体征传感器"。
